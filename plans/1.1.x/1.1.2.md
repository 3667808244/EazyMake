# EazyMake 1.1.2 — 安全加固与静默错误修复

---

## 1 背景

2026-08-08 对 1.1.1 代码库做了一次多模块代码质量评审（5 个并行 reviewer，覆盖 build 管线 / config+CLI / pkg+repo+lockfile / Lua+util+平台 / 测试套件），发现两类需要立即处理的问题：

1. **安全漏洞（4 处）**——本工具的核心职责是解压并运行第三方包，以下四处直接破坏"不可信输入"的安全边界：
   - **zip-slip / 路径穿越**：`extract_zip` / `extract_targz` 把归档条目名直接拼进 `dest / name`，零校验，恶意包可写到暂存目录之外（含 `C:\...`）。
   - **归档命令注入**：`compile_package()` 用裸 `"..."` 拼 `ar` / `lib.exe` 命令，对象路径来自归档内的源文件名，POSIX 下可注入 shell 命令。
   - **`ezmk_file_write` 硬限制逃逸**：项目根外禁写检查用未 `lexically_normal()` 的字符串前缀比较、无目录边界检查，`../` 可越界。
   - **Lua 沙箱可逃逸**：沙箱 `__index = _G` 暴露 `dofile`/`loadfile`/`load`/`require`/`debug`，utils 脚本可读盘上任意文件、执行磁盘上 Lua，绕过 `[utils.permissions]`。

2. **静默产出错误结果（7 处）**——不报错、不崩溃，但二进制/缓存/锁文件悄悄不对：
   - **链接假成功**：`execute_link` 的 temp→rename 错误码从未检查，rename 失败仍打印 `build_success`。
   - **缓存签名漏输入**：`compile_options_signature` 未纳入 `stdlib` 与 `use_pic`，改 stdlib 或 static↔shared 复用陈旧 `.o`。
   - **`--locked` 误报**：`depends_changed` 把根项目直接依赖与 lockfile 全部包名比较，含传递依赖时恒为 true。
   - **Windows 脚本全挂**：`run_script` 前置 `cd /d ... && ...`，经 `CreateProcessA`（无 shell）执行，`cd` 是 cmd 内建 → 安装脚本在 Windows 上跑不起来。
   - **TOML 写入不转义**：`write_default_config` / `lockfile::save` 把项目名/包名原样拼进 TOML，含引号或换行写坏配置。
   - **非事务化安装**：安装先 `remove_all` 旧包再编译，中途失败 = 旧包没了新包没到；`copy_recursive`/`remove_all` 吞掉 `error_code`，磁盘满也报"installed"。
   - **确定性数据竞争**：`compile_one_source` 在工作线程里 `setenv`/`_putenv_s` 改进程全局环境，`-jN` + `deterministic` 时输出反而不确定。

1.1.2 是 **1.1.x 稳定线的补丁发布**：只修 bug 与安全，**不新增命令、不弃用、不触碰 1.1.0 稳定 API**。1.2.0 功能计划（`plans/1.2.x/`）不受影响。

> **发布口径**：对外（CHANGES.md）表述为「**安全加固 + 正确性修复**」；所有修复均为行为收敛，命令名/配置格式/CLI 参数不变。

## 3 详细设计

### 3.0 前置：`run_command` 扩展 `RunOptions`（C4 + C7 的公共基础）

当前 `run_command(const std::string& cmd, int timeout_sec = 0)`（`include/ezmk/util.hpp:140`）：POSIX 走 `fork` + `/bin/sh -c` + 临时文件重定向；Windows 走 `CreateProcessA`（`src/util.cpp:840`，无 shell）。

新增参数化入口，保留旧签名兼容：

```cpp
struct RunOptions {
    int timeout_sec = 0;
    fs::path cwd;                              // 子进程工作目录（空 = 继承）
    std::map<std::string, std::string> env;    // 附加环境变量（空 = 继承）
};
ProcResult run_command(const std::string& cmd, const RunOptions& opts = {});
```

- **POSIX**：`fork` 后、`exec` 前在**子进程**内 `chdir(opts.cwd)` + 逐项 `setenv(...)`——环境改动只在子进程生效，天然无竞争（这同时修复评审发现的 SOURCE_DATE_EPOCH 数据竞争）。
- **Windows**：`CreateProcessA` 的 `lpCurrentDirectory = opts.cwd`；env 用 `GetEnvironmentStringsA` 克隆当前块 → 替换/追加 `opts.env` 键 → 构建双 `\0` 结尾环境块传给 `lpEnvironment`（Windows 无 POSIX 式"子进程隔离 env"，必须显式传块）。env 为空时不传 `lpEnvironment`（走继承，行为不变）。

> **验收**：`run_command(cmd)` 不带 options 时与重构前行为/输出逐字节一致（`bash build.sh test` 零回归）。原 `timeout_sec` 调用点改传 `RunOptions{.timeout_sec = ...}`。

### 3.1 S1：解压路径包含校验 + 解压上限

**位置**：`src/util.cpp:509-530`（`extract_zip`）、`:558-661`（`extract_targz`）。

**修复 A — 路径包含校验**。新增共享 helper：

```cpp
// 将归档条目名解析为 dest 内的安全目标路径；含 `..`、绝对路径、
// 盘符、`\`（Windows 分隔符）、UNC 前缀 → 抛 std::runtime_error。
fs::path safe_extract_path(const fs::path& dest, std::string_view entry);
```

实现要点：
- 统一把条目名中的 `\` 当分隔符处理（`..\..` 与 `../..` 同权），对 Windows 也用 `/` 或 `\` 切分。
- 拒绝：以 `/`、`\` 开头（绝对路径）、含盘符（`C:` / `X:/`）、含 UNC（`\\` 开头）、任一 `..` 分量。
- 合法路径：`dest / entry` 经 `lexically_normal()` 后必须仍位于 `dest` 之下（前缀 + 目录边界检查，复用评审中确认的 `path_within` 边界写法）。
- 校验失败 → `throw std::runtime_error("unsafe path in archive: " + entry)`（沿用现有解压错误风格，安装会走清理流程）。

`extract_zip` 的 `mz_zip_reader_is_file_a_directory` 分支、`extract_targz` 的 file / `typeflag=='5'` 目录分支全部改用 `safe_extract_path`。

**修复 B — 解压大小上限**。`extract_targz` 目前 `out.resize(compressed.size()*4)` 后按需 `*2` 增长（`:571-583`），大档案 / 高压缩比是 OOM / zip-bomb 向量。新增上限常量（如 `kMaxDecompressedSize = 1 GiB`，`util.cpp` 匿名命名空间常量），增长前检查 `out_pos + out_bytes > kMax` → 抛错。

**修复 C — miniz ABI 布局不一致（编写测试时发现的潜伏 bug）**。`src/util.cpp` 原先在 include miniz 前 `#define MINIZ_NO_TIME` / `MINIZ_NO_ARCHIVE_WRITING_APIS`，而 `src/vendor/miniz_zip.c` 单独编译时**不**带这些宏——`mz_zip_archive_file_stat` 的 `m_time` 字段（`#ifndef MINIZ_NO_TIME` 守卫，`miniz_zip.h:35-37`）导致两 TU 结构体布局差 8 字节：`mz_zip_reader_file_stat()` 按全量布局写，`extract_zip()` 按无 `m_time` 布局读，`m_filename` 读到空/垃圾、字段整体错位，**zip 包解出任何文件条目都会失败**（只有目录条目"看起来正常"）。修复：移除 util.cpp 中这两个宏，使 util.cpp 与 vendor 布局一致（`m_time` 字段保留、writer 声明多出但未调用）。此 bug 自初始提交即存在。

**测试**（`test_util.cpp` 新增）：
- 手工构造恶意 zip（含 `../evil`、`/abs`、`C:\abs`、`a/../../b`、`\` 分隔条目）→ 断言抛错、dest 外无文件产生。
- 手工构造恶意 tar.gz（条目名同上）→ 同上；超上限 gzip 数据 → 抛错。

### 3.2 S2：归档命令路径转义

**位置**：`src/pkg.cpp:443-471`。当前 `ar rcs "<lib>" "<obj>"...` / `lib.exe /OUT:"<lib>" "<obj>"...` 用裸 `"..."`，对象路径来自归档内源文件名（POSIX 允许 `$()`、`` ` ``、`;`、`"` 等字符）。

**修复**：把归档命令构造提取为可单测的 helper（`include/ezmk/pkg.hpp` + `src/pkg.cpp`），路径统一经 `util::escape_shell_arg()` 转义（与 `git_clone`/`git_pull` 在 `util.cpp:1069-1089` 的做法一致）：

```cpp
// MSVC: lib.exe /OUT:...，GCC/Clang: ar rcs ...；所有路径转义
std::string build_archive_command(bool is_msvc,
                                  const fs::path& lib_out,
                                  const std::vector<fs::path>& objects);
```

- `compile_package()` 改为调用该 helper；Windows 侧 `lib.exe` 同样转义（`CreateProcessA` 不经 shell，但统一转义无害且防 CRT 解析歧义）。

**测试**：`test_pkg.cpp` 新增 `build_archive_command` 单测——含空格、`$`、反引号、反斜杠的路径断言正确转义（`$(` 前有 `\`、无未转义的 `$(` 紧跟开引号）；空对象列表；`ar`/`lib.exe` 两种前缀。

### 3.3 S3：`ezmk_file_write` 硬限制改为规范化 + 边界检查

**位置**：`src/lua_api.cpp:553-575`。当前 `inside_project` 等三个检查用 `fs::absolute().generic_string()` 前缀比较，未 `lexically_normal()`、无目录边界 → `../evil` 与 `<root>X` 均逃逸；而权限层 `:582` 已正确使用 `lexically_normal()`。

**修复**：
- **复用既有 helper**：`lua_api.cpp` 已有 `norm_path()`（`fs::absolute` + `lexically_normal`，`:67-71`）与 `path_within()`（目录边界检查：`child==parent` 或 `child[parent.size()]=='/'`，`:74-82`）——权限层已正确使用它们。`ezmk_file_write` 的硬限制改为这三处统一走 `norm_path` + `path_within`，替代裸字符串前缀比较。
- 原注释"canonicalize both paths for reliable prefix check"保留，说明现在真正规范化。

**测试**（`test_lua.cpp` 新增）：`file_write("<root>/../evil")`、`file_write("<root>X/evil")`（前缀边界）、`file_write("<parent>/evil")` → 拒绝；`file_write("<root>/sub/../test.txt")`（根内 `..` 归一化）→ 放行。

### 3.4 S4：Lua 沙箱收敛

**位置**：`src/lua_api.cpp:1001-1003`。沙箱 metatable `__index = _G`，且 vendor `linit.c:43-52` 保留了 `base`（含 `dofile`/`loadfile`/`load`）、`package`、`debug`——utils 脚本可完全绕过 `[utils.permissions]` 读任意文件、执行磁盘上 Lua。

**修复**：不再让沙箱回退到裸 `_G`。改为**受限全局表**：

- 实现：新建 `restricted` 表，遍历 `_G` 把不在黑名单中的键拷入（`lua_rawset`，避免触发元表）；沙箱 metatable `__index = restricted`。
- **黑名单**：`dofile`、`loadfile`、`load`、`require`、`debug`、`package`、`collectgarbage`、`_G`。
- **`_G` 自引用**：受限表同时剔除 `_G`（否则 `_G.dofile` 仍可达真实全局表），并在沙箱上设 `sandbox._G = sandbox`——脚本照常用 `_G`，读回退走 sandbox → restricted，`_G.dofile` 解析为 nil。
- `ezmk` API、`io`/`os`（本就被移除）之外的常用函数（`print`/`tostring`/`ipairs`/`table`/`string`/`math`/`type` 等）保留。
- **实现注意**：栈索引一律用相对值——run_script 前可能有 API 调用残留的栈值（测试套件中实测栈底有 3 个残留 number），硬编码绝对索引会索引到残留值触发 panic。
- 注释同步改写：明确沙箱是**便利隔离 + 权限模型的执行边界**，不再声称"编译期移除 os/io 即安全"。

**兼容性**：utils 脚本若依赖 `dofile`/`loadfile`/`require`/`debug` 会拿到 `nil`。官方 utils 无此依赖；文档（`docs/en|zh/utils.md`）补一句"沙箱禁用文件加载函数"。**hooks 不受影响**——hooks 走 `run_lua_script_with_ctx`，其 `_ENV` 独立（权限模型按设计对 hooks 不生效，本次不改动该语义）。

**测试**（`test_lua.cpp` 新增）：沙箱内 `_G[name]` 对全部逃逸面为 nil、`print`/`tostring` 仍可达、调用 `dofile` 报错（exit 1）；原有沙箱隔离测试（arg 数校验、`io`/`os` 不可用、`ezmk.*` 可用）全部保持通过。

### 3.5 C1：`execute_link` rename 失败不再报成功

**位置**：`src/build.cpp:996-998`。`fs::rename(output_tmp, output, ec)` 后未检查 `ec` 直接 `build_success`。

**修复**：提取 `atomic_rename` helper（`build.cpp` 匿名命名空间，与 `compile_one_source` 在 `cache.cpp:601-607` 的 fallback 语义一致）：

```cpp
// 先 rename，失败则 copy_file 覆盖 + 清理 temp；都失败 → 抛 fatal（含路径与原因）
void atomic_rename_or_fail(const fs::path& from, const fs::path& to);
```

- `execute_link` 改用该 helper：失败 → `util::fatal`（`build_failed` + 输出路径 + 原因），不再打印 `build_success`。
- 顺带：link 成功消息现在只在产物真正落盘后输出。

**测试**：OS 层 rename 失败难在 CI 稳定复现。单测覆盖 `atomic_rename_or_fail` 的可测分支（目标已存在 → 覆盖成功；from 不存在 → 抛 fatal）；其余靠人工冒烟（Windows 占用产物 exe 时构建应报失败）。

### 3.6 C2：缓存签名纳入 `stdlib` + `use_pic`

**位置**：`src/cache.cpp:171-211`（`compile_options_signature`）。当前签名含 std_flag / flags / include_dirs / extra_includes / msvc_flags / deterministic，但**不含**在 `build_compile_args` 中注入的 `stdlib`（`:357-360`）与 `use_pic`（`:368`）。

**修复**：为签名函数增加两个参数：

```cpp
std::string compile_options_signature(const config::CompileSection& compile,
                                      const std::vector<fs::path>& extra_includes,
                                      std::string_view std_flag,
                                      std::string_view stdlib,      // 新增
                                      bool use_pic);                 // 新增
```

- 保持两个旧签名（`compile` 单参 / `compile+extra+std`）为转发重载（默认 `{}`/`""`/`false`），避免改到不相干调用点。
- 主调用点（`check_cache` 路径）把 `CompileInput.stdlib` 与 `use_pic` 传入。
- 注释更新：明确「所有改变编译命令的输入都必须进签名」作为防回归约定。

**测试**（`test_cache.cpp` 新增）：同配置仅 `stdlib` 不同（libstdc++ vs libc++）→ 签名不同；仅 `use_pic` 不同 → 签名不同。回归：现有签名测试（改 flag/include/msvc_flags/deterministic 使签名变化的用例）保持通过。

### 3.7 C3：lockfile 记录直接依赖，`depends_changed` 精确比较

**位置**：`src/lockfile.cpp:188-200`（`depends_changed`）；生成侧 `src/pkg.cpp:970-1012`。

**问题**：`depends_changed` 把 cfg 的**直接**依赖（`libs`+`want`）与 lockfile 的**全部**包名（含传递/自动安装）比较 → 有传递依赖时恒 true → `--locked` 恒误报。且完全忽略版本/约束变化。

**修复**：
- **lockfile 元数据新增 `direct_deps`**（根项目直接依赖名集合）：`lockfile::save` 在 `[metadata]` 写入 `direct_deps = ["a", "b"]`；`lockfile::load` 解析之（缺字段 → 空集，兼容旧文件）。
- **`depends_changed` 改为**：比较 `cfg.depends` 名集合与 `lf.metadata.direct_deps`。旧 lockfile（无该字段）→ 视为 changed（`--locked` 报"锁文件与配置不一致，请重新生成"）——属预期行为收敛，重新 `pkg install` 即修复。
- 版本/约束变化检测：为直接依赖记录 name + version spec（`direct_deps` 存 `name` 或 `name@spec`），比较时含约束，`^1.0.0` → `^2.0.0` 也能触发。
- 生成侧：`pkg.cpp` 写 lockfile 时把本次解析到的**直接**依赖（非全部安装包）写入 `direct_deps`。

**测试**（`test_lockfile.cpp` **新建**）：
- 有传递依赖的项目：生成 lockfile → `depends_changed` 返回 false（不再误报）。
- 改直接依赖约束（`^1` → `^2`）→ 返回 true。
- 改 `[depends.want]` → 返回 true。
- `--locked` 集成：建项目 → 装带传递依赖的包 → `ezmk pkg install --locked` 成功；改配置 → `--locked` 报错。

### 3.8 C4：Windows 脚本执行修复

**位置**：`src/util.cpp:1087-1119`（`run_script`）。当前在 Windows 拼 `cd /d "<cwd>" && <interpreter-cmd>`，经 `CreateProcessA`（无 shell）执行，`cd` 非可执行文件 → 任何 `.sh`/`.ps1`/`.bat` 安装脚本都起不来。

**修复**（复用 3.0 的 `RunOptions.cwd`）：
- `run_script` **删除 cd 前缀**：`cmd` 只含解释器调用（`bash <script>` / `powershell ... <script>` / `cmd /c <script>`），工作目录改由 `run_command(cmd, RunOptions{.cwd = cwd})` 注入——Windows 走 `lpCurrentDirectory`，POSIX 走 fork 后 `chdir`。
- `#ifdef EZMK_WIN` 分支收敛（`bash` 路径无需区分平台差异，统一 `bash`；PowerShell 路径的 `cd` 依赖一并移除）。

**测试**：
- `test_util.cpp`：`run_script` 生成的命令不再含 `cd ` 前缀（可对命令串断言，平台无关）。
- Windows 冒烟（人工/CI）：带 `.bat` 安装脚本的包安装成功、脚本 cwd 正确。

### 3.9 C5：TOML 写入统一转义

**位置**：`src/config.cpp:744-772`（`write_default_config`）、`src/lockfile.cpp:83-122`（`lockfile::save`）。两者把用户可控字符串（项目名/包名/版本/source_url）原样拼进 TOML。

**修复**：新增共享 helper（`src/util.cpp` + `include/ezmk/util.hpp`）：

```cpp
// 把字符串安全地写为 TOML 双引号字符串字面量（转义 \\ \" \n \t \r）
std::string toml_quote(std::string_view s);
```

- `write_default_config` 与 `lockfile::save` 全部改经 `toml_quote`；`repo.cpp:102-132` 的 `save_repo_list` 已有同类转义，一并收敛到同一 helper（行为不变）。

### 3.10 C6：安装事务化 + fs 错误不再吞

**位置**：`src/pkg.cpp:700-709`（安装先删旧包）、`src/util.cpp:254-262`（`remove_all`/`copy_recursive` 吞 `error_code`）。

**修复 A — fs 错误浮出**：`remove_all` / `copy_recursive` 改为出错即抛：

```cpp
void remove_all(const fs::path& p);    // ec 非空 → throw std::runtime_error(p)
void copy_recursive(const fs::path& from, const fs::path& to);
```

- 需确认现有调用点（`remove_all` 删临时/缓存目录等）对"目标不存在"的语义：`fs::remove_all` 对不存在路径返回 0、不设 ec → 不抛，现有行为不变；只有真实失败（权限/磁盘满）才抛。逐个调用点过一遍注释中的预期。

**修复 B — 安装事务化**：`install_path = dest_dir / pkg_name` 处**删除**当前 `:708` 的 `util::remove_all(install_path)`。改为在**最终落盘前**做 swap：

```
阶段产物就绪（stage 目录完整）→
  旧包存在 → rename install_path → install_path ".bak"   （失败即中止，旧包完好）
  rename stage → install_path                              （失败 → 回滚 .bak）
  remove_all(install_path ".bak")
```

- 依赖解析、编译、hook 都在 swap 前完成——任何一步失败，旧版本保持可用，符合「安装失败不毁掉既有环境」的语义。
- 原 `overwrite_confirm` 确认逻辑保留（确认后仍只在 swap 点动旧包）。

**测试**：
- `test_util.cpp`：`copy_recursive` 源不存在 → 抛；`remove_all` 真实失败场景难以构造，断言"不存在路径不抛"。
- `test_pkg.cpp`（集成向）：预置已装包 → 构造一个会在编译期失败的升级 → 断言旧版本仍存在于 `install_path`（未被动）。

### 3.11 C7：`SOURCE_DATE_EPOCH` 数据竞争

**位置**：`src/cache.cpp:556-585`。`compile_one_source`（线程池 worker 内）用 `_putenv_s`/`setenv` + 事后恢复改进程全局环境——`-jN` 时线程间互踩，确定性构建输出不确定。

**修复**（复用 3.0 的 `RunOptions.env`）：删除 `setenv`/`_putenv_s`/恢复三段，改为：

```cpp
util::RunOptions opts;
if (!sde_str.empty()) opts.env["SOURCE_DATE_EPOCH"] = sde_str;
auto res = util::run_command(cmd, opts);
```

- POSIX：fork 后子进程内 setenv → 不污染其他 worker，且编译进程在 exec 前拿到变量。
- Windows：`lpEnvironment` 环境块 → 子进程隔离，无全局副作用。
- `old_sde` 保存/恢复逻辑整体删除（不再需要——环境不再改动父进程）。

**测试**（`test_cache.cpp` / 集成）：
- 单测 `run_command`：`RunOptions.env` 传入后子进程 `getenv` 可见、父进程环境未被改动（POSIX 可断言父进程 env 不变）。
- 集成：`deterministic = true` 项目 `-j4` 构建两次 → 产物 hash 一致（现行为可能不一致的用例转为断言一致）。
