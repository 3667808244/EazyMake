# EazyMake 1.1.3 — 安全收敛（二轮）与健壮性收口

---

## 1 背景

2026-08-09 对 1.1.2 代码库做了第二轮多模块安全与质量审计（3 个并行 reviewer，覆盖 pkg/repo/lockfile/crypto、lua/util/build/toolchain、main/cli/config/cache/watcher），并逐条人工核验高风险结论。1.1.2 已修复第一轮 4 处漏洞，本轮审计发现第二层问题：

**安全（5 处）**——多数是「文档承诺的安全属性与实际不符」：
- **钩子沙箱仍裸 `_G`**：1.1.2 S4 只收敛了 utils 脚本（`run_script`）的沙箱；构建钩子与安装钩子共用的 `run_lua_script_with_ctx` 沙箱 `__index` **仍直接指向裸 `_G`**（`lua_api.cpp:1189-1190`），`dofile`/`loadfile`/`load`/`require`/`debug`/`package` 全部可达。而 `pkg.cpp:168` 注释声称「Lua scripts run in sandbox — no editor review needed」——沙箱承诺是空的。
- **包名路径穿越**：`validate_pkg()` 从不校验 `project.name`，恶意包 `name = "../../evil"` 直接拼进 `dest_dir / pkg_name`（`pkg.cpp:714`）→ 越界写文件；lockfile 恢复路径（`lockfile.cpp:155`）同样继承。
- **URL 直装无完整性保证**：sha256 校验仅在 `expected_sha256` 非空时执行（`pkg.cpp:636`）；从 URL 直接安装无 sha256 时完全跳过，显式 `http://` 还允许明文下载。
- **POSIX 编译/链接 flags 命令注入**：`join_shell_args` 的引号元字符集不全（`cache.cpp:415-417`，漏 `;|&#()<>` 等），链接 flags 完全不引号（`build.cpp:275-277`）；`run_command` 在 POSIX 走 `/bin/sh -c`（`util.cpp:1099`）→ 恶意包 `link.flags = ["-lfoo; echo pwned"]` 被 shell 执行。Windows 走 `CreateProcessA` 不解释这些字符，主目标（MSYS2）不受影响。
- **编辑器命令注入**：`open_in_editor` 把 `EDITOR`/`VISUAL` 环境变量派生的 editor **未加引号**拼进 shell 字符串（`util.cpp:1249-1251`）→ POSIX 下 `EDITOR="vim; evil"` 注入。（注：`util.cpp:1231` 的 `system()` 只处理硬编码的 vim/nano/emacs 常量，非漏洞。）

**健壮性（5 处）**——不报错但行为错/易崩：
- `SOURCE_DATE_EPOCH` 非数字 → `stoull` 抛异常且无 catch，`-jN` 下崩 worker 线程（`cache.cpp:560`）。
- `~` 前缀只判断 `[0]=='~'` 就 `substr(2)`，`"~abc"` 被截成 `"c"`（`config.cpp:671`）。
- `file_watcher` 的 `g_overlapped_pool` 是**文件级全局**，多实例时第二个的 `win32_cleanup()` 令第一个悬垂（`file_watcher.cpp:114`）。
- `recursive_` 是死代码——被赋值但三个平台实现都不读（`file_watcher.hpp:74`），递归被静默忽略。
- 边缘：`name.back()` 对空串是 UB（`file_watcher.cpp:81`）、`.o`/`.tmp.o` 魔法字符串散落、CLI 参数嵌入 NUL 未防御（`cli.cpp:618`）。

**代码质量（3 处）**——多数已在 1.1.2 计划「延后项」点名：
- 手写 103 行 JSON 解析器（`config.cpp:268-371`），而项目已依赖 `nlohmann/json`（`cache.cpp:38`）；不支持 Unicode/反斜杠转义、无递归。
- 大函数：`parse_config()` 344 行、`compile_one_source()` 225 行。
- `cli.cpp` 三个 `parse_*` 函数大量重复（positional 校验出现 10+ 次）。

1.1.3 是 **1.1.x 稳定线的补丁发布**（承接 1.1.2）：只修 bug、安全与低风险重构，**不新增命令、不弃用、不触碰 1.1.0 稳定 API**。1.2.0 功能计划不受影响。

> **发布口径**：对外（CHANGES.md）表述为「**安全收敛（二轮）+ 健壮性收口**」；命令名/配置格式/CLI 参数不变。

## 3 详细设计

### 3.1 S1：钩子沙箱收敛

**位置**：`src/lua_api.cpp:1186-1191`（`run_lua_script_with_ctx` 沙箱）、`src/pkg.cpp:158-192`（安装脚本执行 + 注释）。

**问题**：1.1.2 S4 只收敛了 utils 脚本。`run_lua_script_with_ctx`（构建钩子 `pre_build`/`post_build`/`on_failure` + 安装钩子 `preinstall`/`postinstall` 共用）的沙箱 metatable `__index` 直接指向裸 `_G`，`dofile`/`loadfile`/`load`/`require`/`debug`/`package`/`collectgarbage` 全部可达。而 `run_script`（utils 脚本）已实现受限全局表（`lua_api.cpp:1003-1028`）。两处行为不一致，且 `pkg.cpp:168` 注释向用户声称「在沙箱中运行」。

**修复 A — S1a：受限全局表统一（P0）**：
- 把 `run_script` 的受限全局表构建提取为共享 helper（`lua_api.cpp` 匿名命名空间）：

  ```cpp
  // 构建受限全局表：遍历 _G 拷入除黑名单外的键（lua_rawset，避免触发元表）
  void push_restricted_globals(lua_State* L);
  ```

- `run_lua_script_with_ctx` 的沙箱改为与 `run_script` 一致：`sandbox mt.__index = restricted`（剔 `dofile`/`loadfile`/`load`/`require`/`debug`/`package`/`collectgarbage`/`_G`）+ `sandbox._G = sandbox` 自引用。
- **实现注意**：沿用 1.1.2 S4 的约定——栈索引一律用相对值，不硬编码绝对索引。
- **注释诚实化**：`pkg.cpp:168` 注释改为「Lua 安装脚本运行在受限沙箱（禁文件加载/内省函数），但 `ezmk.*` API 仍以当前用户权限执行」；`exec_question` 确认文案补一句「安装脚本以当前用户权限运行，请确认来源可信」。

**修复 B — S1b：安装钩子权限门控（P1，可选）**：
- 安装钩子（第三方代码）设 `g_in_script_context = true` + 从包 `ezmk.toml` 加载权限（复用 `[utils.permissions]` 与 0.2.5 的 legacy 兼容模式：未声明权限 → 保持全权限 + deprecation 警告），使 `ezmk.file_read`/`file_write`/`run` 对安装钩子生效权限门控。
- **风险**：语义变更最大的一项。若影响发布门槛（官方/生态安装钩子回归），允许收口为「本版只做 S1a + 文档说明」，S1b 延到 1.2.0。决策点见 §4 阶段一末尾。

**兼容性**：钩子脚本若依赖 `dofile`/`loadfile`/`require`/`debug` 会拿到 `nil`。官方钩子无此依赖；文档补一句「钩子沙箱禁用文件加载函数」（`docs/en|zh/build_hooks.md` / `docs/en|zh/pkg.md`）。

**测试**（`test_lua.cpp` 新增）：`run_hook_script` / `run_install_hook_script` 沙箱内 `_G[name]` 对全部逃逸面为 nil、`print`/`tostring` 仍可达、调用 `dofile` 报错；原 utils 沙箱测试保持通过（确认 helper 提取无行为漂移）。S1b 若实现：安装钩子未声明权限调用 `ezmk.run` → legacy 警告仍执行；声明只读权限后调用 `ezmk.run` → 拒绝。

### 3.2 S2：包名校验

**位置**：`src/pkg.cpp:220-255`（`validate_pkg`）。

**修复**：`validate_pkg` 在解析 `cfg.project.name` 后增加名校验（复用既有 `safe_extract_path` 的拒绝规则思路）：

```cpp
static void validate_pkg_name(const std::string& name) {
    if (name.empty() || name == "." || name == "..") throw ...;
    if (name.find('/') != npos || name.find('\\') != npos) throw ...;   // 路径分隔符
    if (name.find(':') != npos) throw ...;                               // 盘符
    if (name[0] == '/' || name[0] == '\\' || name[0] == '.') throw ...; // 绝对/隐藏
}
```

- 校验失败 → `std::runtime_error("invalid package name: <name>")`，安装走既有清理流程（stage 删除）中止。
- lockfile 恢复路径（`lockfile.cpp:155`）与 `pkg remove`/`search`（`pkg.cpp:1067/1087`）共用此名来源，一并受益（remove 侧的用户输入名建议同样校验，防自伤）。
- 拒绝规则与解压 `safe_extract_path`（`util.cpp:570-609`）保持一致口径。

**测试**（`test_pkg.cpp` 新增）：构造含 `../evil`、`a\\b`、`C:x`、`/abs`、`.` 名的包目录 → `validate_pkg` 抛错；正常名放行。

### 3.3 S3：URL 安装完整性

**位置**：`src/pkg.cpp:588-651`（URL 判定 + 下载 + sha256 校验）。

**修复**：
- **无 sha256 确认**：`expected_sha256` 为空且走 URL 分支（`is_url == true`）时，下载前打印警告「未提供 sha256，无法校验包完整性」，并走与 `overwrite_confirm` 相同的 `confirm()` 流程（`-y` 可跳过，行为与现有确认逻辑一致）。
- **拒 `http://` 明文**：URL scheme 为显式 `http://` 时打印警告并要求确认（提示 MITM 风险，建议 `https://`）；不新增 flag，保持补丁零新接口。
- 校验逻辑本身不动（`pkg.cpp:636-651` 已正确）。

**测试**（`test_pkg.cpp`）：无 sha256 的 URL 安装 → 断言出现警告/确认提示（非 `-y` 时中止）；`http://` URL → 提示 MITM 警告。

### 3.4 S4：POSIX 编译/链接 flags 元字符引号

**位置**：`src/cache.cpp:406-431`（`join_shell_args`）、`src/build.cpp:275-277`（GCC 链接 flags）。

**修复**：
- `join_shell_args` 的 `need_quote` 元字符集补全为 shell 全部相关字符：

  ```cpp
  bool need_quote = false;
  for (char c : a) {
      if (c==' '||c=='\t'||c=='"'||c=='\''||c=='\\'||c=='`'||c=='$'||
          c==';'||c=='|'||c=='&'||c=='#'||c=='('||c==')'||c=='<'||c=='>'||
          c=='~'||c=='*'||c=='?'||c=='['||c==']'||c=='{'||c=='}'||c=='!'||
          c=='\n'||c=='\r') { need_quote = true; break; }
  }
  ```

  引号分支已用 `escape_shell_arg`（`$`/`` ` `` 被转义为 `\$`/`` \` ``，引号内字面）→ 安全。**不加白名单，用黑名单是保守方向**；补注释说明该集合与 `/bin/sh` 解析规则对应。
- `build.cpp:275-277` 链接 flags 改为与 link_dirs 一致的双引号包裹：`cmd << " \"" << util::escape_shell_arg(f) << "\""`。MSVC 侧（`build.cpp:306-313`）同样统一（`CreateProcessA` 无 shell，但一致转义无害）。
- `escape_shell_arg` 本身不动（已正确转义 `" \ ` $`）。

**测试**（`test_cache.cpp` / `test_util.cpp`）：`join_shell_args` 对含 `;`/`|`/`&`/`#`/`(` 的 arg 输出双引号包裹且 `$`/`` ` `` 被 `\` 转义；含空格的 arg 行为不变；回归：现有签名测试保持通过。
