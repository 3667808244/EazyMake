# EazyMake 1.1.0-pre.3 — 缺陷收集与未实现项补全

---

聚合 pre.2（文档检查）之后的全量已知缺陷与未实现项，作为 pre.3 的工作清单。包含测试系统缺陷、工具/文档缺陷，以及 pre.1 / pre.2 明确延后的发布流水线项。

---

## ⛔ 发布门槛（Release Gate）

**没有完成实现，或破坏了兼容性的版本，不得正式发布。**

任何版本（尤其 `1.1.0` 正式版）发布前**必须同时满足**以下三条，任一不满足即阻断发布：

1. **实现完整**：本版本计划清单（含 pre.3 的缺陷与未实现项）全部完成或明确收口——不允许存在"计划内但未实现"的悬空项
2. **兼容性不破坏**：遵守 [CHANGES.md](../../CHANGES.md#api-stability) 的 API 稳定性承诺——公共 API（命令、`ezmk.toml` 核心配置节 `[project]`/`[compile]`/`[link]`/`[depends]`/`[test]`/`[install]`）无破坏性变更；破坏性变更仅在 `2.0.0` 引入
3. **零回归**：全量测试通过（`bash build.sh test` 单元 + `test-all` 含集成）

> 触发条件：发布 tag 前执行发布清单核对；CI 测试工作流（pre.3 3.2.1）接入后，作为自动 gate 的第一步。

## 1 背景

`1.1.0-pre.2` 完成了文档审计并补齐了 pre.1 遗留项，但过程中系统性检查代码与文档时发现：

1. **测试系统存在实现缺陷**：`run_tests()`（`src/build.cpp`）的超时逻辑未实现、Catch2 输出依赖脆弱的文本解析、`shared`/`utils` 类型的 build-first 检查粗糙；watch 集成测试存在已知的 timing-sensitive 误报可能
2. **缺少 CI 测试工作流**：`.github/workflows/` 仅有 `release.yml`（Release 触发，从未实际跑过），**没有任何在 push/PR 上运行 `bash build.sh test` 的工作流**——回归全靠本地
3. **若干文档引用了不存在的工具/过时数据**：`package_authoring.md` §6.3 引用 `ezmk utils sha256`（未发布）；`ezmk-test` skill 记录的测试基线已过时（~538/2440，实际 545/2613）
4. **pre.1 / pre.2 延后项仍未做**：CI 激活、Homebrew formula、winget manifest、`plans/release/1.1.0.md`、Tutorial 09/10 章节
5. **zsh 补全从未在真实 zsh 环境验证**（Windows 无法验证）；i18n 三方一致性无自动化脚本

本版本将这些缺陷与未实现项汇总为可执行的清单。

## 3 缺陷清单与详细设计

### 3.1 测试系统缺陷（`src/build.cpp` `run_tests()`）

#### 3.1.1 ezmk 内置框架 30s 超时未实现（P0）

- **位置**：`src/build.cpp:1939`（`timed_out` 声明）、`src/build.cpp:1990`（"Run test with timeout (30s hardcoded)" 注释）
- **现象**：`timed_out` 计数器声明后**从未被赋值**（恒为 0）；`run_command()`（`src/util.cpp:815`）签名 `RunResult run_command(const std::string& cmd)` **没有 timeout 参数**。注释声称的 30 秒硬超时实际不存在。
- **影响**：一个死循环/挂起的测试会**无限阻塞整个测试套件**，无任何保护。
- **建议**：给 `run_command()` 增加可选的 timeout 参数（POSIX 用 `alarm`/`waitpid` 超时，Windows 用 `WaitForSingleObject` 超时 + `TerminateProcess`），`run_tests()` 传入 30s；超时测试记为 FAIL 并归入 `timed_out` 计数。

#### 3.1.2 Catch2 输出解析脆弱（P1）

- **位置**：`src/build.cpp:1822~1894`
- **现象**：对 Catch2 控制台输出做**纯文本解析**——逐行 `find("PASSED")` / `find("FAILED")` 判定用例结果，再对 `test cases: N | M passed | K failed` 用 `std::stoi` 抠数字，最后 `total_cases = passed_cases + failed_cases`（`build.cpp:1894`）**覆盖掉解析出的 total**。
- **影响**：① 测试名或断言消息里含 "PASSED"/"FAILED" 子串会被误判；② Catch2 格式升级即解析失效；③ 计数可能把断言数与用例数混淆（`-s` 模式每个 CHECK 都打一行 PASSED）。
- **建议**：改用 Catch2 v3 的 `--reporter junit`（或 `-r xml`）输出并解析 XML，或直接透传 Catch2 的退出码 + 汇总行，放弃逐行猜测。

#### 3.1.3 `run_tests()` build-first 检查对 shared/utils 粗糙（P1）

- **位置**：`src/build.cpp:1555~1568`（`check_built` lambda）
- **现象**：仅 `executable`（查 exe）和 `static`（查 `.a`/`.lib`）有真实产物检查；`shared`/`utils` 只 `return util::file_exists(build_dir)`——`build/` 目录在任意一次构建后恒存在。
- **影响**：`shared` 项目的 `.dll` 被删除后 `ezmk test` 会跳过构建，链接时失败；`utils` 类型无意义。
- **建议**：`shared` 检查 `build/<name>.dll`/`.so`（Win 下 DLL + 导入库）；`utils` 类型直接走 `build_project()` 或明确跳过构建步骤。

#### 3.1.4 watch 集成测试 timing-sensitive（P1）

- **位置**：`test/test_integration.cpp:289~292`
- **现象**：测试自文档标注 "Watch mode test: no rebuild detected (timing-sensitive, may be false negative)"，实际 `test-all` 运行时确实出现了 `0` 的 warning。
- **影响**：CI（若接入）会出现非确定性失败。
- **建议**：加大轮询等待窗口 / 用固定 debounce 而非真实时间；或将该断言降级为 `CHECK` 并带 INFO，避免 CI 红色。

### 3.2 工具与文档缺陷

#### 3.2.1 无 CI 测试工作流（P0）

- **位置**：`.github/workflows/`（仅 `release.yml`）
- **现象**：`release.yml` 只在 tag/Release 时触发（且从未实际运行过）；**没有任何在 push / PR 上运行 `bash build.sh test` 的工作流**。
- **影响**：回归保护完全依赖本地；pre.2 的"零回归"承诺无法在 CI 上持续验证。
- **建议**：新增 `.github/workflows/ci.yml`：push/PR 触发，Ubuntu + MSYS2 环境跑 `bash build.sh test`（单元）；可选 `test-all`。需确认 MSYS2 上如何装 g++/python。

#### 3.2.2 `package_authoring.md` 引用不存在的 `ezmk utils sha256`（P1）

- **位置**：`docs/en/package_authoring.md:297`（`# Or:\nezmk utils sha256 ... # if available`）、`docs/zh/package_authoring.md`（pre.2 同步补入）
- **现象**：官方工具列表（`cli.md` / `docs/en/technical.md`）只有 `cc` / `link` / `gen-build-package`，**无 `sha256` 工具**；全仓 `*.lua` 无匹配。
- **影响**：读者按文档执行会得到"工具不存在"。
- **建议**：二选一——在 `ezmk-official-utils` 包补一个 `sha256` 工具，或删掉文档中的该行。

#### 3.2.3 `install.sh` 安装的 zsh 补全不生效（P1）—— 已修复

- **位置**：`install.sh:143~165`（zsh completions 块）
- **现象**：补全文件 `res/ezmk.zsh` 手动安装（复制到 fpath 目录 + `compinit`）**验证有效**；但经 `install.sh` 安装后**不生效**。
- **根因（2 个真实缺陷）**：
  1. **幂等性检查过松**：`grep -q 'zsh/completions' "$ZSHRC"` 只要 `.zshrc` 任何一行含 "zsh/completions"（含注释），就误判"已配置"而跳过写入 `fpath`/`compinit` → 补全文件复制到位但从不被加载
  2. **硬编码 `$HOME/.zshrc`**：zsh 实际读 `$ZDOTDIR/.zshrc`（默认 `$HOME/.zshrc`），设置 `ZDOTDIR` 的用户配置写入了 zsh 不读的文件
- **修复（pre.3 已应用）**：改为精确匹配 marker `# Added by EazyMake installer`（`grep -qF`），并 `ZSHRC="${ZDOTDIR:-$HOME}/.zshrc"`
- **遗留**：修复需在 Linux/macOS 真实 zsh 环境回归——跑一遍 `install.sh`（或复现安装步骤）后新开 zsh，验证顶层别名与子命令补全生效

#### 3.2.4 i18n 三方一致性无自动化脚本（P1）

- **位置**：`include/ezmk/i18n_keys.def` + `locale/en.json` + `locale/zh.json`
- **现象**：pre.2 确认三方 273 key 一致，但**靠手动对比**（pre.2 设计文档 §7："目前无自动化脚本，手动对比容易遗漏"）。
- **影响**：新增 key 时可能漏改 JSON 或 .def，回归 `{???}` 类问题。
- **建议**：在 `scripts/` 下加 `check_i18n.py`（读 def + 两份 JSON，比对 key 集合三向一致），纳入 CI。

#### 3.2.5 过时文档数据（P2）

- **位置**：`.claude/skills/ezmk-test.md:74~76`（"~538 test cases / ~2440 assertions"、"Integration tests: 7 scenarios"）
- **现象**：实际为 **545 用例 / 2613 断言**（单元），集成 8 个场景（`docs/en/technical.md`）。skill 数据滞后。
- **建议**：同步更新 skill 与任何引用过时测试基线的文档；或改为不写死数字。

## 6 跨版本关注点 / 风险

- **超时实现跨平台**：POSIX `waitpid`+`alarm` 与 Windows `WaitForSingleObject`+`TerminateProcess` 两条路径都要测；注意子进程退出后回收。
- **CI 首次落地**：MSYS2 GitHub Actions 上安装 g++/python 的步骤要在 workflow 里显式写，避免 `bash build.sh` 因缺 python 走空 locale 分支。
- **watch flaky 与 CI 叠加**：CI 一旦接入，3.1.4 的 timing-sensitive 测试可能成为主要红灯来源，优先级应提前。
- **`ezmk utils sha256` 归属**：工具在 `ezmk-official-utils` 包（`ezmk-repo` 仓库）里实现，注意与主仓库的发布节奏同步；若选择删除文档引用，则无需动仓库。
- **延后边界**：3.3.x 全部是发布流水线建设，若 pre.3 时间紧，可整体并入 1.1.0 正式版收尾；但 3.1.x / 3.2.x（缺陷修复 + CI + 文档修正）建议在 pre.3 内完成。
