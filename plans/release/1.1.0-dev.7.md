# EazyMake 1.1.0-dev.7 — 包生态拓充与包处理改善

---

## 1 背景

当前 EazyMake 的包处理存在两个改进方向：

1. **包生态不足**：官方仓库（`ezmk-repo`）现有 22（0.9.7）+ 20（0.9.8）= 42 个包，但缺少网络通信（HTTP/gRPC）、数据库连接（SQLite/PostgreSQL/Redis）、序列化（Protobuf/msgpack）、科学计算（Eigen）、测试框架（Google Test）等领域的常用库。用户在这些场景下仍需手动编译链接。

2. **缺失依赖的处理粗糙**：
   - 构建时硬依赖（`[depends].lib`）未安装 → **无前置检查**，直接被 g++/ld 原始错误捕获（`cannot find -lxxx` / `fatal error: 'xxx.h' file not found`），用户得不到语义化提示
   - `pkg install` 时可选依赖（`[depends].want`）缺失 → 静默跳过，用户不知道有哪些可选增强可以安装
   - 仓库安装时硬依赖缺失 → 直接报错退出，不会自动安装，用户需手动逐个 `pkg install`

本版本聚焦包生态拓充（扩展仓库覆盖面）和包处理改善（构建时前置检查 + 自动安装 + 交互式可选依赖）。

## 3 包处理改善

### 3.1 构建时硬依赖前置检查

#### 3.1.1 问题

当前 `build_project()` 扫描 `.ezmk/pkg/` 获取已安装包列表 `installed_pkgs`，但对 `[depends].lib` 中未安装的包无任何检查——构建直接进行，直到编译器报 `file not found` 或链接器报 `cannot find -lxxx`。

#### 3.1.2 设计

在 `prepare_build_state()` 中，收集已安装包信息后，立即遍历 `cfg.depends.libs` 检查是否均已安装：

```cpp
// 伪代码 — 在 src/build.cpp prepare_build_state() 中
// 位置：want.lib 处理之后（当前行 679）、版本验证之前（当前行 681）

std::vector<std::string> missing_hard_deps;
for (auto& entry : cfg.depends.libs) {
    if (installed_pkgs.find(entry.name) == installed_pkgs.end()) {
        missing_hard_deps.push_back(entry.name);
    }
}

if (!missing_hard_deps.empty()) {
    // 打印语义化错误
    // 检查已注册仓库中是否可安装（只检查最顶层，即直接依赖）
    std::vector<std::string> installable;
    for (auto& name : missing_hard_deps) {
        // 尝试在所有已注册仓库中搜索
        if (can_find_in_repos(name)) {
            installable.push_back(name);
        }
    }

    std::string msg = "missing hard dependencies: ";
    for (size_t i = 0; i < missing_hard_deps.size(); ++i) {
        if (i > 0) msg += ", ";
        msg += "'" + missing_hard_deps[i] + "'";
    }
    msg += ". ";

    if (!installable.empty()) {
        msg += "Install them with: ezmk pkg install ";
        for (size_t i = 0; i < installable.size(); ++i) {
            if (i > 0) msg += " ";
            msg += installable[i];
        }
    } else {
        msg += "These packages are not available in registered repos. "
               "Add a repo that provides them, or install them manually.";
    }

    util::fatal(msg); // 或 i18n 化为 missing_dep_at_build
}
```

#### 3.1.3 实现细节

- **检查位置**：`src/build.cpp` 的 `prepare_build_state()` 函数末尾
- **仓库搜索**：复用 `pkg::search_in_repos()` 或新增 `pkg::package_available()` 接口
- **仅提示直接依赖**：不递归检查传递依赖（传递依赖由 `pkg install` 自身处理）
- **新 i18n key**：`missing_dep_at_build`（替代硬编码字符串）

### 3.2 从仓库安装时自动安装缺失库

> 本节仅适用于 `ezmk pkg install <name>` 从仓库安装（不适用 `.zip`/`.tar.gz` 文件和 URL）。

#### 3.2.1 `depends.lib` 自动安装

当前行为：仓库安装时，若 `depends.lib` 中的依赖未安装且不在当前安装批次 → `missing_dep` fatal。

**改进**：自动递归安装硬依赖，无需用户手动干预。

```cpp
// 伪代码 — 在 src/pkg.cpp install_from_repo() 中
// 替换当前的 throw missing_dep 逻辑

for (auto& dep : cur_cfg.depends.libs) {
    if (seen.insert(dep.name).second) {
        fs::path dep_path = dest_dir / dep.name;
        if (util::file_exists(dep_path)) {
            // 已安装 → 验证版本约束（保持现有逻辑）
        } else {
            // 自动安装 → 递归调用 install_from_repo(dep.name)
            ezmk::util::info("auto-installing dependency: " + dep.name);
            install_from_repo(dep.name, dest_dir, scope, opts);
        }
    }
}
```

**行为变化**：
| | 之前 | 之后 |
|------|------|------|
| 硬依赖未安装 | `fatal: missing dependency: 'xxx'` | 自动安装 `xxx`（含其传递依赖） |
| 自动安装失败 | 不适用 | `fatal: failed to install dependency 'xxx': <reason>` |

#### 3.2.2 `depends.want` 交互式安装

当前行为：`depends.want` 中的可选依赖缺失 → 静默跳过。

**改进**：询问用户是否安装（支持一次性决策，避免逐包询问）。

```
假设有 A 库依赖 B 库
用户安装 A 时

[ezmk] 可选依赖:
  A 推荐安装: hiredis (Redis client)
  是否安装? [Y]es/[N]o/[A]ll/[D]eny-all:
```

**四个选项**：

| 选项 | 全称 | 行为 |
|------|------|------|
| `Y` / `y` | Yes | 安装当前可选依赖（不递归其子依赖中的 want） |
| `N` / `n` | No | 跳过当前可选依赖 |
| `A` / `a` | Allow / All | 安装当前及之后所有可选依赖（递归 apply） |
| `D` / `d` | Deny / Deny-all | 跳过当前及之后所有可选依赖 |

**递归语义**：
- `Y` / `N`：仅影响当前这一个 want 包，后续 want 包继续询问
- `A`：同意当前包 + 后续所有 want 包，且对 want 包的子 want 也自动同意（递归 All）
- `D`：拒绝当前包 + 后续所有 want 包，且对 want 包的子 want 也自动拒绝（递归 Deny）

**非交互模式（`-y`）**：
- `ezmk pkg install -y` → 跳过所有 want 依赖（等效 `D`），保持 CI 兼容

**实现位置**：`src/pkg.cpp` 的依赖解析循环（`install_from_repo()` 或 `resolve_dependencies()`）。

## 6 风险与注意事项

- **`gRPC` 编译复杂度高**：依赖 protobuf + openssl + abseil-cpp（可选），CMake 构建耗时长。建议先发布不依赖 abseil 的最小构建模式，后续迭代增强。
- **`libpqxx` 的 Windows 依赖**：Windows 上 PostgreSQL 客户端库 `libpq` 需随 MSYS2 安装，或作为独立预编译包提供。建议首版仅支持 Linux/macOS，Windows 后续补充。
- **交互式 prompt 测试**：`std::cin` 交互难以在单元测试中模拟。建议将 prompt 逻辑抽取为可注入的函数对象（或使用 `std::istream&` 参数），便于测试时用 `std::istringstream` 替代。
- **自动安装的递归深度**：需防止循环依赖导致无限递归（复用现有 seen set 机制）。
