## 1 背景

### 1.1 现状：内部生成物格式是「TOML 与 JSON 混杂」

| 文件 | 归属 | 现状格式 | 写入方式 |
|------|------|----------|----------|
| `ezmk.toml` | 用户手写 | TOML | — |
| `ezmk-workspace.toml` | 用户手写 | TOML | 文本级拼接（保留注释） |
| `index.toml` | 仓库作者手写 | TOML | — |
| **`ezmk.lock`** | **ezmk 全权生成** | **TOML** | **手写字符串拼接**（`src/lockfile.cpp:105-165`） |
| **`list.toml`** | **ezmk 全权生成** | **TOML** | **手写字符串拼接**（`src/repo.cpp:126-139`） |
| `.ezmk/cache/record.json` | ezmk 全权生成 | JSON | `nlohmann` + 原子写 |
| `.ezmk/links.json` | 用户/工具写 | JSON | `nlohmann` |
| `compile_commands.json` | ezmk 生成 | JSON | `nlohmann` + 原子写 |
| `.vscode/{launch,tasks,settings}.json` | ezmk 生成 | JSON | `nlohmann` + 原子写 |

即：**机器读写的文件里只有这两个还是 TOML**，其余早已是 JSON。TOML 目前真正的职责是"人写配置"（`ezmk.toml` / `ezmk-workspace.toml` / `index.toml`），而 `ezmk.lock` 与 `list.toml` 是"ezmk 自己写、自己也读、且文档明确'请勿手改'"的文件——用 TOML 只是 1.1.0 与 0.2.x 时期的惯性。

### 1.2 为什么值得改（三条具体理由 + 一条顺带收益）

1. **手写 TOML 写入器是正确性负担**。两个文件的写出全靠字符串拼接，安全依赖"每个插值都记得过一遍 `util::toml_quote`"这条**人为纪律**——1.1.2 C5（`toml_quote` 单点转义）与 1.4.2 F-04（`sha256` 别名与两个哈希字段的分离）都是为修补这类写入器而生的历史。改为 `nlohmann::json` 后，转义、嵌套、数组与空值语义交给库，只有"字段是否写出"由我们决定。
2. **`list.toml` 名实不符**。既然内容是"ezmk 生成的结构化数据"，扩展名应当如实；`ezmk.lock` 恰好没有扩展名，可以直接变成 `ezmk.lock.json` 而不强迫任何"名字里带 .toml"的别扭折中。
3. **心智负担单一化**。用户面对的文件类型收敛为两类：**人写的 = TOML**，**ezmk 生成的 = JSON**。文档、skill、排障话术都不再需要"这个 .toml 其实你不用看"这类解释。
4. **顺带收益（本版一并做）**：两个文件现在是**非原子写**（`util::file_write` 直写），而 `record.json` / `.o` / `.vscode` 三件套都是 tmp → rename。借写入器重写之机升级为原子写，对齐 `docs/{en,zh}/safety.md` 已对外承诺的"原子写"口径（半截 lockfile 在 `deterministic = true` 下是致命错误，值得防）。

### 1.3 为什么放在 1.4.5 而不是 2.0.0

- **它不是破坏性变更**：旧文件照读、只在新文件写入时才迁移；不删任何公共 API、不放宽也不移除任何弃用面（`plans/2.0.x/REMOVALS.md` §7 的硬约束是"不放宽不移除"，本版**新增**兼容回退，方向相反）。
- **唯一真实破坏面是"降级"**：1.4.5 写的 `ezmk.lock.json` 对 1.4.4 不可见（老版本只找 `ezmk.lock`）——`deterministic = true` 时报"缺少 lockfile"并致命。这条必须在 CHANGES 与 `config_file.md` 的迁移指南里写明（§5）。
- **迁移越晚，存量越大**：lockfile 是进版本库的长期文件，早一轮迁移比晚一轮便宜。

## 3 详细设计

### 3.1 目标格式（`ezmk.lock.json`）

**形状与旧 TOML 一一对应**（`metadata` 对象 + `packages` 数组），只换容器不换结构——迁移可逐字段对拍（§3.9），调用方代码零改动。

```json
{
  "metadata": {
    "version": 1,
    "generated_by": "ezmk 1.4.5",
    "generated_at": "2026-09-27T10:00:00Z",
    "toolchain": "gcc",
    "toolchain_version": "g++ (GCC) 14.2.0",
    "direct_deps": ["fmt", "spdlog@^1.14.0"]
  },
  "packages": [
    {
      "name": "fmt",
      "version": "10.2.1",
      "source": "repo",
      "source_url": "ezmk-official",
      "sha256": "…",
      "lib_sha256": "…",
      "archive_sha256": "…",
      "type": "static",
      "scope": "project",
      "platform": "windows_x86_64_gcc",
      "dependencies": ["zlib"]
    }
  ]
}
```

**字段与 `config::Lockfile` / `config::LockedPackage` 的映射（必须逐字段对拍）**

| JSON 路径 | 结构体字段 | 备注 |
|-----------|------------|------|
| `metadata.version` | `Lockfile::version` | **仍为 1**：字段结构未变；容器差异由文件名承担（D-01「不因非字段变动而 bump」的口径） |
| `metadata.generated_by` / `generated_at` / `toolchain` / `toolchain_version` | 同名 | 旧 TOML 头部的两行 `#` 注释信息由 `generated_by` 承担（JSON 无注释） |
| `metadata.direct_deps` | `Lockfile::direct_deps` | 空时写 `[]` |
| `packages[].name` … `packages[].platform` | `LockedPackage::*` | 键名与旧 TOML **完全一致**（含 `sha256` 别名）；`source` 是**来源类型**（`repo` / `url` / `local` / `archive` / `git`），具体来源（仓库名或 URL）在 `source_url`——示例与实现一致（`src/pkg.cpp:1601`/`:2012`） |
| `packages[].dependencies` | `LockedPackage::dependencies` | 空时写 `[]` |

**空字段策略（沿用旧写入器语义，不得放宽）**：`lib_sha256` / `archive_sha256` / `commit` 为空时**不写出**（读取侧 `value_or("")` 默认空串，`lockfile::artifact_hash()` / `archive_hash()` 的"空 = 未知"语义因此不变）。理由：与旧写入器"新字段为空不写、旧输出字节稳定"的既有约定一致，也不把 D-01（`sha256` 别名）提前消费——**新写入器继续双写 `sha256`**，使 1.4.5 产物的字段集合与 1.4.4 完全等价，便于对拍验证。

### 3.2 路径与命名

| 逻辑 | 新路径 | 旧路径（只读） |
|------|--------|----------------|
| 项目 lockfile | `<proj_root>/ezmk.lock.json` | `<proj_root>/ezmk.lock` |
| 项目注册表 | `<proj_root>/.ezmk/repo/list.json` | `<proj_root>/.ezmk/repo/list.toml` |
| 用户注册表 | `~/.local/ezmk/repo/list.json` · `%LOCALAPPDATA%\ezmk\repo\list.json` | 同名目录下的 `list.toml` |
| 全局注册表 | `<ezmk_install_dir>/repo/list.json` | 同名目录下的 `list.toml` |

### 3.3 读取（双格式 + 优先级）

- `lockfile::load(proj_root)`：`ezmk.lock.json` 存在 → 走 JSON 解析；否则 `ezmk.lock` 存在 → 走 **TOML 回退**（`toml++` 解析路径保留，字段读取代码不动）并打印 `lock_legacy_detected`；两者都不存在 → `nullopt`（行为不变）。
- 两者**同时存在** → JSON 生效 + `lock_legacy_stale` 警告（旧文件被视为陈旧，将在下次写入时清理），**不得**静默合并或二选一。
- `repo::load_repo_list(scope)`：同规则（`list.json` 优先 → `list.toml` 回退），并**保留 1.4.2 F-24 的名字安全校验**（手改的旧文件同样能塞 `../evil`，回退路径不得绕过）。
- 旧的解析失败处理不变：警告 + 当作"无此文件"（`lockfile.cpp:96-99` / `repo.cpp:115-117` 的 catch 语义保留；i18n 化见 §3.8 可选项）。

### 3.4 写入与迁移

```
save(path_new, data):
    text = json.dump(2)
    util::atomic_write_text(path_new, text)     # tmp → rename；失败 → 抛错/返回，旧文件保留
    若存在 path_legacy: fs::remove(path_legacy) # best-effort；失败仅警告，不 fatal
    若本次确实删除了旧文件: info(lock_migrated / repo_list_migrated)
```

- **只在"新文件写入成功之后"才删旧文件**——失败时宁可留下双文件（下一次读取会走 JSON + `*_legacy_stale` 警告），也不冒险丢 lockfile。
- 删除旧文件是**一次性、可预期**的动作（用户会在 `git status` 里看到 `ezmk.lock` 删除 + `ezmk.lock.json` 新增，一次 commit 完成重命名）。
- **迁移只由写入触发**：`ezmk build`（只读校验）不会改盘上文件；`pkg install`（写 lockfile）与 `repo add/remove/update`（写注册表）触发。
- `pkg remove` 现状**不重写** lockfile（`src/pkg.cpp:2185` 只删目录）→ 本版不改变该行为（属既有语义，避免顺手扩大范围）。

### 3.5 API 面（纯增量）

| 位置 | 变更 |
|------|------|
| `include/ezmk/lockfile.hpp` | 新增 `fs::path lockfile_path(const fs::path& proj_root)`（新文件名）、`fs::path legacy_lockfile_path(...)`、`fs::path active_path(...)`（JSON 优先 → 旧文件 → 默认新名）；`load` / `save` / `verify` / `depends_changed` / `direct_dep_specs` **签名不变** |

| `include/ezmk/util.hpp` | 新增 `bool atomic_write_text(const fs::path&, std::string_view)`（上提 `workspace.cpp:521` 的实现；`workspace.cpp` 改为调用公共版本） |

### 3.6 缓存签名的正确性细节（M-04，**本版最容易踩的坑**）

`deterministic = true` 时，lockfile 的内容哈希被并入编译签名，共**三处**：

- `src/build.cpp:1035`（保存侧：`st.proj_root / "ezmk.lock"`）
- `src/cache.cpp:317`（校验侧：`proj_root / "ezmk.lock"`）
- `src/pkg.cpp:949`（包缓存：定位到的项目根 + `"ezmk.lock"`）

三处**必须同时**改为 `lockfile::active_path(proj_root)`，且保存侧与校验侧算法逐字节一致（1.4.2 修过一次"两侧签名永不等 → 每次全量重编"的同类缺陷，见 `CHANGES.md:430`）。若只改一处、或写成"只哈希新名字"：

- 迁移前（盘上只有旧文件）→ 哈希不到文件 → 该侧签名缺少 lock 段 → 与另一侧永不等 → 每次构建全量重编；
- 迁移后（旧文件已删、只有新文件）→ 硬编码旧名的一侧同样哈希不到文件 → 同一后果。

`active_path()` 让"实际生效的那一份"成为唯一被哈希的对象。注意签名是 lockfile 的**内容**哈希（`crypto::sha256_file`），不是路径：

- **迁移会让内容变化**（TOML 文本 → JSON 文本）→ 哈希变化 → 迁移后**恰有一次**全量重编；此后同一状态下重复构建命中。
- 双文件共存的瞬时状态（写新删旧之间）不是问题：`active_path()` 两条侧都优先取 JSON，仍然一致。
- 同一状态下两侧必须解析到同一个文件——这正是 `active_path()` 的契约。

> 结论写进测试：`test_cache.cpp` 增补"确定性签名跟随**当前生效的 lockfile**"用例——旧 TOML 状态下命中 → 迁移到 JSON 后旧签名**失效**（恰一次重编）→ 按新文件重新签名后再次命中。该用例同时是"硬编码旧名会让两侧永不等"这一缺陷形态的定点探测器。

### 3.7 `list.json` 结构与 zsh 补全

```json
{
  "repos": [
    { "name": "ezmk-official", "url": "https://github.com/…/eazymake-repo.git",
      "type": "git", "branch": "main", "last_update": "2026-09-27T10:00:00Z" },
    { "name": "local-dev", "url": "/path/to/repo", "type": "local",
      "last_update": "2026-09-27T10:00:00Z" }
  ]
}
```

- 键名与旧 `[[repos]]` 一致；`type == "git"` 时才写 `branch`（沿用现状）；顶层加 `"version": 1` 供后续演进（旧文件无此字段 → 读取默认 1）。
- `repo::{add,remove,update}` 三个调用点写 `list.json`（逻辑不变，只有 `save_repo_list` 的序列化与路径改变）。
- `res/ezmk.zsh` 的 `_ezmk_repo_names()`（`:33-41`）现在 `grep -E '^name\s*=\s*"' .ezmk/repo/list.toml`：改为**先试 `list.json`**（`grep -E '"name"\s*:'`），**文件不存在再回退旧名**。静态补全脚本不会随升级自动更新，双分支是必须的（用户可能装着旧脚本、项目可能是旧注册表）。

### 3.8 i18n 新键（三向一致，`zh-TW` 变体继承无需补）
