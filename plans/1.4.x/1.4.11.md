## 1 背景

第四轮审计在 1.4.10 发布态上重新展开，结论与前几轮互补：

- 第一轮（1.4.0-dev.6）修 8 项 P0/P1；第二轮（1.4.2）修接口层与跨平台路径/编码 36 项；第三轮（1.4.6）修错误路径与不可信输入边界 32 项。本轮发现**约 47 项**，分布在八个域，其中多数是前三轮同类形态在**新代码（1.4.5~1.4.10）或未覆盖的调用点**上的复现。

新一轮的主要形态：

- **跨模块契约不一致**：lockfile 写出的依赖约束 `pkg@^1.2` 无法被 config 读回；test 缓存不跟随编译器版本失效，而 build 缓存跟随；`compile_package` 与 `cache.cpp` 各自手写了一份「rename 失败→copy→删临时」的回退，且都没有 `atomic_rename` 修过的错误检查。
- **命令装配的转义遗漏**：Windows 上 `project new` 的 `git init`、`build_editor_command` 仍用 POSIX `escape_shell_arg`；`$CXX` 探测路径未引号化；测试运行器命令用裸双引号拼接。1.4.2 F-15 / 1.4.6 Q-20 已修过同类点，但未穷尽调用点。
- **权限/沙箱边界**：Lua `ezmk.run` 只按**首 token** 做 run 权限判定，却把整条命令交给 `/bin/sh -c` 执行 → `git ; rm -rf ~` 绕过 allow/deny/Ask；权限 glob 允许项用未锚定的 `regex_search` 匹配绝对路径。
- **资源与错误路径**：POSIX `run_command` 在 `fork()` 之后调用会 malloc 的 `setenv()`（多线程 `-jN` 下可死锁）；`ThreadPool` 构造期 `std::thread` 抛异常导致 `terminate`；`json_to_lua` 无深度上限（与 encode 侧不对称）。
- **平台语义**：`project import` 的平台常量硬编码 `WIN32=true`、条件链 `if/elseif/else` 已取分支后仍继续求值；Windows 下载不拆分 `host:port`；`extract_targz` 不校验 gzip CRC。

立项基线实测（`build/test_ezmk.exe --order decl`，与 `build.sh test-all` 同一执行）：**1156 用例 / 1151 passed / 5 skipped；6675 断言全过；失败集合与 1.4.10 发布态一致**。

## 3 详细设计

### 3.1 进程与命令执行安全（Q4-01 ~ Q4-06）

**Q4-01 — POSIX `run_command` 在 fork 后 `setenv`**。`src/util.cpp:1704-1706`：子进程在 `fork()` 与 `exec` 之间遍历 `opts.env` 调 `setenv()`。`setenv` 会 malloc/realloc `environ`，**不是 async-signal-safe**；多线程 `-jN` 构建中若 `fork` 时恰好有兄弟线程持有 malloc arena 锁，子进程会永久阻塞于 `exec` 之前。可达路径：`cache.cpp:832-836`（确定性构建注入 `SOURCE_DATE_EPOCH`）。
方案：在 `fork()` **之前**把 `opts.env` 合并进一份 `std::vector<char*>`（或 `std::vector<std::string>` 持有），子进程用 `execve` / `execle` 传递；更彻底可改 `posix_spawn`（配上 `posix_spawnattr` + file actions）。Windows 分支不受影响。
测试：多线程并发触发带 env 的 `run_command`（如 `-jN` 确定性构建）连续多次不 hang；单测断言子进程看到的环境值正确、父进程环境未被污染。

**Q4-02 — Lua run 权限首 token 绕过**。`src/lua_api.cpp:736-738`（`ezmk_run`）与 `:774-776`（`ezmk_run_capture`）用 `first_token(cmd)`（`:220-232`，遇空白截止）做 `[utils.permissions].run` 判定，随后把**整条命令**交给 `util::run_command`，POSIX 下即 `/bin/sh -c`（`util.cpp:1712`）。若 allow 含 `git`，`ezmk.run("git ; rm -rf ~")` 首 token 为 `git` → Allow，分号后的命令照常执行；`run_deny` 与交互式 Ask 同样被绕过，且已缓存的 `RUN:git` always-allow 会零提示放行。
方案（按保守度择一，推荐 a）：
(a) 权限激活（`g_current_perms` 非空）时不经 shell：复用与 `first_token` 一致的规则把命令切分为 argv，`execvp` 执行（新增 `run_command_no_shell` / `RunOptions.no_shell`）；
(b) 若保留 shell，则拒绝含未转义 `; | & $ 反引号 > <` 与换行的命令，并把控制符之前的完整命令串纳入 deny/allow/Ask 匹配。
两条路径都需保留 `run_allow`/`run_deny`/Ask 语义。
测试：`run = ["git"]` 下断言 `git ; touch marker` 被拒；`run_deny = ["rm"]` 下 `git ; rm x` 被拒；合法单命令仍可执行；Windows（无 shell 展开）行为不变。

**Q4-03 — 测试运行器命令裸引号**。`src/build.cpp:2427` 与 `:2630` 用 `"\"" + path + "\""` 拼接 runner / test_exe，而紧邻的 `--filter` / `--report` 参数已转义。POSIX 下 `run_command` 走 `/bin/sh -c`，项目路径含 `"`、`$()`、反引号或换行时会误解析甚至注入。
方案：改用 `util::escape_shell_arg`（POSIX）/ `util::quote_cli_arg`（Windows）或统一的平台适配。
测试：含空格/引号/`$` 的临时项目路径下 `ezmk test` 能运行；恶意目录名不产生副作用。

**Q4-04 / Q4-05 — Windows 分支仍用 POSIX 转义（1.4.2 F-15 遗漏）**。`src/project.cpp:126-128`（`git init`）与 `src/util.cpp:1910`（`build_editor_command`）在 `#ifdef EZMK_WIN` 分支仍调用 `escape_shell_arg`，而 Windows 的 `run_command` 直达 `CreateProcessW`（无 shell）。`escape_shell_arg` 会翻倍反斜杠并对 `$`/反引号插反斜杠，破坏 UNC / 扩展长度路径与含 `$` 的路径。
方案：Windows 分支改用 `util::quote_cli_arg`（MSVCRT 规则）；POSIX 分支保持 `escape_shell_arg`。
测试：Windows 上从 UNC / 含 `$` 的路径执行 `project new` 与 `open_in_editor` 成功（无 Windows 环境时以 `quote_cli_arg` 单测覆盖参数串）。

**Q4-06 — `$CXX` / `$CC` 探测路径未引号化**。`src/toolchain.cpp:456`（另见 `:754` / `:788`）把 `cxx + " --version 2>&1"` 交给 `run_command`。`CXX="C:/Program Files/LLVM/bin/clang++.exe"` 会在首个空格处被拆分 → 探测失败 → 误报「no compiler found」或回退。
方案：先 `quote_cli_arg` / `escape_shell_arg`（按平台）再拼参数；或改用 argv 形式执行。
测试：`CXX` 指向含空格路径的编译器（可复制 `g++` 到含空格目录）时能识别版本。

### 3.2 数据完整性与错误路径（Q4-07 ~ Q4-10）

**Q4-07 — 回退 copy 失败仍删临时文件（prior-fix-incomplete）**。`src/cache.cpp:861-867` 与 `src/pkg.cpp:1041-1048` 是同一手写形态：

    fs::rename(tmp, final, ec);
    if (ec) { fs::copy_file(tmp, final, overwrite, ec); fs::remove(tmp, ec); }   // ec 被覆盖、从未检查

`rename` 失败（Windows 目标被占用 / 已存在）且 `copy_file` 也失败（空间/权限）时，唯一可用的临时成品被删；`cache.cpp` 仍 `result.success = true` 且 `result.object = obj`（可能缺失/陈旧），`pkg.cpp` 仍返回 `lib` 并把陈旧/缺失归档写入 lockfile、报告安装成功。`util::atomic_rename`（`util.cpp:291-307`，Q-04 已修）正是为此，但这两处未复用。
方案：两处都改用 `util::atomic_rename(tmp, final)`（失败时保留源并抛/返回错误），或至少在 `copy_file` 失败时保留 `tmp` 并置 `success=false` / 抛异常。
测试：注入「rename 失败 + copy 失败」场景（目标为只读目录/占用文件），断言临时对象/归档仍在、命令非零退出、lockfile 未被写入。

**Q4-08 — 回退 rename 泄漏 `.tmp`**。`src/cache.cpp:395-402`（`record.json`）与 `src/compile_db.cpp:127-135`（`compile_commands.json`）在 `fs::rename(tmp, final, ec)` 失败后 `file_write(final, ...)` 兜底，但从不删除 `tmp`。Windows 上目标已存在时该分支预期会触发，于是 `*.tmp` 在项目里不断累积。`util::atomic_write_text`（`util.cpp:312-326`）已正确清理。
方案：改用 `util::atomic_write_text()`，或在兜底后 `fs::remove(tmp, ec)`。
测试：预置只读/占用目标使 rename 失败，断言兜底成功且无 `*.tmp` 残留。

**Q4-09 — ThreadPool 构造期线程创建失败 → terminate**。`include/ezmk/thread_pool.hpp:25-41` 的 `workers_.emplace_back(...)` 若在第 i>0 个线程抛 `std::system_error`，异常离开构造函数；析构时 `workers_` 中已创建的可 join 线程触发 `std::terminate()`，而非可捕获异常。
方案：`try/catch` 包裹 spawn 循环；失败时 `stop_=true`、`notify_all()`、join 已创建线程后重抛。
测试：以「受限线程数」或注入桩覆盖（无桩时以代码审查 + 注释记录）。

**Q4-10 — `repo remove` 先删 cache 后写注册表**。`src/repo.cpp:565-576`：先 `fs::remove_all(cache)`，再 `save_repo_list(scope, entries)`（后者失败会 `util::fatal`）。若持久化失败，注册表仍列出该 repo 但 cache 已删。
方案：先成功 `save_repo_list`，再删 cache；或删除失败可回滚。
测试：写入只读注册表使保存失败，断言 cache 仍在、注册表未变。

### 3.3 增量缓存与构建正确性（Q4-11 ~ Q4-14）

**Q4-11 — test 缓存不随编译器版本失效**。`src/build.cpp:33-42` 的 `validate_test_cache_signature()` 只比较 `compile_options_signature` 并据此 `record.files.clear()`，从不读写 `record.compiler_version`；而 build 路径 `compile_phase`（`build.cpp:1077-1082`）会「编译器版本变化 → 清空缓存」。两种 runner（Catch2 `:2359`、EZMK `:2586`）共用同一 `.test_cache.json`。
触发：升级/切换编译器（`$CXX`、PATH）而 flags 不变，再 `ezmk test`。
后果：旧编译器产出的测试对象被复用并与新编译的项目对象链接 → 链接/ABI 失败或测试结果不可信。
方案：在 `validate_test_cache_signature` 中镜像 `compile_phase` 的 `compiler_version` 比较与清空，并一并折入 deterministic / lock / SDE（与 build 侧同源）。
测试：篡改 `.test_cache.json` 的 `compiler_version`，断言 `ezmk test` 触发重编。

**Q4-12 — executable 入口检测忽略 `main.cc` / `main.cxx`**。`src/build.cpp:206-210` 只认 `main.cpp` / `main.c`，而 `collect_sources` 的扩展集（`:149`）含 `.cc` / `.cxx`。以 `main.cc` 为入口的 executable 会 `fatal(main_missing)`。
方案：按 `f.stem() == "main"` 判定（扩展名已在收集阶段过滤），或显式补全四扩展。
测试：`src/main.cc` 的 executable 项目可构建；`main.txt` 不误判。

**Q4-13 — 单源失败丢弃全部缓存更新**。`src/build.cpp:1229-1246`：并行路径 `if (has_failure) util::fatal(build_failed)` 在 `cache::save_record(record)` 之前；串行路径在 `cache.cpp:932` 直接抛。其余 N-1 个成功源的对象不落盘，修好一个文件后下次仍全量重编。
方案：在 fatal 之前保存已合并的成功条目（或捕获、保存、重抛）。
测试：两文件项目，其一语法错误 → 修复后重建只重编该文件。

**Q4-14 — `collect_test_sources` 未按路径去重**。`src/build.cpp:2157-2164` 仅在 `rec`（递归）分支用 `seen_paths` 去重；flat 分支无条件 `push_back`。`[test].dirs` 含重复项（如 `["tests","tests"]` 或 `["tests","./tests"]`）会把同一测试源加入两次 → 重复 `.o`/符号、测试重复执行。对照 `collect_sources` 的 flat 文件名去重。

### 3.5 Lua 与 i18n（Q4-21 ~ Q4-26）

**Q4-21 — `lua_pushstring` 截断内嵌 NUL**。`src/lua_api.cpp:664-665`（`file_read`）、`:758-760`、`:787`（run 输出）、`:866`（`json_to_lua` 字符串）均用 `lua_pushstring`，以 `strlen` 计长；`util::file_read` 以 binary 打开返回完整字节，子进程输出也可能含 NUL。

**Q4-22 — `json_to_lua` 无深度上限**。`src/lua_api.cpp:850-890` 递归无 depth 参数，而 encode 侧 `lua_to_json`（`:916-919`）有 `kJsonMaxDepth` 检查；`init()`（`:345-354`）的注释声称两侧都受限，与实现不符。nlohmann 解析为迭代式，深层 JSON（如 10 万个 `[`）会一路进入 C++ 递归 → 栈溢出崩溃，沙箱内脚本可 DoS。
方案：给 `json_to_lua` 增加 depth 参数，超过 `kJsonMaxDepth` 时抛与 encode 一致的 Lua 错误（或 decode 入口先做深度预检）。

**Q4-24 — `lua_setupvalue` 返回值未检查**。`src/lua_api.cpp:1431-1432` 忽略返回值也未弹栈（失败时 `lua_setupvalue` 不弹出压入值）；对照 `run_script`（`:1241-1246`）有 `nullptr` 检查。当前 Lua 5.4 下不可达，属潜在栈失衡。

**Q4-25 — `ezmk_lua_main` 无异常处理**。`src/ezmk_lua_main.cpp:82-88`：`lua::init()` 失败会 `util::fatal` → `throw ezmk::fatal_error`，main 未捕获 → `std::terminate`/abort（退出码非 1）。与 `src/main.cpp:644-659` 不一致。

**Q4-26 — i18n 变体独立数据 / overlay 半写**。`src/i18n.cpp:282-303` 的 `init` 仅在 `base_loaded` 时应用变体，而 `detect_language`（`:384-398`）允许仅变体有数据 → `fr-CA` 有文件但无 `fr` 基础时回退英文（I18N-1）。`parse_locale_json`（`:155-171`）overlay 分支边遍历边写 `g_strings`，某值类型错误在 `get<std::string>()` 抛异常时已写入的键保留，且 `init` 不检查返回值 → 中英混杂（I18N-2）。

**Q4-43 — `project export --glob` 未生效**。`src/cli.cpp:528-529` 只处理 `--no-glob`，无 `--glob`；`--glob` 仅靠结构体默认值（`cli.hpp:89`）。`--no-glob --glob` 时后者不生效。
方案：显式处理 `--glob`（末次优先）或拒绝冲突组合。
测试：仅 `--glob`、`--no-glob --glob`、`--glob --no-glob` 的最终值符合「末次优先」。

### 3.8 归档 / 下载 / 工具函数（Q4-44 ~ Q4-47）

**Q4-44 — `resolve_relative_path_flags` 前缀过度匹配**。`src/util.cpp:474-482` 的 `joined_prefix` 用 `f.compare(0,n,p)==0` 判断，`/I` 会命中 `/INCREMENTAL:NO`、`/IMPLIB:`、`/IGNORE:`、`/INCLUDE:`；`-include` 会命中 `-include-pch`；`-isystem` 命中 `-isystem-after`。随后 `resolve()` 把余下字符串当项目根相对路径拼接（`:493-496`），产生错误 include 目录或非法 flag。仅在从子目录构建（`resolve_flags` 开启）时触发。
方案：仅在余下部分确为路径操作数时才视为合并形式（`/I` 后需为 `X:`、`/`、`\`、`.`；`-include`/`-isystem` 仅在存在分隔/驱动器时），或对已知非路径前缀（`/INCREMENTAL`、`/IMPLIB`、`/IGNORE`…）加白名单豁免。
测试：`/INCREMENTAL:NO`、`-include-pch`、`-isystem-after` 原样保留；`-Iinc`、`/Iinc`、`/LIBPATH:lib` 仍正确解析。

**Q4-45 — Windows 下载不拆分 `host:port`**。`src/util.cpp:1344-1350` 取 `host = url.substr(0, slash)`，`:1362-1363` 直接传给 `WinHttpConnect`。`http://host:8080/...` 会以 `host:8080` 作主机名导致连接失败（POSIX curl 正常）。
方案：从 authority 解析出端口（与 userinfo），以数字端口传给 `WinHttpConnect`。
测试：含端口的 URL 在 Windows 分支解析出正确 host/port（以解析函数单测覆盖）。

**Q4-46 — `safe_extract_path` 误拒 `.` / 尾分隔符目标**。`src/util.cpp:1009-1016`：`dest="."` 时 `("." / "file").lexically_normal()=="file"`，前缀比较失败而抛「unsafe path」；`dest="out/"` 保留尾斜杠同样失败。当前仓库内调用方都传绝对临时目录，属潜在缺陷，但函数已导出。
方案：比较前 strip 尾分隔符并归一化 `.` / 空目标。
测试：`extract_archive(..., ".")` 与 `"out/"` 正常解压；真正的逃逸路径仍被拒。

**Q4-47 — `extract_targz` 不校验 gzip CRC32/ISIZE**。`src/util.cpp:1142-1200` 解压到 `TINFL_STATUS_DONE` 后直接解析 tar，忽略末尾 8 字节（CRC32 LE + ISIZE mod 2^32）。raw deflate 无内部校验，位翻转的 `.tar.gz` 在无外部 sha256 时可静默解出损坏内容。
方案：解压后读取 footer，比对 `mz_crc32(MZ_CRC32_INIT, out.data(), out.size())` 与 `(uint32_t)out.size()`，不匹配即抛。
测试：篡改一字节的 `.tar.gz` 报错；正常归档行为不变。

### 3.13 根因分类与复盘

| 类别 | 典型条目 | 共性 |
|------|----------|------|
| 错误 / 清理路径 | Q4-07、Q4-08、Q4-09、Q4-10、Q4-13 | 正常路径正确，失败分支漏判返回值 / 漏删临时 / 丢缓存 |

**四个盲区**：① 负路径测试不足（失败分支、类型错误、超深/超大输入）；② Windows / macOS 分支缺 CI 真机；③ 返回值忽略是「静默」的；④ 同类缺陷跨模块重复，缺统一契约。

**可复用教训**：修错误路径要收敛到**结构性单点**（`atomic_rename` / 统一签名函数）；权限判定要**与实际执行对象一致**；新平台分支要么进 CI，要么留「仅 X 平台可测」注释 + 单测。
