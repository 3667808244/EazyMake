## 1 背景

### 1.1 三个构建钩子拿不到“当前生效 profile”（缺陷）

三个构建钩子 `pre_build` / `post_build` / `on_failure` 共用 `run_hook()`（`src/build.cpp:498`），三处调用分别位于：

- `pre_build` → `src/build.cpp:996-997`
- `on_failure` → `src/build.cpp:1339-1340`
- `post_build` → `src/build.cpp:1533-1534`

三处传的都是 `opts.profile`；Lua 侧把它注入 `ctx.profile`（`src/lua_api.cpp:1487-1488`），机制本身存在。

问题在值：profile 的“当前生效值”由 `apply_profile()`（`src/build.cpp:529`）在内部解析——`CLI --profile` 优先，否则回退 `[compile].default_profile`（`src/build.cpp:535-537`）——但 `opts.profile` 只由 CLI 填充（`src/cli.cpp:82`），main 不会把 `default_profile` 回填给 `build_opts`（对比 `project cc` 在 `src/main.cpp:113` 回填、`project export` 在 `src/export.cpp:117-118` 回填）。实测语义：

| 场景 | 实际编译 | 钩子 `ctx.profile` |
|---|---|---|
| `ezmk build -p release` | release | `"release"` ✅ |
| 无 `-p` + `default_profile = "debug"` | debug | `""` ❌ |
| 无 `-p` 且无 `default_profile` | 基础配置 | `""` ✅（确实无 profile） |

附带不一致：`project export cmake` 已把解析后的 profile 传给 `ezmk-lua --profile`（`src/export.cpp:117-118`、`src/export.cpp:452`），所以同一份 `[hooks]` 脚本在原生 `ezmk build` 与导出的 CMake 构建下会看到不同的 `ctx.profile`。

### 1.2 按 profile 导出对象归档（新功能）

部分场景需要的是**单个源文件的目标文件**，而不是最终可执行文件 / 静态库：交给外部链接器、做增量链接、静态分析、归档留存、或把某 profile 优化过的对象交付下游。现状目标文件只落在内部目录——`.ezmk/temp`（`src/build.cpp:648`，`make_compile_input` 的 `obj_dir`）与持久缓存 `.ezmk/cache/obj`（`src/build.cpp:650`），用户没有受支持的取用方式。

用户裁定：该能力作为 **`[compile.profile.<name>]` 的配置选项**，随该 profile 生效；导出形态为**单个归档**——`build/obj_files.zip` 或 `build/obj_files.tar.gz`。归档内条目镜像源码目录结构（如 `src/main.o`）。

另外，用户要求**默认模板的 release profile 默认启用该选项**（`export_objs = true`），使 `ezmk project new` 出来的项目执行 `ezmk build --profile release` 即产出 `build/obj_files.zip`；`[compile].default_profile = "debug"` 保持不变，因此裸 `ezmk build` 不触发导出。

## 3 详细设计

### 3.1 钩子 profile 解析修复（H-01 / H-02）

- `AppliedProfile`（`src/build.cpp:524`）追加 `std::string active_profile;`（空 = 无生效 profile）。
- `apply_profile()`（`src/build.cpp:529`）把解析出的 `active_profile` 写入返回值；注意 `active_profile.empty()` 提前返回（`src/build.cpp:537`）与 link-only（`src/build.cpp:542`）两条路径都要带上。
- `BuildState`（`src/build.cpp:478`）追加 `std::string active_profile;`；`prepare_build_state()` 在 `apply_profile` 调用点（`src/build.cpp:727`）赋值。
- 三处 `run_hook(...)` 的第 4 个实参由 `opts.profile` 改为 `st.active_profile`。
- **H-02（去重）**：把“CLI > `[compile].default_profile`”的取名逻辑抽成单一 helper（`build` 或 `config` 命名空间），供 `apply_profile` / `export.cpp`（`:117-118`、`:546-547`）/ `run_tests` 共用，保证三处永远同值。
- 边界与不变量：
  - link-only profile 也返回其名字（compile 配置不变）——钩子仍应看到它。
  - 未知 profile 仍 fatal（`src/build.cpp:572`），不因本改动变化。
  - 无 profile（CLI 与 default 均空）→ `active_profile == ""`，`ctx.profile` 仍为 `""`（语义不变）。
  - 不改 `lua_api.cpp` 的 ctx 注入；`ezmk test` 不跑构建钩子，不在范围。

### 3.2 配置选项语法（O-01）

    [compile.profile.release]
    flags = ["-O2", "-DNDEBUG"]
    export_objs = true                      # 默认归档 build/obj_files.zip
    export_objs = "build/obj_files.zip"     # 显式 zip
    export_objs = "build/obj_files.tar.gz"  # tar.gz（.tgz 等价）

- 类型：boolean 或 string。
  - `true` → 启用，默认归档 `<proj_root>/build/obj_files.zip`；
  - `"<path>"` → 启用，归档写到该路径（相对项目根；绝对路径原样）；
  - `false` / 缺省 → 不导出；
  - 空字符串 → 视为不导出（合法，等价关闭）；
  - 其它类型 → 配置期报错（新增键 `config_err_profile_export_objs_type`，携带 profile 名）。
- 归档格式由扩展名决定：`.zip` → `util::create_zip`；`.tar.gz` / `.tgz` → `util::create_targz`；其它扩展名 → 配置期报错（新增键 `config_err_profile_export_objs_ext`，携带 profile 名与值）。
- 结构：`ProfileConfig`（`include/ezmk/config.hpp:84`）追加 `bool export_objs = false;` 与 `std::string export_objs_path;`（空 = 默认归档）。追加在末尾，保持聚合初始化兼容。
- 解析：`parse_profiles()`（`src/config.cpp:707`）读 `prof_table->get("export_objs")`，分 bool / string 两支，并在解析期校验扩展名；与既有 `flags` / `msvc_flags` / `macros` 同级。
- 归属 `[compile.profile.*]` 而非 `[link.profile.*]`：对象文件是编译产物；link profile 不参与 compile 合并。
- **默认模板（O-06）**：`write_default_config()`（`src/config.cpp:993`，`ezmk project new` 使用）的 `[compile.profile.release]` 增加 `export_objs = true`；`project import` 生成的模板（`src/import.cpp:714-716`）同步对齐。`[compile].default_profile = "debug"` 不变，只有 release 构建产出归档。

### 3.3 导出执行（O-02 / O-03）

- **时机**：`build_project()`（`src/build.cpp:1501`）在 `compile_phase` 成功返回之后、`link_phase` 之前导出。理由：导出物是编译产物，链接失败不应丢弃；`on_failure` 钩子触发时归档已在盘上。`pre_build` 仍由 `prepare_build_state` 正常触发（`src/build.cpp:996`），本功能不新增钩子点。
- **目标路径**：`export_objs_path` 为空 → `<proj_root>/build/obj_files.zip`；否则相对 `proj_root` 解析（绝对原样）。父目录不存在则创建。
- **staging + 打包**（复用 1.3.5/1.3.6 归档设施，不新写归档器）：
  1. 建临时 staging 目录 `<temp_dir>/obj_export_stage`；
  2. 对 `compile_phase` 返回的每个对象 `obj`，取 `rel = fs::relative(obj, st.temp_dir)`，复制到 `stage/rel`；rel 逃逸项目根（源文件在项目外，`safe_relative` 回退绝对路径）时 warn 跳过（新增键）；
  3. 按扩展名调 `util::create_zip(stage, out)` 或 `util::create_targz(stage, out)`——两者内部遍历 staging（排序、正斜杠条目名、目录条目），且都是**先写临时文件再原子改名**（`src/util.cpp:688` / `:845`，1.4.6 Q-24）；
  4. 移除 staging（best-effort）。
- **归档内容**：条目名镜像源码目录结构（`src/main.o`、`src/sub/x.obj`），后缀随工具链。因为 staging 只放本次 `objects`，归档**天然不含**已删除源文件的陈旧对象——比“目录镜像”更干净。
- **空对象集**：`compile_phase` 返回空（如无源文件）→ warn 跳过、不产出空归档（新增键）。
- **错误处理**：staging 复制失败或归档创建失败 → fatal（新增键 `obj_export_failed`）；成功 → info 汇总（对象数 + 归档路径，新增键 `obj_export_written`）。归档文件存在时覆盖（原子改名语义）。
- **并发**：`compile_phase` 的线程池已 join，导出在主线程串行，无共享状态问题。
- **作用范围**：仅 `build_project` 路径——`build` / `run` / `install` / `pack`（含 `--precompiled`）/ `watch` 每次重建 / workspace 成员构建。**不**作用于 `ezmk test`，**不**作用于依赖包编译。`-j N` 与 `--disable-cache` 均无影响（导出读 `compile_phase` 返回值）。
- **已知语义**：默认文件名 `build/obj_files.zip` 固定不含 profile 名——若多个 profile 都开 `export_objs`，它们写同一个归档（后构建者覆盖）；需要并存时用字符串给不同路径。归档字节不承诺确定性（tar.gz 含 staging 拷贝的 mtime，与 `pack` 现状一致）。

### 3.4 为什么不做成 CLI（O-01 决策）

用户裁定走 profile 配置。理由：导出与 profile 的构建语义绑定（如 release 导出优化对象），跟随 `default_profile` 自动生效，无需每次传参，也不新增命令面 / man CLI 面 / zsh 补全面。备选（`project export obj` 命令、`build --obj-dir`）见 §3.6。

### 3.5 测试设计（O-04）

- **配置解析**（`test/test_config.cpp` 的 profile 用例组）：`export_objs = true` / `.zip` / `.tar.gz` / `.tgz` / `false` / 非法类型报错 / 非法扩展名报错；字符串值原样进入 `export_objs_path`。
- **profile 解析（H-03）**：
  - 单测 `apply_profile` 返回值：CLI 命中 / default 命中 / 两者皆无 / link-only。
  - 集成：项目设 `default_profile = "debug"` + `post_build` 钩子把 `ctx.profile` 写入文件；无 `--profile` 构建 → 文件 == `debug`；加 `--profile release` → `release`；无 profile 项目 → 空。
- **归档导出（集成）**：
  - `export_objs = "build/obj_files.zip"`：归档存在、用 `util::extract_archive` 解到临时目录，条目数 == 源文件数、条目名镜像 `src/...`、后缀按工具链，且**链接产物仍生成**；
  - `.tar.gz` / `.tgz`：同断言走 tar.gz 分支；
  - 默认值 `true`：落到 `build/obj_files.zip`；
  - 非导出 profile / 无 profile：不产出归档文件；
  - 连续两次构建（第二次全缓存命中）都产出且条目完整；与 `--disable-cache` 组合；
  - 陈旧对象：先构建 2 个源文件、删除 1 个、再构建 → 归档只剩 1 个条目（staging 只含本次对象）。
- **默认模板（O-06）**：`write_default_config` 单测断言 `compile_profiles["release"].export_objs == true`、`["debug"].export_objs == false`；模板原文含 `export_objs = true`；模板集成用例断言 `ezmk build --profile release` 产出 `build/obj_files.zip`、默认（debug）构建不产出。
- **回归**：全量零新增失败（基线 1133/6525）。

### 3.6 明确不做

- 目录镜像导出（用户已裁定改为归档）。
- 归档去确定性 / 固定 mtime（与 `pack` 现状一致，不做）。
- CLI 命令 `project export obj` / `build --obj-file`（若后续需要再评估；届时可复用同一导出 helper）。
- 依赖包对象导出；`ezmk test` 的对象导出。
- 破坏性 API 变更 / 弃用面移除（归 2.0.0）。

## 6 跨版本关注点
