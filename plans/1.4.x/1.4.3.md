## 1 背景

1.4.2 发布后，`ezmk` 的**离线**参考只有两处：`ezmk --help`（必须运行二进制，单页速览，且受 `EZMK_LANG` 影响）与仓库内 `docs/` + `tutorial/`（需克隆或联网访问 GitHub）。Unix 用户的默认预期——`man ezmk`——目前完全落空：仓库里**没有任何 man 基础设施**，`man` 目录不存在，三渠道也都不安装手册页。

而"随包分发静态资源"的链路在本仓**已经成熟**：zsh 补全 `res/ezmk.zsh` 由 `install.sh`（`~/.zsh/completions/_ezmk` + fpath 幂等写入）、`publish/arch/PKGBUILD`（`/usr/share/zsh/site-functions/_ezmk`）与 Homebrew formula（`zsh_completion.install "_ezmk"`）三条路径分发，release.yml 也把它打进每个平台的资产。man 手册可以复用同一条链路，成本低、收益明确。

三条渠道的**构建方式不同**，决定了 man 的打包路径必须分开设计：

- `install.sh`、`publish/arch/PKGBUILD`：**从源码 tag 构建**，可直接从仓库检出里取 `man/`；
- `publish/homebrew/ezmk.rb`：**从 Release 资产安装**（tarball 根目录含 `ezmk` / `ezmk-lua` / `_ezmk`），因此 man **必须进 tar.gz**，且资产变化会让 formula 的 `sha256` 失效——这正是 1.4.2 发布时踩过并已流程化的坑；
- Windows（`install.ps1` 下载 zip）：无 `man` 命令，**明确不做**。

最后一个动机来自 1.4.2 的教训：本仓 CLI 文档历史上多次与 `src/cli.cpp` 漂移（1.4.2 的文档对齐修正即为一例，涉及 `--pug`、`--type`、`--no-data`、`pack --output`、`workspace watch -j` 等）。**再新增一份手写 CLI 文档，如果不带闸门，只会再添一处漂移源**——所以本版把"防漂移校验脚本 + CI 闸门"列为与 man 正文同优先级的 P0 交付物。

## 3 详细设计

### 3.1 交付物与目录布局

新增**顶层 `man/`**（不放 `res/`）：

```
man/
├── ezmk.1                  # man ezmk
├── ezmk.toml.5             # man 5 ezmk.toml
├── ezmk-workspace.toml.5   # 随附（M-11）
└── ezmk-lua.1              # 随附（M-11）
```

- **为什么不放 `res/`**：`res/` 现有内容是运行期/打包资源（`logo.txt`、`ezmk.zsh` 补全），而 man 是**源文档**，独立目录便于 lint/CI 定位、也符合 `man/` 的通行约定；`res/` 的补全改动与 man 改动是两类审阅意图，混放会让 `git log` 与 CI 断言都变糊。
- **文件名的语义**：`ezmk.1` ↔ `man ezmk`；`ezmk.toml.5` ↔ `man 5 ezmk.toml`（第 5 节＝文件格式），与 `ezmk.toml` 这一配置文件名拼写一致，便于 `man 5 ezmk.toml` 直觉命中。
- **安装目标**：Linux/macOS `$PREFIX/share/man/man1|man5`，Arch/MSYS2 `/usr/share/man/man1|man5`。
- **职责边界（写入 CONTRIBUTING）**：`man/` 是**速查**（离线、结构化、字段级），`docs/` 是**完整规范**（长解释、动机、示例）。两者都要改时以 `docs/` 为准再精简进 man；`check_man_sync.py` 负责结构一致性（§3.5），不校验文案。

### 3.2 roff 方言与写作约定

- **传统 man macros**（`.TH .SH .SS .TP .B .BR .IR .PP .nf/.fi`），**不引入 mdoc**：团队无 mdoc 经验、收益仅是形式更规范，而本书面量与结构（字段表为主）用 `.TP` 已足够；同时避免把新工具链带进构建期（无需 `pandoc`/`ronn`/`scdoc`）。
- **文件头**：`.TH EZMK 1 "<YYYY-MM-DD>" "EazyMake 1.4.3" "User Commands"`、`.TH EZMK.TOML 5 ... "File Formats"`；日期在**发布 commit**统一更新（§3.10 坑 1）。
- **转义铁律**：所有选项/参数里的连字符写 `\-`（如 `\-\-profile`、`\-\-jobs`）——不转义会被 groff 渲染成减号 U+2212，用户复制粘贴即失败；`man/*.1|5` 中出现未转义的企业连字符由 lint 步骤直接失败（§3.6）。
- **纯 ASCII 正文**：英文-only 且不使用 UTF-8 特殊字符，规避 `groff` 在 C locale 下的编码差异。
- **引用约定**：命令与选项用 `\fB...\fR`，占位符用 `\fI...\fR`；跨手册引用写 `\fBezmk.toml\fR(5)`、`\fBezmk\fR(1)`。
- **SEE ALSO**：`ezmk.toml(5)`、`ezmk-lua(1)`（若随附）、在线文档（`https://github.com/3667808244/EazyMake/blob/main/docs/en/cli.md` 与 `docs/en/config_file.md`、教程入口），保持"离线可读、细节在线"。

### 3.3 `ezmk(1)` 内容结构

| 节 | 内容要点（来源：`docs/en/cli.md` + `src/cli.cpp` 的 spec/`kAliases`） |
|---|---|
| NAME | `ezmk` — simple C/C++ build tool |
| SYNOPSIS | `ezmk <command> [subcommand] [options] [arguments]`、`ezmk <shorthand> …`、`ezmk <action> …`（顶层别名） |
| DESCRIPTION | 定位（易用优先、单产物、声明式）；项目根定位＝从当前目录**向上最多 5 级**查找 `ezmk.toml`（`util.hpp` 的 `kProjectRootMaxUp`） |
| COMMANDS | 日常 7 条（build/run/clean/watch/install/test/pack，含完整形式 `project <x>`）；`project new/cc/export/import`；`pkg install/remove/search/info/list/update`；`repo add/remove/update/list/info`；`workspace list/build/test/watch/clean/scan`；`utils`、`example`、`help`、`version` |
| OPTIONS | 按组：通用 build-opts（`--disable-cache`/`--verbose`/`-j`/`--profile`/`--auto-update`/`--compile-commands`）、`project new`、`install`、`pack`、`test`、`pkg install/update`、`workspace`、全局 `--color`；每条一句用途 + 默认值（如 `-j 0` = 自动） |
| SCOPE FLAGS | `-p`/`-u`/`-g` 语义与安装路径；`pkg install`/`repo add` 只能选一个且**默认项目作用域**；其余 scoped 命令可组合（`-pug`）且**默认三者全选** |
| SHORTHANDS | 顶部别名 7 + 命令位置简写 28（`pn`…`pt`、`ki`…`ku`、`ra`…`ri`、`wl`/`wb`/`wt`/`wc`/`ww`/`ws`、`u`/`h`/`v`）；标注 `example` 组刻意无简写、`ezmk project pn` 不展开 |
| OPTION SYNTAX | `--flag=value` ≡ `--flag value`；`-pug` 组合；`-j4` 贴值；`--` 终止解析并透传（`utils`、`project run`、`watch --run -- <args>`） |
| ENVIRONMENT | `EZMK_LANG`、`NO_COLOR`、`CXX`/`CC`、`SOURCE_DATE_EPOCH`、`EDITOR`/`VISUAL`（其余安装期变量归 `install.sh`/`install.ps1` 手册或 README，不在 `ezmk(1)` 里） |
| EXIT STATUS | `0` 成功；`1` 致命错误（配置/构建/包/权限等，经 `util::fatal`）；`ezmk test` 以测试失败非零退出；`ezmk watch` 监视器异常结束＝1、Ctrl+C 正常停止＝0 |
| FILES | `ezmk.toml`、`ezmk.lock`、`ezmk-workspace.toml`、`.ezmk/`（cache/pkg/repo/temp/test-results） |
| SEE ALSO | 见 §3.2 |

### 3.4 `ezmk.toml(5)` 内容结构

以 `.TP` 字段表为主，每节给出**字段名 / 类型 / 默认值 / 一句话**（不复制 `docs/en/config_file.md` 的长解释）：

| 节 | 字段（只列名，正文写默认值） |
|---|---|
| `[project]` | `name`（非必校验，仅 `version` 强制）、`version`、`type`（executable/static/shared/utils）、`language`（默认 `C++17`，含区间语法）、`stdlib`、`header_only`、`precompiled`、`precompiled_strict` |
| `[compile]` | `flags`、`msvc_flags`、`include_dirs`、`src_dirs`、`ezmk_macros`、`compile_commands`、`default_profile`、`deterministic`、`source_date_epoch`、`[compile.macros]`、`[compile.profile.<name>]` |
| `[link]` | `flags`、`msvc_flags`、`link_dirs`、`system_target`（单数！）、`[link.profile.<name>]`（前置条件：同名 profile 必须存在于 `[compile.profile.*]`） |
| `[depends]` | `lib`、`want`、`workspace`、版本约束语法（`@`/`^`/`~`/`>=`…） |
| `[test]` | `dirs`、`framework`（catch2/ezmk）、`default_profile`、`include_dirs`、`link_targets`、`flags`（**已弃用**，2.0.0 移除） |
| `[hooks]` | `pre_build`、`post_build`、`on_failure`（仅链接失败触发）、`ctx` 字段 `output`/`project_root`/`profile` |
| `[install]` | `prefix`、`bindir`、`libdir`、`includedir`、`sharedir`（**保留/未实现**） |
| `[utils]` | `tools`（只读展示，不校验）、`[utils.permissions]`（`read`/`write`/`run`，deny > allow > ask） |
| `[pkg]` | `strict_std_check` |

### 3.5 防漂移校验脚本 `scripts/check_man_sync.py`

**语言**：Python 3（与 `scripts/check_i18n.py` 同款先例；CI 已装 `python3`；零新依赖）。

**提取侧（事实源）**：

1. `src/cli.cpp` 的 `OptionSpec` 初始化列表 → 长选项名集合 + 短选项名集合（正则匹配 `{'\0', "name", bool}` 与 `{'x', "name", bool}`）；
2. `kAliases` 表 → 顶层别名（7）+ 简写（28）；
3. `print_help()` 里 `row("ezmk …")` 的命令串 → 命令清单；
4. `std::getenv("X")` 全仓（`src/*.cpp`）→ 运行时环境变量集合；
5. `src/config.cpp` 的 `(*sec)["key"]` / `get("key")` → 各配置节键集合（用于校验 `ezmk.toml(5)` 的字段名，P1 扩展）。

**提取侧（man）**：`.SH OPTIONS`（含各 `.SS` 分组）中的 `\-\-flag`/`\-x`、`.SH SHORTHANDS` 表、`.SH COMMANDS` 中的命令名、`.SH ENVIRONMENT` 中的变量名、`.TP` 后的字段名。

**断言（全部失败即 exit 1）**：

- 双向差集为空：`CLI\man`（漏写）与 `man\CLI`（多写＝CLI 已删除）都报错并分组打印；
- **白名单**（允许出现在 man 但不属于 OptionSpec）：`--color`、`--help`/`-h`、`--version`/`-V`、`--`、`--` 透传约定；
- 别名/简写表逐条一致（数量 + 内容）；
- 配置键对照 `config.cpp`（P1）；
- **提取基线断言**：提取到的选项数/命令数低于脚本内置基线（当前 CLI 规模）即**失败并提示"cli.cpp 结构可能已变更，请更新提取正则"**——防止 CLI 重构后脚本静默通过（这是本设计里最关键的一条防线，§3.10 坑 5）。

**明确不做**：不做 C++ 语义解析（只做结构化正则提取）、不校验文案与 i18n 一致、不比较 man 与 `docs/` 的措辞。

**输出**：分组列出 missing/extra/基线异常；`exit 0/1`；本地与 CI 同一入口。

### 3.6 CI 接入（渲染 lint + 漂移闸门 + 分发断言）

- **ubuntu job** 增装 `groff man-db`，新增两步：
  1. `Man pages: render lint` — `groff -man -Tutf8 -z -ww man/*.1 man/*.5`（零告警才通过；`-z` 只检查不输出）+ `grep -nP '(?<!\\)-' man/*` 检查未转义连字符；
  2. `Man pages: CLI drift gate` — `python scripts/check_man_sync.py`。
- **新增 `man-pages` job**（对照现有 `zsh-completions` job 的既有策略：它**不执行** `install.sh`（会联网 clone），而是断言其代码块并在本地复现关键步骤）：
  - 断言 `install.sh` 含 man 安装块与 `EZMK_NO_MAN` 分支；断言 `publish/arch/PKGBUILD` 含两条 `install -Dm644 man/…`；
  - 断言 `release.yml` 的 linux/macOS 打包步骤含 `cp -r man`，且 **Windows 打包步骤不含** man；
  - 断言 `publish/homebrew/ezmk.rb` 含 `man1.install`/`man5.install`；
  - 用 `PREFIX=$RUNNER_TEMP` 复现安装动作后跑 `man --warnings -l "$MANPAGE"` 确认可渲染。
- **本地自检**（写入 CONTRIBUTING 与 `ezmk-workflow` skill 的文档改动清单）：改 CLI/man 后跑 `python scripts/check_man_sync.py` + groff lint。

### 3.8 `ezmk help` 的 See also 行（i18n）

- **位置**：`cli::print_help()` 末尾，GNU 语法说明之后（`src/cli.cpp:1426` 之后、函数收尾 `}` 之前），`std::cout << get(I18nKey::help_see_also_man) << "\n";`。
- **文案**：en `See also: man ezmk (man 5 ezmk.toml for the config file)`；zh `另见：man ezmk（配置文件见 man 5 ezmk.toml）`；zh-TW 按现有变体惯例处理（未转写则继承 zh，不强制新增）。
- **i18n 三向**：`include/ezmk/i18n_keys.def` 的 help 分组新增 `help_see_also_man` + `locale/en.json` + `locale/zh.json` → **405 → 406 键**，`python scripts/check_i18n.py` 通过；`test/test_i18n.cpp` 的 X-macro 全键回归（`kAllKeys` 由 `i18n_keys.def` 生成）**自动覆盖，无需改测试**；`build.sh` 重跑 `scripts/embed_locale.py`。
- **不做动态探测**：不检测 `command -v man` 后再决定是否打印（会引入平台分支与测试面）；静态一行，由用户自行判断——这与"易用优先、不堆机制"的定位一致。

### 3.10 已知坑位与对策

1. **`.TH` 日期漂移** → 发布 commit 统一更新，写入发布清单（不放构建期自动日期，保持 man 可复现）。
2. **连字符未转义** → groff 渲染成 U+2212，破坏复制粘贴；CI lint + `grep` 双保险（§3.6）。
3. **`man ezmk` 命中不到**（`PREFIX=$HOME/.local` 等非标准前缀）→ `install.sh` 打印 `MANPATH` 提示，`technical.md` 写明。
4. **Homebrew digest 失效** → 资产内含 man 后 `sha256` 变化，发布后**必须回填**；否则 `brew install` 校验失败（1.4.2 同类坑，已有流程）。
5. **校验脚本静默失效**（CLI 重构后正则不再命中）→ §3.5 的"提取基线断言"：提取数低于基线即失败并要求更新脚本。
6. **Windows 资产混入 man** → release.yml 的 Windows 步骤明确不加，CI 断言"Windows 打包不含 man"。
7. **PKGBUILD 双分支漏装** → 把 man 安装放在 `if [ -f build/ezmk.exe ]` 之外（两分支共用）。
8. **`ezmk.toml(5)` 与 `docs/en/config_file.md` 双源** → 职责边界（速查 vs 规范）+ SEE ALSO；脚本对配置键做集合级校验（P1），降低字段级漂移。
9. **非 ASCII/locale** → man 源全 ASCII（§3.2），避免 `groff` 在不同 locale 下的编码差异。
10. **man 与补全的"新命令"漏更** → 本版不联动补全（§3.11）；但 `check_man_sync.py` 会把"新增 CLI 选项未进 man"变成 CI 失败，间接形成提醒。

### 3.11 明确不做（延后）

- **Windows 手册**：`install.ps1` / winget 不含 man（Windows 无 `man`；MSYS2 用户走 `install.sh`）。
- **man 多语言**：不做 `man/zh_CN/` 或 i18n 生成；中文用户继续用 `docs/zh` 与 `EZMK_LANG=zh ezmk help`。
- **`ezmk man` 子命令 / `--man`**：不新增 CLI 面（本版唯一 CLI 改动是 `help` 末尾一行文案）。
- **把 `docs/` 全文搬进 man**：man 保持速查（§3.1 职责边界）。
- **mdoc 迁移与文档生成工具链**（pandoc/ronn/scdoc）：不引入新构建依赖。
- **补全联动**：`res/ezmk.zsh` 与 man 的双向校验不在本版。
- **`man/ezmk-workspace.toml.5` / `man/ezmk-lua.1` 的正式交付**：列为 M-11 随附项，若时间/评审不允许则延后到 1.4.4 或 2.0.0 前的补丁。

## 6 跨版本关注点

- **与 2.0.0 的联动（重要）**：2.0.0 将移除 `[test].flags`（1.2.0-dev.12 弃用）与 `ezmk utils cc`（1.2.0 弃用）。这些条目一旦从 CLI/配置中删除，`check_man_sync.py` 会**立即失败**——这正是本版设计的目的（把"删 CLI 忘了改文档"变成 CI 红灯）。建议 2.0.0 计划把"同步 man 条目"列为显式交付项。
- **与 1.4.x 系列**：1.4.3 是 1.4.2 之后的**文档/分发补丁**，与 1.4.0/1.4.1/1.4.2 无顺序依赖，也不触碰任何 1.4.x 已发布的语义。
- **与 `docs/` 双层结构**：man＝离线速查、docs＝完整规范。后续新增 CLI 选项的检查清单加两条：更新 `man/` + 跑 `check_man_sync.py`（写入 CONTRIBUTING 与 `ezmk-workflow`/`ezmk-codebase` skill）。
- **与分发/发布 skill**：`ezmk-publish` 的发布清单与 Homebrew/pacman 章节需补 man（资产内容、formula 的 `man1.install`、PKGBUILD 的两行安装、digest 回填）；`ezmk-workflow` §3.3/§3.4 的产物核对加"手册页存在且可渲染"。
- **后续可选演进**（不在本版）：man 多语言（`man/zh_CN`）、`ezmk man`/`--man`、`ezmk-lua(1)`、`ezmk-workspace.toml(5)` 正式化、与 zsh 补全的双向校验、`docs/` 与 man 的字段级自动同步。
