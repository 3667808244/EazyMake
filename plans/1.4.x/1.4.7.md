## 1 背景

1.4.6 的 Q-20 把 MSVC 的 `make_msvc_exe_cmd` / `make_msvc_dll_cmd` / `make_msvc_lib_cmd` 从 `escape_shell_arg`（POSIX 规则、反斜杠翻倍）改为 `quote_windows_arg`（MSVCRT 规则）。为验证它，我在本机（VS 2022 **Build Tools**）做了端到端实测，发现四处既存缺陷，使这条验证链根本无法到达构建阶段：

1. **Build Tools 从不被探测**：`find_vcvars64()` 的 vswhere 查询是 `-latest -property installationPath`；实测该查询**无输出**（vswhere 默认过滤掉 Build Tools），加 `-products *` 才输出 `...\@@2022\BuildTools`。硬编码回退列表里也只有 Community/Professional/Enterprise，没有 `2022\BuildTools`。
2. **MSVC 探测命令拼错**：探测用 `cmd /c "call \"<vcvars>"\ > NUL && cl /Bv"`，cmd 实际收到字面 `\"C:\...\vcvars64.bat\"`，报 `不是内部或外部命令` → 探测恒失败。`escape_cmd_arg` 本身正确，错在 `\"` 加外层引号的包裹方式；`load_msvc_env()` 内有同一写法。
3. **`load_msvc_env()` 从未被调用**：`detect_toolchain()` 只把 `tc.vcvars_path` 存下来，没有任何编译/链接路径加载 vcvars 环境。因此即便探测成功，`cl.exe` / `INCLUDE` / `LIB` 也不可用——除非 ezmk 本身是在 VS 开发者命令行里启动的。实测：普通 shell 下（探测已临时修好）ezmk 选中 MSVC 后编译以 `cl.exe` 找不到失败；vcvars shell 下则成功。
4. **优先级与本机现状**：现有顺序是 `$CXX` 覆盖 → **MSVC 优先** → MinGW。用户裁定改为 **g++/clang++ 优先，MSVC 回退**：既符合本机/CI 的 MinGW 工作流，也避免“装了 Build Tools 的机器一夜之间默认改用 MSVC”。

本版把 1~3 修好、落实用户要求的优先级，并补一条可显式强制工具链的通道（`EZMK_TOOLCHAIN`），使 MSVC 路径能在本机/CI 被真正验证。

## 3 详细设计

### 3.1 工具链探测与优先级（M-04 / M-06）

`detect_toolchain()`（`src/toolchain.cpp`）顺序调整为：

1. `$CXX` / `$CC` 覆盖（保持现状，最高优先）。
2. **系统 g++/clang++**（`g++ --version` / `clang++ --version`）——即 MinGW/系统 PATH 上的 GCC/Clang。
3. **MSVC**（`find_vcvars64()` + `call vcvars && cl /Bv` 探测）。
4. 都不可用 → 现有“未找到编译器”报错。

新增 `EZMK_TOOLCHAIN`（大小写不敏感）：`msvc` / `gcc` / `clang` / 空=自动。显式指定时跳过自动顺序、直接解析；目标不可用时报明确错误（而不是静默回退）。它与 `$CXX` 的关系：`$CXX` 仍最优先（保持既有语义），`EZMK_TOOLCHAIN` 在自动探测阶段生效。

### 3.2 Build Tools 探测（M-01）

- `find_vcvars64()` 的 vswhere 命令加 `-products *`。
- 硬编码回退补 `C:\Program Files\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat` 与 x86 版本。

### 3.3 cmd 引用修复（M-02）

探测与 `load_msvc_env` 统一为 `cmd /c call "<escaped vcvars path>" > NUL && <cl /Bv | set>`（去掉 `\"` 与外层引号；路径经 `escape_cmd_arg` 处理）。

### 3.4 MSVC 环境注入（M-03 / M-05）

- 新增 `toolchain::msvc_env(const Toolchain&)`：首次调用执行 `load_msvc_env`，结果缓存，返回 `const std::map<std::string,std::string>&`；非 Windows 或非 MSVC 返回空表。
- 新增 `toolchain::apply_msvc_env(RunOptions&, const Toolchain&)` 收敛注入点。
- **编译**（`src/cache.cpp` `compile_one_source`）：MSVC 时把 env 并入 `RunOptions.env`（与既有 `SOURCE_DATE_EPOCH` 合并）。
- **链接 / 归档 / 测试链接 / 包编译**（`src/build.cpp`、`src/pkg.cpp`）：所有 MSVC 分支的 `run_command` / `execute_link` 调用注入同一 env。
- POSIX 路径不变（`load_msvc_env` 在 `#ifdef EZMK_WIN`）。

### 3.5 测试（M-05 / M-06）

- **默认回归不变**：MinGW 优先后，本机/CI 的 `test-all` 仍走 g++，基线 1130/6536，新增用例只增。
- **MSVC 定向验证（可用性守卫）**：新增集成用例，当 `EZMK_TOOLCHAIN=msvc` 且 vcvars 可定位时，构建含空格路径的 executable / static / shared，断言产物存在；不可用时 SKIP。
- **缓存失效**：两套工具链各建一次，断言 `record.json` 的 `compiler` 字段变化触发重编。
- 本机已验证的实测证据（1.4.7 实现后应可复现）：MSVC 下 `cl` 编译、`link.exe /OUT:"..."`（单反斜杠）、`lib.exe` 静态库、`link.exe /DLL` 动态库、产物可运行。

### 3.6 明确不做

- 破坏性 API 变更 / 弃用面移除（归 2.0.0）。
- Linux/macOS 文件监视真递归。
- MSVC 下完整“开发者命令行”文档重写（仅在 docs 构建页补一段“Windows 工具链选择与 MSVC 回退”）。

## 5 兼容性

| 变更 | 影响 | 说明 |
|------|------|------|
| 工具链优先级（MinGW 优先） | **行为变更（Windows）** | 本机/CI 行为不变（仍 g++）；装了 Build Tools 的机器也仍优先用 PATH 上的 g++/clang++，不再默认切 MSVC |
