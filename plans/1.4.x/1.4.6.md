## 1 背景

第一轮审计（1.4.0-dev.6）修 8 项 P0/P1，第二轮（1.4.2）修接口层与跨平台路径/编码共 36 项。本轮（第三轮）在 1.4.x 线上重新展开，结论与前两轮互补：**编译器与静态分析在首方代码上已经是干净的**，问题集中在那些正常路径不经过、但一旦触发就会损坏数据或放行坏输入的分支：

- **错误路径的资源与事务**：zip 解压失败对同一 `FILE*` 二次 `fclose`（UB）；`pkg install` 目录/git 源**成功**却回滚依赖；`atomic_rename` 兜底 copy 失败仍删源。
- **命令/参数装配**：GCC 响应文件按「一行一参数」写入却未转义（GCC 实际按空白切分）；`--report` 格式串未转义；Windows 路径用了 POSIX 转义。
- **不可信输入解析**：tar size 字段溢出绕过越界保护、截断 gzip 被当部分成功；URL 末段文件名未净化、临时包不清理。
- **配置/契约**：`[workspace.options].stop_on_error` 解析后从不生效；`--precompiled` 标记插入位置假设 `[project]` 是首节；仅 `[link.profile.*]` 的 profile 被误拒。
- **确定性**：目录遍历未排序影响 `-I`/链接顺序；并行路径对新文件误报 include 结构变化。

逐条修复项与方案见 §2/§3，执行阶段见 §4。审计中已核实为**误报**的项（`ThreadPool`、`safe_extract_path`、SHA-256、`topo_layers` Kahn 等）记录在 §3.8，后续轮次不必重复追查。

## 3 详细设计

### 3.1 内存安全与数据完整性（Q-01 / Q-02 / Q-04）

**Q-01 — `extract_zip` 二次 `fclose`**。`src/util.cpp` 的 `extract_zip` 自己 `fopen` 归档文件，内层失败分支（输出文件打开失败或 `mz_zip_reader_extract_to_callback` 失败）已经 `mz_zip_reader_end(&zip); std::fclose(archive_file);` 后 `throw`，外层 `catch(...)` 又对同一 `FILE*` 再执行一次 `mz_zip_reader_end` + `fclose`；`mz_zip_reader_init_cfile` 并不接管该 `FILE*`（只关自己打开的 `MZ_ZIP_TYPE_FILE`）。
方案：把「结束 reader + 关闭归档文件」收敛为**唯一出口**（RAII guard 或单一 `cleanup` lambda），错误分支只 `throw`、不再自行关闭；`mz_zip_reader_end` 可保留二次调用（其内部对 `m_pState==NULL` 提前返回，安全），但 `fclose` 必须恰好一次。
测试：构造必然失败的解压用例（截断/CRC 错的 zip、或不可写目标目录），断言进程不崩、只关闭一次（可用 hook/计数器在测试内验证 `FILE*` 关闭次数）。

**Q-02 — 事务提交点未覆盖目录/git 安装**。`src/pkg.cpp` 的 `install()` 用 `TxnGuard`（析构时 `if (outermost && !committed) AutoInstallTxn::rollback()`）实现「最外层安装失败 → 回滚自动装的依赖」。但只有压缩包路径把 `txn_guard.committed` 置 true；目录安装、git 源安装、repo `type="dir"` 三条路径都直接 `return install_from_directory(...)` / `return install_git_source(...)`，`committed` 恒为 false。`install_from_directory` → `process_installed_pkg` 会触发依赖自动安装（`AutoInstallTxn::paths()` 记录 `dest_dir/dep.name`）。
触发：`ezmk pkg install <目录>` / `pkg install <git-url>` / 仓库 dir 包，且其依赖被自动安装。
后果：安装成功后析构回滚，把刚装好的依赖 `remove_all` 掉，得到残缺安装；lockfile 已写入并列出已不存在的依赖。
方案：**所有成功返回路径**都必须提交事务——在三个 `return install_from_directory/git_source` 之前置 `txn_guard.committed = true`（或在 `InstallOutcome::Ok` 时统一提交；`Cancelled`/抛异常保持回滚）。注意 git 链路的成功判定要跟随内层返回值。
测试：目录源 + git 源两类夹具，各自带一个缺失依赖（在测试仓库内提供可自动安装的依赖包）；断言安装成功后依赖仍在、lockfile 与实际一致；再补一条失败用例断言仍回滚。

**Q-04 — `atomic_rename` 失败仍删源**。`src/util.cpp` 中 `fs::remove(from, rm_ec)` 在 `if (ec) fatal(...)` 之前无条件执行。
触发：`fs::rename` 失败（Windows 目标被运行中的 exe 占用）且 `fs::copy_file` 也失败（空间/权限/跨设备）。
后果：唯一可用的成品被删；且 `copy_file(overwrite_existing)` 可能已把目标截断。`atomic_write_text` 因此可能把真实目标留成半截文件却返回 false。
方案：只有 `copy_file` 成功后才删除源；失败时保留源并 `fatal`（或在 `atomic_write_text` 语境下返回 false 且不动源/目标）。同时评估 `copy_file` 前先删目标的风险，必要时改为「先写临时目标再替换」。
测试：单测注入 `from` 存在、目标不可写（或 `copy_options` 失败桩）场景，断言源文件仍在；成功路径保持原行为。

### 3.2 编译正确性与确定性（Q-03 / Q-19 / Q-30 / Q-31）

**Q-03 — 响应文件参数未转义**。`src/cache.cpp` 的 `join_args_with_response_file()` 注释称「一行就是一个参数，含空格路径安全」，但 GCC/Clang 的 `@file` 语法是**按空白切分**并支持引号/反斜杠转义。仅当拼接后命令超过 `kResponseFileThreshold`（16 KiB）才走此路径。
触发：命令超阈值且任一参数含空格、引号或结尾反斜杠（如 `-I` 指向含空格目录、`src with space/main.cpp`、`-DKEY="a b"`）。
后果：参数被拆散或引号被吞——轻则编译/链接失败，重则**宏值静默改错**（错误但可构建）。
方案：写入响应文件时按 GCC `@file` 规则转义每个参数（空格/引号/反斜杠/换行），或改用「每参数一行 + 单引号包裹 + 转义内层单引号」。需确认该 helper 仅服务于 GCC/Clang（MSVC 响应文件规则不同，勿混用）。
测试：构造含空格/引号/结尾反斜杠的参数集，超过阈值触发响应文件，断言传回编译器的 argv 与原始参数逐元素相等（用回显干程序或解析辅助函数）；修正 `test_workspace_build.cpp` 中固化错误前提的用例。

**Q-19 — 目录遍历未排序**。`util::list_files`、`build.cpp` 的包归档收集与 `.ezmk/pkg` 扫描使用 `fs::directory_iterator` 未排序，导致对象顺序、包归档顺序、多包 `-I`/`-L`/`-l` 顺序依赖文件系统（同头文件多来源时 `-I` 谁生效、相互依赖静态库的链接顺序）。
方案：这些遍历统一按标准化路径（或相对名）排序后再使用；给排序键加注释说明确定性意图。
测试：单测构造多目录多归档，断言输出顺序稳定且与创建顺序无关；集成确认全量构建结果不变。

**Q-30 — 并行路径 `operator[]` 先于 `find`**。`build.cpp` 的并行结果合并先执行 `record.files[sr.rel_src]`（默认插入）再 `find`，使 `old_it != end()` 恒真，新文件误报 include 结构变化；串行路径（`cache.cpp`）先 `find`，两者行为不一致。
方案：并行路径改成先 `find` 判存在，再按需插入；对齐串行路径。
测试：新增文件 + `-jN` 构建，断言不输出结构变化提示；已存在文件改动仍正常提示。

**Q-31 — 仅 link profile 被拒**。`build.cpp` 的 `apply_profile()` 只查 `cfg.compile_profiles`，否则走 fatal「unknown profile」；但同一函数把 `cfg.link_profiles` 收进建议名列表，自相矛盾。
方案：profile 合法性按「compile 或 link 任一存在」判定；仅 link profile 时只应用 link 侧。
测试：`[link.profile.fast]`（无 compile 同名）+ `--profile fast` 构建成功；完全未知 profile 仍报错并给出建议。

### 3.3 归档与下载健壮性（Q-05 / Q-06 / Q-22 / Q-24 / Q-25 / Q-26）

**Q-05 — tar size 字段与截断 gzip**。`util.cpp` 的 `octal_to_size` 不校验数字且按有符号 char 做减法 `s[i]-'0'`，全 0xFF 可解析出 2^64-1，使 `off + fsize > out.size()` 回绕、越界保护失效；`extract_targz` 的解压循环只处理 `DONE` 与 `FAILED(-1)`，未传 `TINFL_FLAG_HAS_MORE_INPUT` 时输入耗尽返回 -4 会被放行。
方案：(a) `octal_to_size` 严格只接受 0-7（与空格/NUL 终止），非法即抛；(b) 越界判断用减法（先例：1.4.5 zip 总量 `m_uncomp_size > kMaxDecompressedSize - total`）防回绕；(c) 解压循环把其余负状态（含 `FAILED_CANNOT_MAKE_PROGRESS`）一律按错误处理。可选：校验 tar 校验和。
测试：恶意 size（全 0xFF、非八进制、超出剩余字节）三种夹具断言抛错且不越界；截断 gzip 报错而非空/部分解包。

**Q-06 — 下载失败与 URL 文件名**。`util.cpp` 的 Windows 下载循环忽略 `WinHttpQueryDataAvailable`/`WinHttpReadData` 失败（`dwSize` 保持 0 即退出而 `write_ok` 仍真），断流被当成功；`if (!write_ok) continue;` 还会跳过 1 GiB 统计；非 Windows 的 `curl -sL` 无 `--fail`，HTTP 错误页会被存成归档；`pkg.cpp` 取 URL 末段作文件名未净化（Windows 下反斜杠加点点可逃出 temp），且临时包从不清理。
方案：(a) 查询/读取失败置错误并抛（或至少置 `write_ok=false`）；(b) `curl -sL --fail`；(c) 文件名净化（拒绝路径分隔符与上级目录记号，或统一生成唯一名）+ 安装结束清理临时归档（含异常路径，用 RAII/作用域清理）。
测试：模拟读取中断（可注入的桩/本地 HTTP 服务器返回中途断开）断言报错；含上级目录记号的 URL 断言不写出 temp；安装后断言临时文件已删。

**Q-22/Q-24/Q-25/Q-26 — 边界与失败检查**。`skip_gzip_header` 对 FEXTRA 的 `xlen`、FNAME/FCOMMENT 的 NUL 扫描、FHCRC 未做越界校验（可让位置越过数据末尾后静默解出空结果）；`create_zip` 直写目标（非原子，崩溃/失败毁掉既有归档）；tar 解包的 `ofstream` 不检查打开与写入；`mz_deflateInit2`、Windows `CreatePipe` 返回值未检查（失败后在未初始化对象上继续）。
方案：逐项补边界检查 / 失败返回 / 原子写（复用 `atomic_rename` 或同款 tmp 后 rename）；`create_zip` 与 `create_targz` 行为对齐。
测试：畸形 gzip 头、同路径既有归档被保护、只读目标报错、`CreatePipe` 失败桩。

### 3.4 pkg 事务与 lockfile 校验（Q-11 / Q-12 / Q-13 / Q-15 / Q-16 / Q-17 / Q-18）

**Q-11 — 取消未传播**。`process_installed_pkg` 返回 `void`，拒绝覆盖/preinstall 提示只是 `return`；调用方仍返回 `InstallOutcome::Ok` 并重写 lockfile；`update_all` 把取消计为已更新。
方案：`process_installed_pkg` 返回三态（`Ok` / `Cancelled` / 抛异常），`install_from_directory` 与压缩包路径据此返回；取消时**不写 lockfile**；`update_all` 分计 `updated`/`cancelled`/`failed`（对照 1.4.2 F-29 的失败退出语义）。
测试：对覆盖提示答 n、对 preinstall 提示答 n 两条夹具，断言退出码/计数/lockfile 均未被误改。

**Q-12 — verify 盲点**。`lockfile.cpp` 的 `verify()` 在记录 hash 非空但 `find_package_archive` 为空时既不 mismatch 也不告警（删产物可静默通过确定性构建）；header-only 分支先于 git 分支且 `recorded` 为空即 continue，使 `source=="git"` 的 commit/来源校验不可达。
方案：产物缺失 + 期望 hash 非空 → 记 mismatch（或至少告警）；git 包按来源类型优先校验（header-only 但 `source=="git"` → 走 marker/commit 校验）；明确「无 hash 可查」与「hash 缺失」的区别。
测试：删除产物 → verify 报 mismatch；header-only git 包篡改/删除 marker → mismatch。

**Q-13 — `.new` 暂存误删**。`pkg.cpp` 安装前无条件 `remove_all(install_path + ".new")`，而 `validate_pkg_name` 允许点号，故存在名为 `x.new` 的合法包时会被静默删除。
方案：暂存目录改名到不可能与合法包名冲突的隐藏前缀 + 唯一后缀（如 `.ezmk-stage-<name>-<pid/ns>`），复用注释中已声明的「隐藏且无冲突」思路。
测试：安装 `x` 且已装 `x.new`，断言 `x.new` 仍在。

**Q-15/Q-16/Q-17/Q-18 — 输入校验与写入可见性**。版本约束对超长数字串的 `std::stoul` 会裸抛 `out_of_range`（`config.cpp` 校验器放行任意长度数字）；`save_repo_list` / `lockfile::save` 忽略 `atomic_write_text` 返回值；损坏/被截断的 `list.json` 被解析成空注册表后由 `repo add` 覆盖（永久丢失既有登记）；`pkg info` / `pkg update` 未做 `validate_pkg_name`（越目录读取）。
方案：`stoul` 收敛到带 try/catch + 明确错误的 helper；写失败必须让命令以非零退出或至少显式告警，不得静默成功；注册表解析失败与「空注册表」区分（解析失败拒绝写入或先备份）；补齐名字校验（入口统一）。
测试：超长版本串夹具、只读注册表/lockfile 写入失败断言、损坏 JSON 后 `repo add` 不吞登记、`pkg info ../x` 被拒。

### 3.5 watcher 与 workspace（Q-09 / Q-10 / Q-28 / Q-29）

**Q-09 — macOS 补挂双 close**。`file_watcher.cpp` 的 `macos_repair_watches()` 先 `close(w.fd)`，随后 `open()` 失败分支 `continue` 却未把 `w.fd = -1`，下一个 2s 修复周期会对同一（可能已被复用的）fd 再 `close` 一次。相邻的 `macos_register` 失败分支是正确的，反证此处漏重置。
方案：`close` 后立即 `w.fd = -1`；统一「关闭即置 -1」的辅助函数。
测试：macOS 环境用桩模拟 `open` 失败后二次修复，断言只 close 一次；无 macOS 环境时以单元桩覆盖状态机。

**Q-10 — `stop_on_error` 配置不生效**。`workspace.cpp` 把 `[workspace.options].stop_on_error` 解析进 `ws.options`，但 `workspace_build.cpp` 只消费 CLI `opts.stop_on_error`。
方案：配置值作为 CLI 未显式给出时的默认（CLI 优先），在 `run_build`/`run_test`/`run_watch` 计算有效值；对照 `default_jobs` 的既有消费方式。
测试：`ezmk-workspace.toml` 置 true、无 CLI 旗标 → 首次成员失败即停止；CLI `--stop-on-error` 仍优先。

**Q-28/Q-29 — 写回边界与平台健壮性**。`workspace.cpp` 的 `members` 数组结束定位在 `[` 换行到下一行时返回 npos、`[workspace]` 无结尾换行时插入会拼成 `[workspace]members`、`default_jobs` int64 到 int 无上限（可致线程爆炸）；Linux `inotify` 读把 `EAGAIN` 当致命；Windows `win32_cleanup` 在排空取消完成前就释放 OVERLAPPED 池（停机期潜在 UAF）。
方案：写回按「替换整行/整节 + 保证换行分隔 + 多行数组感知」处理；`default_jobs` 上限收敛（如 1 到 1024，或按 `INT_MAX`/硬件上限钳制）；`inotify` 重试 `EAGAIN`；`win32_cleanup` 先 `GetQueuedCompletionStatus` 排空/等待取消，再释放池。
测试：多行 `members`、无结尾换行、超大 `default_jobs` 三类夹具；inotify/OVERLAPPED 以平台可运行范围覆盖，其余以代码审查 + 注释记录。

### 3.6 导出/CLI/跨平台（Q-07 / Q-08 / Q-14 / Q-20 / Q-21 / Q-23 / Q-27）

**Q-07 — `--precompiled` 标记位置**。`build.cpp` 的 `inject_precompiled_marker()` 查找「`[project]` 之后的下一个节头」，隐含假设 `[project]` 是首节；若文件以注释或其它节开头，第一处换行加 `[` 就是 `[project]` 自己，`precompiled = true` 被插到文档根级，消费端读 `project.precompiled` 仍为 false，`--precompiled` 归档因缺 `src/` 被拒装。
方案：先定位 `[project]` 节头，再在该节内（下一个节头之前）插入；或改用 toml++ 解析定位（注意保留注释/格式，可参考 workspace 写回的文本级做法）。
测试：首行注释、`[project]` 前有其它节、`[project]` 为末节三种 fixture，断言标记落在 `[project]` 内且打包可被 `pkg install` 接受。

**Q-08 — `--report` 注入**。`build.cpp` 把 `ctx.report_fmt` 原样拼进 shell 命令（同行的 filter 与 report_path 都转义）；POSIX 上 `run_command` 走 `/bin/sh -c`。
方案：`report_fmt` 也经 `escape_shell_arg` / 平台正确的引用；或对值做白名单（合法 reporter 名 + 可选参数）。
测试：`--report 'x; <cmd>'` 断言命令不被注入（输出不含副作用标记）；合法 `console`/`junit` 仍工作。

**Q-14/Q-20/Q-21/Q-23/Q-27 — 线程安全、转义与契约**。`detect_toolchain()` 的 `static bool cached_valid` + `static Toolchain cached` 非线程安全（并发首调竞争）；MSVC/`ar` 构建器用 `escape_shell_arg`（POSIX 规则）配 Windows `CreateProcessW`（已有 `quote_windows_arg`）；POSIX `run_command` 的 `1>out 2>err` 未给临时路径加引号（`TMPDIR` 含空格/元字符会破坏捕获，理论上可注入）；`toml_quote` 只转义换行/制表/回车/引号/反斜杠，其余控制字符原样输出破坏 TOML；`file_write` 的 `fs::create_directories` 可抛异常违背 bool 契约。
方案：`detect_toolchain` 用 `std::once_flag` / 函数内静态初始化；Windows 路径统一 `quote_windows_arg`；POSIX 重定向路径引号化（或改用不经过 shell 的 fork/dup2 直接重定向）；`toml_quote` 对小于 0x20（除已知）与 0x7F 转义为 U+XXXX 形式；`file_write` 捕获目录创建异常并返回 false。
测试：并发 `detect_toolchain`（多线程）无竞争；含空格 `TMPDIR` 的输出捕获正确；控制字符 TOML round-trip 合法；只读父目录下 `file_write` 返回 false 不抛。
