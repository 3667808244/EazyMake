# EazyMake 1.2.0-dev.9 — 包构建配置收敛：`[compile].src_dirs` / `[compile].include_dirs` 对包生效

> 本计划并入 1.2.0 正式发布版。发布总览见 [`1.2.0.md`](1.2.0.md)。
>
> **dev.7 的延伸**：dev.7（`pkg install <dir>` 从文件夹安装 + `ezmk.toml` 向上查找）把包安装扩展到本地目录，但包的**构建配置**仍不完整——`[compile].src_dirs` 被硬编码忽略。本计划收口包配置与项目配置的语义差距。

---

## 1 背景

`package_authoring.md` §2.3 已声明包支持 `[compile]` 的 `include_dirs` / `src_dirs`，但实现未对齐，导致「文档承诺」与「实际行为」漂移：

- **`src_dirs` 被静默忽略**：`compile_package()`（`src/pkg.cpp:381`）硬编码 `util::list_files(pkg_dir / "src", ...)`，只编 `src/`。包作者写 `src_dirs = ["src", "generated"]` 看着有效实则无效，与项目侧（`build::collect_sources()` 多目录收集，`src/build.cpp:124`）行为不一致。
- **`include_dirs` 基本生效但未固化**：
  - 包自编译：`cfg.compile` → `compile_sources` 相对包根解析 `-I`（`src/cache.cpp:413-416`），已生效。
  - 消费者侧：项目依赖包时逐个加 `<pkg>/<include_dir>`（`src/build.cpp:616-623`），已生效。
  - 但存在边界缺口：`include_dirs` 含默认 `"include"` 时与 `def_inc`（`proj_root/include`，`src/cache.cpp:411`）重复 `-I`；自定义 `include_dirs` / `@link:` 解析均无测试固化。
- **包 `type` 语义未对齐**：包文档默认 `type = "executable"` 却编译成静态库，若直接复用 `collect_sources(project_type)` 会把包误判为应用、误要求 `main.cpp`。

目标：让包的 `[compile]` 配置与项目语义对齐，**修复 + 固化 + 测试 + 文档**。

## 3 详细设计

### 3.1 `collect_sources` 增加 `require_main` 参数（项目零变化）

现状签名（`include/ezmk/build.hpp:40` / `src/build.cpp:124`）：

```cpp
std::vector<fs::path> collect_sources(
    const std::vector<std::string>& src_dirs,
    const fs::path& proj_root,
    const std::string& project_type);   // 仅用于 "executable" 的 main.cpp 校验
```

问题：包文档默认 `type = "executable"`，但包永远编译成静态库（`compile_package()` 一律归档 `.a`/`.lib`）。直接把 `cfg.project.type` 传入会让默认包误触发 `main_missing` 致命错误。

设计：追加可选参数 `bool require_main = true`（默认 `true` 保项目行为）：

```cpp
std::vector<fs::path> collect_sources(
    const std::vector<std::string>& src_dirs,
    const fs::path& proj_root,
    const std::string& project_type,
    bool require_main = true);          // false → 包模式：跳过 main.cpp 校验
```

- 项目调用点（`src/build.cpp:576,787`）不传该参数 → 行为零变化。
- 包调用点显式传 `false`：`collect_sources(cfg.compile.src_dirs, pkg_dir, cfg.project.type, /*require_main=*/false)`。
- **空源行为收紧**：`collect_sources` 对「无任何源文件 / 全部目录缺失」走 `util::fatal`（`no_source_files`/`src_dir_missing`）。现状包路径是 warn + 返回空（`src/pkg.cpp:385`）。因 header_only/precompiled/utils 短路全部前移到收集之前（见 §3.2），能到达收集的包必属「非 header_only 却无源文件」的退化情形 → **推荐收紧为 fatal**（对齐项目语义、fail-fast）。兼容性见 §5。

### 3.2 `compile_package()` 源收集改造

`src/pkg.cpp` `compile_package()` 现状（`365-387`）：

```cpp
// precompiled 短路在前（373-376）
fs::path build_dir = pkg_dir / "build";
...
auto sources = util::list_files(pkg_dir / "src", {".c",".cc",".cpp",".cxx"});  // 381 硬编码
if (sources.empty()) {
    if (cfg.project.header_only) return {};   // 384
    util::warn("package has no source files: " + name);  // 385
    return {};
}
```

改为：

```cpp
if (cfg.project.precompiled) { /* 不变 */ }
if (cfg.project.header_only) return {};                     // 短路前移到收集前（无 src/ 的包不得触发 src_dir_missing）
auto sources = build::collect_sources(
    cfg.compile.src_dirs, pkg_dir, cfg.project.type,
    /*require_main=*/false);                                 // 多目录 + 去重 + 缺失 warn；空 → fatal
```

- `cfg.compile.src_dirs` 由 `parse_config` 默认填充 `["src"]`（`src/config.cpp:439-440`），包不写则行为与现状完全一致。
- `@link:` 已在 `parse_config` 对 `src_dirs` 生效（`src/config.cpp:725-728`，共享解析器），包配置自动受益。

### 3.3 `include_dirs` 固化

**自编译侧（共享修复）**：`src/cache.cpp:411-417` 先无条件加 `def_inc = proj_root/include`（存在时），再逐条加 `include_dirs` 相对 `proj_root` 解析结果。当 `include_dirs` 含默认 `"include"` 时产生重复 `-I`（项目侧同样存在）。修复：对 `[def_inc] + [include_dirs 解析结果]` 做**保序去重**后输出。编译器行为不变，compile_commands.json 输出更干净。

**消费者侧（固化）**：`src/build.cpp:612-623` 已把默认 `<pkg>/include` 与每个 `<pkg>/<include_dir>` 加入 `extra_includes`（相对包根解析、与 `pkg_include` 去重、缺失目录跳过）。逻辑正确 → 本轮**补测试冻结**，不改实现（去重细节统一为集合即可）。

**`@link:`**：`parse_config` 对 `include_dirs` 的 `@link:` 解析（`src/config.cpp:729-732`）在包配置上同样生效（共享解析器）。补测试。

### 3.4 utils 门控 + `pkg info`

- **utils 门控 src_dirs 感知**（`src/pkg.cpp:928`）：现状 `if (cfg.project.type == "utils" && !util::file_exists(dir / "src")) continue;` 硬编码 `src/`。改为对 `cfg.compile.src_dirs` 做存在性检查（任一目录存在且有源文件才编译）。实现建议：try/catch 包裹 `collect_sources(..., require_main=false)`（空 → 抛 → 继续跳过），或轻量目录存在性遍历。
- **`pkg info` 增显 `src_dirs`**：镜像 `include_dirs` 输出块（`src/pkg.cpp:1196-1202`），新增 i18n key `pkg_info_src_dirs`。

## 5 兼容性

| 变更 | 影响 | 处理 |
|------|------|------|
| 包 `[compile].src_dirs` 从「忽略」→「生效」 | 默认 `["src"]` 与现状一致，绝大多数包零影响 | 默认值对齐；多目录/自定义目录为纯新增能力 |
| 空 src 包：warn+空库 → fatal | 仅「非 header_only/precompiled/utils 却无任何源文件」的退化包 | 行为收紧；三种短路前置不变（§3.2），兼容矩阵说明 |
| `collect_sources` 新增 `require_main`（默认 `true`） | 项目路径零变化 | 默认值兼容；包路径显式传 `false` |
| 自编译 `-I` 保序去重 | 消除重复 `-I`（项目+包），编译器语义不变 | 去重保持首次出现顺序 |
| `pkg info` 增显 `src_dirs` 行 | 纯新增输出 | 新增 i18n key |
| utils 门控 src_dirs 感知 | 仅影响「utils 且 src_dirs ≠ 默认」的包 | 语义对齐，默认行为不变 |
| header_only / precompiled / utils 短路 | 无 | 短路逻辑前置，行为逐字节不变 |

## 6 跨版本关注点

- **dev.7 联动**：`pkg install <dir>` 本地目录安装共用 `validate_pkg` + `compile_package`，`src_dirs`/`include_dirs` 修复自动惠及该路径。
- **官方仓库包**：绝大多数用默认 `src/`（= 默认 `src_dirs`）与 `include/`，零影响；无需批量改包。
- **与 export cmake（dev.2）无关**：导出的是项目 config，不导出包配置；包 `src_dirs`/`include_dirs` 不在 export 范围（范围边界，不扩展）。
- **i18n X-macro**：新增 key 走 `i18n_keys.def` + en/zh 双 JSON，`check_i18n.py` 三向一致；空源提示复用现有 `no_source_files`/`src_dir_missing`，不新增同义 key。
- **回归基线**：全量测试零回归（dev.6 后基线 685 用例 / 3194 断言），作为硬门槛。
