# EazyMake 1.2.0-dev.8 — CMake 导出钩子运行时（`ezmk-lua` 独立运行时）

> 本计划并入 1.2.0 正式发布版。发布总览见 [`1.2.0.md`](1.2.0.md)。
>
> **dev.2 的延伸**：dev.2（`ezmk project export cmake`）把 project/compile/link/deps 映射到 CMakeLists.txt，但 `[hooks]` 被丢弃（`export.cpp:387-402` 仅注释 + `message(WARNING)`）。本计划补上钩子映射。

---

## 1 背景

`ezmk.toml` 的 `[hooks]`（`pre_build`/`post_build`/`on_failure`，Lua 脚本，`HooksSection`）在 `ezmk build` 里由沙箱 Lua 运行时执行，CMake 无等价运行时，因此 dev.2 导出时只能「不映射」。结果是：导出的 CMake 构建**不跑钩子后处理**，与 `ezmk build` 行为漂移。

本计划把 EazyMake 的 Lua 运行时抽成一个**独立、无黑白名单**的二进制 `ezmk-lua`，由导出的 CMake 在构建节点调用它执行钩子：

- **`ezmk` 本体不变**：沙箱 + 黑白名单机制原样保留（`run_script` / `push_restricted_globals` / `check_*_permission` 一行不动）。
- **`ezmk-lua` 去黑白名单**：全量 Lua 环境（不建 restricted globals、不查 `[utils.permissions]`），但仍注册同一套 `ezmk.*` API → 现有钩子脚本零改动（沙箱的**超集**）。

定位：dev.2 的**范围收口**，只动导出侧 + 新增一个独立运行时产物，不触碰本体安全模型。

## 3 详细设计

### 3.1 运行时抽取（共享编译单元）

把 Lua state 创建 + `register_api`（`src/lua_api.cpp`）作为**两个二进制共享**的代码，新增一个**无沙箱运行函数**，与沙箱版 `run_script`（`980`）并列、不改它：

```cpp
// src/lua_api.cpp 新增（与沙箱版 run_script 并列，不改后者）
int run_script_unrestricted(lua_State* L, const fs::path& script_path,
                            const std::string& project_root,
                            const std::string& profile,
                            const std::string& output);
```

- 与 `run_script` 的区别只在**入口环境**：不建 sandbox env、不 `push_restricted_globals`、不加载 `[utils.permissions]`；直接 `luaL_loadfile` 后用全量 `_G`（注入 `ezmk` 表）执行。
- `ctx`（`ctx.project_root`/`ctx.profile`/`ctx.output`）沿用现有构建钩子的构造方式，由 CLI 参数填充后传给 `run(ctx)`。
- **沙箱路径零改动**：`run_script` / `push_restricted_globals` / `check_*_permission` 保持不变。

### 3.2 `ezmk-lua` CLI 契约

```
ezmk-lua <hook.lua> --project-root <dir> --profile <name> --output <path>
```

| 项 | 值 |
|---|---|
| 位置参数 | 钩子脚本路径（必填） |
| `--project-root` | 注入 `ctx.project_root` + 设置 `g_project_root`（供 `ezmk.*` 读配置） |
| `--profile` | 注入 `ctx.profile` |
| `--output` | 注入 `ctx.output`（目标产物路径） |
| 入口约定 | 沿用 `run(ctx)`（返回 exit code；未定义 → warn + 跳过），与沙箱钩子一致 |

### 3.3 bindings 与全局状态解耦（关键，不碰本体）

`ezmk.*` 里读配置/项目根的函数依赖 `g_project_root` / `g_config_loaded` / `g_cached_config`（`lua_api.cpp:320-340`）。`ezmk-lua` 的 `main` 在 `register_api` **之前**用 `--project-root` 设置这些全局，使 `ezmk.*` 在无构建上下文下也能工作。

- 只**新增**设置入口，不改 `run_script`/沙箱路径，保证本体不变。
- 无 `--project-root` 时：读配置类 `ezmk.*` 函数降级（返回空 / warn），纯工具函数（`ezmk.info`/`ezmk.warn`/`ezmk.error`/`ezmk.file_read`/`ezmk.file_write`/`ezmk.run`）照常。

### 3.4 `export cmake` 钩子生成（替换 `export.cpp:387-402`）

```cmake
# --- hooks (run via ezmk-lua, EazyMake standalone Lua runtime) ---
find_program(EZMK_LUA ezmk-lua)
if(NOT EZMK_LUA)
    message(WARNING "[hooks] need 'ezmk-lua' on PATH — hook post-processing will not run.")
else()
    add_custom_command(TARGET <name> PRE_BUILD
        COMMAND ${EZMK_LUA} "<pre_build>"
                --project-root ${CMAKE_CURRENT_SOURCE_DIR}
                --output $<TARGET_FILE:<name>>)
    add_custom_command(TARGET <name> POST_BUILD
        COMMAND ${EZMK_LUA} "<post_build>"
                --project-root ${CMAKE_CURRENT_SOURCE_DIR}
                --output $<TARGET_FILE:<name>>)
endif()
# on_failure: CMake 无原生失败钩子 — 保持注释 + 说明（同 dev.2 现状）
```

- `pre_build` → `PRE_BUILD`、`post_build` → `POST_BUILD`；`--profile` 由导出时的 `--profile` 决定（可选内联）。
- `on_failure`：CMake 无原生「构建失败」钩子，保持**不导出 + 注释**（范围边界，与 dev.2 一致）。
- `find_program(ezmk-lua)` 找不到 → 回退 `message(WARNING)`（best-effort，不硬依赖 ezmk 已安装）。

### 3.5 能力面（超集）说明

`ezmk-lua` 是沙箱的超集：钩子可用 `os.execute`/`io`/`dofile` 等，但同一脚本在 `ezmk build`（沙箱）下会失败。**文档约定**：导出到 CMake 的钩子应只用 `ezmk.*` 子集，保证「`ezmk build` 沙箱」与「导出 CMake 无沙箱」两处行为一致。

### 3.7 分发（`ezmk-lua` 随 `ezmk` 一起分发）

`ezmk-lua` 是导出 CMake 项目跑钩子所需的运行时（`find_program(EZMK_LUA ezmk-lua)`），必须随 `ezmk` 进入所有分发渠道，否则导出产物在未单独装 `ezmk-lua` 的机器上会回退「跳过钩子」。各触点：

| 触点 | 变更 |
|------|------|
| `release.yml`（4 平台 job） | `Package` 步骤在 `build/ezmk` 外再拷贝 `build/ezmk-lua`（Windows `ezmk-lua.exe`）进 dist；Windows 另产 standalone `ezmk-lua.exe` + `ezmk-lua.exe.sha256`（供 install.ps1） |
| `install.sh`（源码构建） | `build.sh` 现产 `build/ezmk-lua`，安装块在 `ezmk` 外再 `cp` 安装 `ezmk-lua`（Windows `ezmk-lua.exe`） |
| `install.ps1`（预编译） | 下载 `ezmk.exe` 外再下载/校验/安装 `ezmk-lua.exe`（依赖 release.yml 产 `ezmk-lua.exe.sha256`） |
| winget（`publish/winget/`） | `installer.yaml` 的 `NestedInstallerFiles` 增 `ezmk-lua.exe` + `PortableCommandAlias: ezmk-lua` |
| Homebrew（`publish/homebrew/`） | 公式 `install` 块增 `bin.install "ezmk-lua"`（与 `ezmk`/`_ezmk` 并列） |
| pacman（`publish/arch/PKGBUILD`，见 pre.1） | `package()` 增 `install -Dm755 build/ezmk-lua "$pkgdir/usr/bin/ezmk-lua"` |

> 各渠道的**提交**（winget PR / Homebrew tap 更新）属发布流水线阶段，与 pre.1、1.2.0 发布收口一并执行；**pacman 渠道暂不提交 AUR**（AUR 新账户注册未开放），当前以「仓库内 `publish/arch/PKGBUILD` 自取 + `makepkg -si`」为主，AUR 上传延后。本节只定义「哪些文件要改、改成什么」。

## 6 跨版本关注点

- **dev.2 延伸**：dev.2 §3.1「hooks 不映射」在此收口为「hooks 经 `ezmk-lua` 映射（pre/post）」；dev.2 的 `test_export.cpp`「hooks 注释 + WARNING」用例相应更新。
- **沙箱安全模型不松动**：`ezmk-lua` 是信任边界**之外**的开发者工具，永不接入包安装钩子（`script/preinstall.lua` 等）或 utils 脚本路径——那些仍走本体沙箱。边界体现在「独立二进制」上，而非 flag。
- **bindings 双维护风险**：Lua VM + `register_api` 共享编译单元，避免 `ezmk.*` 在两处漂移；改 bindings 只改一处。
- **2.0.0 窗口**：`ezmk-lua` 为新产物，无破坏性；若未来想调整其 CLI/语义，集中 2.0.0。
- **分发联动**：`ezmk-lua` 分发跨 release.yml / install 脚本 / winget / Homebrew / pacman（pre.1），任一渠道漏配会导致「导出钩子在该渠道回退跳过」；与 pre.1 的 PKGBUILD 联动。
- **回归基线**：全量测试零回归（本体沙箱路径必须零变化，作为硬门槛）。
