# EazyMake 1.2.0-pre.1 — pacman 分发（Arch Linux / MSYS2）

> 发布流水线补充：为 EazyMake 增加 pacman 分发渠道，与 winget（Windows）、Homebrew（macOS/Linux）并列。
> 从 [`1.2.0-dev.7.md`](1.2.0-dev.7.md) 拆分而来——pacman 属发布阶段而非开发子版本。

---

## 1 背景

当前分发只覆盖 winget（Windows）与 Homebrew（macOS/Linux）。Arch Linux / MSYS2 用户只能走 `install.sh`（源码构建），缺少 `pacman` 一条命令安装的体验。`release.yml` 已产出 `ezmk-linux-x64.tar.gz`（**静态链接**的 Linux 二进制 + `_ezmk` zsh 补全），pacman 打包原料现成。

> **发布约束**：AUR 新账户注册尚未开放，本计划**不提交 AUR**。pacman 渠道以「自取 PKGBUILD + `makepkg -si`」为主（用户从仓库拉 `publish/arch/PKGBUILD` 本地构建安装），AUR 上传延后到账户开通后。

## 3 详细设计

### 3.1 `publish/` 目录重组

```
publish/
├── winget/            # 原 manifests/e/ezmk/*.yaml 移入（含 1.1.0/1.1.3 参考 manifest）
├── homebrew/          # 原 homebrew-eazymake/ezmk.rb 移入
└── arch/
    └── PKGBUILD       # 本节新增
```

- 移动后用 `git mv` 保留历史；同步更新引用这些路径的文档（`ezmk-publish` skill §4「相关文件」、README 若提及、记忆 `eazymake-110-release`）。
- 重组是纯目录搬迁，不影响 winget-pkgs / Homebrew tap 的线上提交流程（那些是独立仓库，本地只是参考副本）。

### 3.2 PKGBUILD（源码构建，标准 Arch 实践）

`build.sh` 在 Linux 产出**静态链接**二进制（`LDFLAGS="-static"`），故 `depends` 为空、`makedepends` 仅 `gcc` + `python`：

```bash
pkgname=eazymake
pkgver=1.2.0
pkgrel=1
pkgdesc="A simple C/C++ build tool (GCC/Clang/MSVC)"
arch=('x86_64')
url="https://github.com/3667808244/EazyMake"
license=('MIT')
makedepends=('gcc' 'python')
source=("$pkgname-$pkgver.tar.gz::https://github.com/3667808244/EazyMake/archive/refs/tags/v$pkgver.tar.gz")
sha256sums=('SKIP')          # 首次用 SKIP；稳定后填 gh api releases 的真实 digest

build() {
  cd "EazyMake-$pkgver"
  EZMK_VERSION="$pkgver" bash build.sh
}

package() {
  cd "EazyMake-$pkgver"
  install -Dm755 build/ezmk "$pkgdir/usr/bin/ezmk"
  install -Dm755 build/ezmk-lua "$pkgdir/usr/bin/ezmk-lua"
  install -Dm644 res/ezmk.zsh "$pkgdir/usr/share/zsh/site-functions/_ezmk"
}
```

**设计决策**：
- **源码构建 vs 二进制重打包**：首选源码构建（PKGBUILD 标准形态，`makepkg` 从 git tag 拉源码 + `build.sh` 编译）。备选：`ezmk-linux-x64.tar.gz` 二进制重打包（`-bin` 风格，`source=` 直接指向 Release 资产 + `sha256sums` 用真实 digest）——若源码构建在远端网络受限，用备选。
- **`pkgname`**：`eazymake`（项目名）；安装的二进制名保持 `ezmk`（与 CLI 一致）。
- **`_ezmk` 补全**：安装到 `zsh/site-functions/_ezmk`，与 Homebrew 的 `zsh_completion.install "_ezmk"` 对齐。
- **版本绑定**：`pkgver` 指向 `v1.2.0` 正式 tag——**需在 1.2.0 Release 发布后**，`makepkg` 才能拉到源码做最终验证。

### 3.3 验证流程

1. **本机 MSYS2**：MSYS2 base-devel 自带 `makepkg`，`makepkg -si` 生成并安装；验证 `ezmk version` 输出正确版本、补全文件落位。
2. **远程 Arch Linux**：`ssh ezmk_project@192.168.136.131`，把 PKGBUILD（+ 源码）推上去，`makepkg -si` 或 `makepkg` 仅生成 `.pkg.tar.zst`，验证产物。

### 3.4 发布机制（自取 PKGBUILD + AUR 延后）

- **发布形态**：`publish/arch/PKGBUILD` 随仓库分发，用户**自取**后本地构建安装，不经过 AUR。AUR 新账户注册尚未开放 → **AUR 提交延后**，账户可用后再补。
- **用户安装方式**：
  - **Arch Linux**：`curl -fsSL <raw PKGBUILD> -o PKGBUILD && makepkg -si`（需 `base-devel`）
  - **MSYS2**：MINGW 环境 `makepkg-mingw -si`（或 `makepkg -si`）
- **验证**（无需 AUR 账户）：本机 MSYS2 `makepkg` + 远程 Arch Linux `makepkg`（§3.3）。
- **未来补 AUR**：账户开通后，把 `publish/arch/PKGBUILD` 提交为 AUR 包（`pkgbase=eazymake`），验证流程与本节一致；届时 `ezmk-publish` skill 补 AUR 章节。

## 6 跨版本关注点

- **分发渠道统一收口**：pacman 加入后，分发渠道 = winget（Windows）+ Homebrew（macOS/Linux）+ pacman（Arch Linux/MSYS2），统一在 `publish/` 下管理；`ezmk-publish` skill 应扩展为三渠道总览。
- **依赖 1.2.0 Release**：PKGBUILD 的 `source=` 指向 `v1.2.0` tag，最终验证须在正式 Release 发布后进行；`pkgver` 随版本号手工同步。
- **2.0.0 窗口**：`publish/` 目录迁移、以及任何未来想调整的分发路径/包名，若有破坏性调整集中在 2.0.0，1.2.0 只加不改。
- **与 dev.7 的关系**：pacman 分发与 dev.7（本地包源 + 向上查找）无代码依赖，二者独立推进。
- **与 dev.8 联动**：PKGBUILD 的 `package()` 同时安装 `ezmk-lua`（dev.8 新增的独立运行时），保证 pacman 渠道下导出钩子可用。
- **AUR 发布延后**：AUR 新账户注册尚未开放，当前**不提交 AUR**；pacman 渠道以「仓库内 `publish/arch/PKGBUILD` 自取 + `makepkg -si`」为主。本机 MSYS2 + 远程 Arch Linux 的 `makepkg` 验证**无需 AUR 账户**，不受影响；账户可用后再补 AUR 包。
