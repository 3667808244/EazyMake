# EazyMake 1.2.0-dev.10 — 平台标识符扩展：工具链 + ABI 后缀

> 本计划并入 1.2.0 正式发布版。发布总览见 [`1.2.0.md`](1.2.0.md)。
>
> **承接 `docs/zh|en/package_authoring.md` §3.3 多平台共包**：现有命名 `lib<name>.<os>-<arch>.<ext>` 刻意省略工具链（文档原文"预编译归档不与特定编译器绑定"），这对 C 成立，但对 **C++ 不成立**——GCC/Clang/MSVC 的 ABI 互不兼容，同平台同架构也可能因工具链/ABI 不同而链接失败。本计划把平台标识符扩展为 `os-arch[-compiler][-abi]`，并提供 **ABI 安全的 4 级匹配优先级**。

---

## 1 背景

`package_authoring.md` §3.3 的命名约定（`docs/zh/package_authoring.md:167-193` / `docs/en/package_authoring.md:197-218`）用 `lib<name>.<os>-<arch>.<ext>` 标记预编译产物，并明确写了理由：

> **Why this naming convention?** … The tag is deliberately a simplified `os-arch` — it omits the toolchain because a prebuilt archive is not bound to a specific compiler family …

这个理由对 **C ABI** 成立，但对 **C++ ABI** 不成立。C++ 的 ABI 由「编译器族 + 工具链版本 + 标准库 ABI」共同决定，`<os>-<arch>` 完全无法区分，导致三类真实故障：

1. **编译器族不同**：`libexample.linux-x64.a` 由 GCC 编译，Clang 消费者链接 → libstdc++/libc++ 符号不匹配。
2. **同族不同版本**：GCC 13 编译的 `.a` 给 GCC 11 链接 → 引用了较新 libstdc++ 才有的符号（`std::__cxx11` / 新版本库接口）。
3. **MSVC 工具集不同**：`msvc143`（VS2022）编译的 `.lib` 给 `msvc142`（VS2019）链接 → STL 内部布局/符号差异。

现状实现（`src/pkg.cpp:301-348` `select_precompiled_archive()`）只做**精确 os-arch 匹配 + 裸名回退**，没有工具链维度，也不会对"跨工具链降级"给出任何提示——用户拿到错误 ABI 的库，链接期才炸。

本计划目标：让**包作者**能在 `lib/` 下按工具链/ABI 细分产物，让 **`ezmk` 消费端**按 ABI 安全的优先级选择，并在降级匹配（可能跨工具链）时**显式警告**。

## 3 详细设计

### 3.1 标签生成

#### 3.1.1 编译器标签 `compiler_tag()`

新增函数（`include/ezmk/toolchain.hpp` + `src/toolchain.cpp`）：

```cpp
// 返回 "gcc13" / "clang18" / "msvc143"。解析 tc.version（detect_toolchain 已缓存）。
// GCC:   "g++ (GCC) 13.2.0"        → gcc13
// Clang: "clang version 18.1.8"    → clang18
//        "Apple clang version 15.0.0" → clang15（Apple Clang 版本号与 LLVM 不对齐，见 §6）
// MSVC:  "Microsoft (R) C/C++ Optimizing Compiler Version 19.43.34808 for x64" → msvc143
std::string compiler_tag(const Toolchain& tc);
```

- **GCC / Clang**：解析 `tc.version` 首个数字段（major），拼 `gcc<major>` / `clang<major>`。
- **MSVC**：解析 cl 版本 `19.<minor>.xxxxx` → `_MSC_VER` 等价数 = `1900 + minor`，再按工具集映射表折算：

  | `_MSC_VER` 范围 | VS 版本 | 工具集标签 |
  |-----------------|---------|-----------|
  | `1900`          | VS 2015 | `msvc140` |
  | `1910 – 1919`   | VS 2017 | `msvc141` |
  | `1920 – 1929`   | VS 2019 | `msvc142` |
  | `≥ 1930`        | VS 2022 及以后 | `msvc143` |

  > MSVC 在 VS2022 各 17.x 内维持 v143 工具集二进制兼容，故 `≥1930` 一律收束为 `143`（用查表，不用算术：`1943→143` 若按 `140+(1943-1900)/10` 会错算成 `144`）。

#### 3.1.2 ABI 标签

消费端 ABI 标签由**工具链默认值**决定（零子进程、零配置）：

| 工具链 | ABI 标签 | 理由 |
|--------|----------|------|
| GCC（libstdc++ 默认） | `abi11` | libstdc++ ≥5 默认 `_GLIBCXX_USE_CXX11_ABI=1`（CXX11 ABI） |
| Clang + libstdc++（Linux 默认 / `-stdlib=libstdc++`） | `abi11` | 同上 |
| Clang + libc++（`-stdlib=libc++`） | （无） | libc++ 维持 ABI 稳定 |
| MSVC | （无） | ABI 由工具集（§3.1.1）决定 |

> **覆盖场景（P2 延后，文档注明）**：消费端显式 `-D_GLIBCXX_USE_CXX11_ABI=0`（旧 ABI）构建时，本版不做自动探测；包作者可为该场景单独命名 `abi8` 产物，`ezmk` 默认按 `abi11` 匹配（该 `abi8` 文件仅能经 os-arch 降级路径被选中并触发警告）。

#### 3.1.3 完整标签

`select_precompiled_archive()` 内部合成消费端完整标签（`os-arch[-compiler][-abi]`）：

```
detect_platform_tag()      → "linux-x64"            （既有函数，保持不变）
compiler_tag(detect_toolchain()) → "gcc13"
→ 完整标签 = "linux-x64-gcc13-abi11"
```

- `detect_platform_tag()`（`src/util.cpp:335`）**不改**——它还被 `src/repo.cpp:300`（index.toml `[[packages]].platform` 过滤）与 `src/build.cpp:1419`（pack 的 verbose 元数据）使用，这两处属于**源码包分发**维度，不涉及 C++ ABI，保持 os-arch 即可。

### 3.2 `select_precompiled_archive()` 4 级匹配

现状（`src/pkg.cpp:301-348`）：精确 os-arch 相等即返回，否则裸名，否则报错。改为**分段解析 + 打分**：

```cpp
// 每个候选文件 lib<name>.<rest>.<ext> 的 <rest> 解析为组件：
//   os/arch        固定前缀，取自既有表格（win/linux/mac × x64/arm64/x86）
//   compiler       段形如 gcc\d+ / clang\d+ / msvc14\d
//   abi            段形如 abi\d+
//   其余未知段     不识别 → 视为非本命名体系（不匹配，仅列入 available 报告）

评分（数值越高越优先）：
  L4  os+arch+compiler+abi 全部相等            → 4
  L3  os+arch+compiler 相等，且 abi 缺失       → 3   （同编译器 = 同默认 ABI，安全）
  L2  os+arch 相等，compiler/abi 均缺失        → 2
  L1  裸名 lib<name>.a / lib<name>.lib        → 1

特例：compiler 相等但 abi 段存在且不相等（如 gcc11-abi8 对 gcc11-abi11）
  → 视为 ABI 不兼容，跳过（不得落入 L3；若仅此一个候选则报错——ABI 不匹配本就该失败）
同分取 filename 字典序最小者（确定性，不依赖目录迭代顺序）。
```

**降级警告**：当选中 L2 / L1（消费端带 compiler 标签却落到 os-arch/裸名）时，输出 i18n 警告，指明当前工具链标签与可用产物：

```
[ezmk] warning: precompiled package 'example' has no build for toolchain
       'gcc13' — falling back to 'libexample.linux-x64.a' (may be ABI-incompatible)
       available: linux-x64-gcc13-abi11, linux-x64-gcc11-abi11, linux-x64
```

**严格模式**（`[project].precompiled_strict = true`，P1）：L2/L1 降级改为致命错误（`precompiled_strict_mismatch`），fail-fast——官方仓库的包可借此强制"没匹配工具链就拒绝链接"。

**报错增强**：无任何匹配时，错误信息补上当前完整标签（`linux-x64-gcc13-abi11`）+ available 列表（现状 `src/pkg.cpp:338-347` 已有 available，补完整标签即可）。

### 3.3 `pkg info` 增显（P1）

## 6 跨版本关注点

- **dev.9 联动**：dev.9 收口包 `[compile].src_dirs`/`include_dirs`，dev.10 面向 `precompiled` 包的 `lib/` 选择路径，二者同属包配置收敛，互不重叠；共享回归基线（dev.12 后 727 用例 / 3361 断言）。
- **pre.2 联动**：dev.10 的命名约定与 ABI 警告是 pre.2「加强预编译包跨工具链兼容性警告 + 声明最佳实践」的**实现前提**——pre.2 文档直接引用本计划的 `os-arch[-compiler][-abi]` 命名与 4 级优先级。
- **repo index `os_arch_toolchain` 三元组（`src/repo.cpp:227`）**：现有机制只区分编译器**族**（`windows_x86_64_msvc`），用于源码包分发过滤，与 `lib/` 文件级 ABI 匹配是两套系统。本版**不合并**；未来如需版本化工具链三元组，归 2.0.0 窗口。
- **Apple Clang 版本号**：Apple Clang（`clang15` 等）与 LLVM Clang 版本号不对齐，且同一 major 内部也可能 ABI 变——文档注明该局限，精确 full 匹配仍可用。
- **clang-cl（MSVC ABI）**：`clang<major>` 处理，不生成 `msvc1xx` 标签——需 MSVC ABI 时用真 MSVC 构建该产物；文档注明（避免过度工程）。
- **`_GLIBCXX_USE_CXX11_ABI=0` 覆盖**：P2 延后项，文档注明包作者可为旧 ABI 单独命名 `abi8` 产物。
- **i18n X-macro**：新增 key 走 `i18n_keys.def` + en/zh 双 JSON，`check_i18n.py` 三向一致。
- **回归基线**：全量测试零回归作为硬门槛。
