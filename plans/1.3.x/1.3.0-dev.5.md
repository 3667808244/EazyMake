# EazyMake 1.3.0-dev.5 — 依赖构建产物的命令一律总是自动构建

> 1.3.0 第五个开发子版本。总览见 [`1.3.x/README.md`](README.md)，正式版设计见 [`1.3.0.md`](1.3.0.md)。

---

## 1 背景

当前「消费构建产物」的命令对构建的触发**策略不一致**：

| 命令 | 当前行为 | 问题 |
|------|---------|------|
| `ezmk run` / `project run` | **总是**先 `build_project` 再运行 | — |
| `ezmk project install` | **总是**先 `build_project` 再安装 | — |
| `ezmk project watch` | **总是**构建（首轮 + 变更重建） | — |
| `ezmk test` / `project test` | **产物存在才不构建**（`check_built()` 只查存在性，不比较时间戳） | 源码改过但旧产物还在 → `ezmk test` 直接复用旧 `.o` 链接测试，**测试跑的不是最新代码** |
| `ezmk project pack --precompiled` | **产物缺失才构建**（存在则直接打包） | 源码改过但旧 `lib<a>.a` 还在 → 打包的是**过期产物** |

`test` 与 `pack --precompiled` 的「存在性门控」是**陈旧产物陷阱**：用户改了源码后直接 `ezmk test` / `ezmk project pack --precompiled`，得到的是基于旧代码的结果，且**没有任何提示**。run/install 之所以没这个问题，是因为它们无条件走 `build_project`（增量缓存保证产物新鲜时开销趋近于零）。

## 2 目标

| # | 目标 | 优先级 |
|---|------|--------|
| 1 | `ezmk test`：移除 `check_built()` 存在性门控，**总是**先 `build_project`（增量）再收集/编译/运行测试 | P0 |
| 2 | `ezmk project pack --precompiled`：**总是**先 `build_project`（增量）再打包预编译产物 | P0 |
| 3 | 统一所有消费构建产物命令的语义：**先增量构建，保证产物新鲜，再消费** | P0 |
| 4 | 存量测试回归：新增「改源码后直接 test/pack 用新产物」断言（锁定陈旧产物陷阱修复） | P0 |
| 5 | 行为变更在 CHANGES.md 明确记录（test/pack 现在总是构建，增量缓存保证开销可忽略） | P1 |

## 3 详细设计

### 3.1 `ezmk test`：总是构建

`src/build.cpp` `run_tests()` 当前逻辑（1.2.0-dev.7 起）：

```cpp
bool project_built = false;
auto check_built = [&]() -> bool { /* 只查 exe/lib/so 存在性 */ };
if (!check_built()) {
    util::info("project not built — building first...");
    cli::BuildOptions build_opts;
    build_opts.jobs = 0;
    try { build_project(cfg, build_opts); project_built = true; }
    catch (...) { util::fatal("project build failed, cannot run tests: ..."); }
}
```

改为**无条件构建**：

```cpp
// 1.3.0-dev.5: 总是先构建（增量缓存保证新鲜产物时开销趋近于零），
// 消除「改源码后旧产物仍在 → 测试跑旧代码」的陈旧产物陷阱。
util::info("building project before tests...");
cli::BuildOptions build_opts;
build_opts.jobs = 0;
try {
    build_project(cfg, build_opts);
} catch (const std::exception& e) {
    util::fatal(std::string("project build failed, cannot run tests: ") + e.what());
}
```

- **保留** `cfg.project.type == "utils"` 例外：utils（Lua 工具包）无编译产物，`build_project` 对 utils 本身是无害空跑（构建收集不到源码、不产出物），但为保持「无产物可构建」语义，utils 类型可跳过构建提示直接进测试收集（现状 `check_built` 对 utils 恒返回 true）
  - 决策：**utils 类型仍跳过 build_project**（与现状一致，避免无意义输出）；其余类型一律构建
- **增量保证**：`build_project` 走缓存——产物新鲜时仅打印 `building` 信息行 + 秒过，不重编译
- `project_built` 变量与 `check_built()` lambda 整体删除；`build_project` 返回值/副作用不变

### 3.2 `ezmk project pack --precompiled`：总是构建

`src/build.cpp` `pack_project()` 当前逻辑（1.2.5）：

```cpp
auto archive_path = project_artifact_paths(...).primary;
if (!util::file_exists(archive_path)) {
    util::info("building project before packing...");
    cli::BuildOptions build_opts;
    build_opts.jobs = 0;
    build_project(cfg, build_opts);
    if (!util::file_exists(archive_path)) {
        util::fatal("build did not produce ... — cannot pack");
    }
}
```

改为**无条件构建**（保留产物复核）：

```cpp
// 1.3.0-dev.5: 总是先构建（增量），保证预编译包产物新鲜；
// 打包前复核产物存在，构建异常不静默打包过期产物。
util::info("building project before packing...");
cli::BuildOptions build_opts;
build_opts.jobs = 0;
build_project(cfg, build_opts);
if (!util::file_exists(archive_path)) {
    util::fatal("build did not produce " + archive_path.filename().string() +
                " — cannot pack");
}
```

- **源码包（默认，非 `--precompiled`）不变**：仍不构建（平台无关、消费者侧编译，打包 `src/`+`include/`+`ezmk.toml` 与产物无关）
- 类型校验不变（`--precompiled` 仅 `static`）

### 3.3 语义统一

所有**消费构建产物**的命令统一为：**先 `build_project`（增量）→ 产物新鲜 → 消费**。

| 命令 | 1.3.0-dev.5 前 | 1.3.0-dev.5 后 |
|------|----------------|----------------|
| run | 总是构建 | 不变 |
| install | 总是构建 | 不变 |
| watch | 总是构建 | 不变 |
| test | 产物存在跳过 | **总是构建**（utils 除外） |
| pack --precompiled | 产物存在跳过 | **总是构建** |
| pack（源码包） | 不构建 | 不变 |
| cc / export / import / clean | 不构建（元数据/反向/清理，不消费产物） | 不变 |

### 3.4 与既有代码的边界

- **改动**：`src/build.cpp` 仅两处——`run_tests()` 移除存在性门控改无条件构建（utils 例外保留）；`pack_project()` `--precompiled` 分支移除存在性门控改无条件构建（复核保留）
- **零改动**：`main.cpp`（run/install/watch 路径不动）、`cli.cpp`、缓存/增量逻辑、`compile_db`/`export`/`import`/`clean`
- **行为变更**（非破坏）：`ezmk test` 与 `ezmk project pack --precompiled` 在产物已存在时**也会执行一次增量构建**——产物新鲜则仅打印一行 + 秒过；产物过期则自动重建。这是修复而非回归
- **无新 CLI/配置/文件**：纯行为收敛，公共 API 无破坏性变更

## 6 跨版本关注点

- **与 dev.1 ~ dev.4 解耦**：workspace 的 `workspace test`（dev.2/dev.3）逐成员透传单项目 `ezmk test`，本版让成员测试也获得「总是构建」语义（成员内 `ezmk test` 现走同一 `run_tests`），无需额外联动。
- **增量开销**：`build_project` 的缓存命中路径已是最小化（读取 record.json + 比对签名）；多次调用（如 workspace 逐成员）不会放大为全量重编。
- **测试锁定**：陈旧产物陷阱的回归用例（改源码 → test/pack 用新产物）是核心验收，防止未来有人「优化」回存在性门控。
- **后续窗口**：`check_built` 的「产物新鲜度校验」如未来需要（比较时间戳而非存在性），归 2.0.0 或后续评估——本版采用最简「总是构建」语义，不引入时间戳比较的复杂度。
