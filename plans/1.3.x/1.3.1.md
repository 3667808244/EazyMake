# EazyMake 1.3.1 — 区间语言标准与包/消费者标准兼容校验

> 1.3.0 正式发布后的**补丁版本**。发布总览见 [`1.3.x/README.md`](README.md)。

---

## 1 背景

`[project].language` 目前只接受**精确标准**（`<语言><版本>`，如 `C++17`、`C11`、`GNUCPP17`）：`config::parse_language()`（[`src/config.cpp`](../../src/config.cpp) `:230-327`）把字符串直接映射到**唯一一个** `-std=` 标志，无任何区间/约束语法。三个实际诉求无法表达：

1. **库作者声明"最低兼容标准"**：如"本库兼容 >= C++11"（基础接口 C++11、拓展接口 C++17——头文件用 `#if __cplusplus` 条件编译实现）。目前只能写精确值 `C++11`，且**没有语义区分**"编译用 C++11"与"最低要求 C++11"。
2. **包与消费者之间无标准匹配校验**：`compile_package()`（[`src/pkg.cpp`](../../src/pkg.cpp) `:638`）拿包自己的 `language` 独立编译，消费者项目拿自己的 `language` 编译（[`src/build.cpp`](../../src/build.cpp) `:602`），两者从不比较。预编译库的 ABI 断裂风险（`std::__cxx11` 未定义引用，见 [1.2.0-dev.10](../1.2.x/1.2.0-dev.10.md)）在语言标准维度上没有门禁。
3. **"区间"的语义歧义**：≥ 下限、≤ 上限、还是"编译器支持多高用多高"（CMake `CXX_STANDARD` 语义）？需要定死一个可落地的语义。

**语义定死为 A（元数据 + 校验）**：区间只表达**最低要求**（可选上界仅作元数据），编译仍用单一精确标准（取 min）。"编译协商"（按消费者标准重编包）与"工具链能力表"（编译器支持的最高标准）语义 B/C 预留 **1.4.0**，本版不做（见 §6）。

## 3 详细设计

### 3.1 语法

| 用户输入 | 解析结果 | 生效 `-std=` |
|----------|----------|-------------|
| `C++11`（现状） | min=11, max=0（无区间） | `-std=c++11` |
| `>=C++11` / `>=CPP11` | min=11, max=0 | `-std=c++11` |
| `C++11..C++17` | min=11, max=17 | `-std=c++11` |
| `>=GNUCPP11` | min=11, max=0, gnu | `-std=gnu++11` |
| `C`（无版本） | min=11（默认 C11） | `-std=c11` |

- 约束符号复用 `[depends]` 已有的版本约束语法（[`src/config.cpp`](../../src/config.cpp) `:104-125` 的 ops 表 + 最早位置扫描思路）：`>=` = 单边下界；`..` = 双边区间（新符号，需加入扫描）；**不引入 `+` 后缀**（语法面最小）。
- **约束剥离在 GNU 前缀识别之前**（[`src/config.cpp`](../../src/config.cpp) `:261`）：`>=GNUCPP11` → 剥离 `>=` → 剩 `GNUCPP11` → 走原逻辑，GNU 组合自然支持。
- `normalize_lang()`（`:193-208`）只做大写/trim，`>=` 与 `..` 不受影响。
- **非法形式拒绝**（新增 i18n key，见 §3.7）：`C++17..C++11`（max < min）、`>C++11`（不支持 `>`）、`C++11+`（不支持）；`>=C`（无版本 → 默认 11）**允许**，等价 `>=C11`。

### 3.2 LanguageInfo 扩展与 parse_language 改造

[`include/ezmk/config.hpp`](../../include/ezmk/config.hpp) `:190-196`：

```cpp
struct LanguageInfo {
    std::string compiler;
    std::string std_flag;            // 语义变为"生效标志"：区间取 min
    std::string detected_compiler;
    bool gnu_extensions = false;
    std::string normalized_lang;     // 区间时取 min 规范形（"CPP11"），不进区间串
    int min_ver = 0;                 // 1.3.1：解析出的下界（0 = 未声明）
    int max_ver = 0;                 // 1.3.1：上界（0 = 无上界）
};
```

- `parse_language()`（`src/config.cpp:230-327`）新流程：`normalize_lang()` → **约束剥离**（`>=` / `..`，拆 min/max）→ C++/CXX→CPP 替换 → GNU 前缀剥离 → `CPP<Ver>`/`C<Ver>` 解析（版本缺失默认 C++17/C11，`:286-290`）→ ver_map 校验（`:293-297`）→ 生成 `std_flag`（**取 min**）+ 回填 `min_ver`/`max_ver`。
- `normalized_lang` 区间时返回 **min 的规范形**（`">=C++11"` → `"CPP11"`）——`EZMK_LANG` 宏（[`src/build.cpp`](../../src/build.cpp) `:101-106`）的值对精确与区间写法定点不变（坑 2）。
- **max 不参与缓存签名**（[`src/cache.cpp`](../../src/cache.cpp) `compile_options_signature` `:201-211` 已按 `std_flag` 哈希）：改 max 只是元数据变更，不应触发全量重建；min 变化 → 生效标志变 → 签名变 → 自动失效。零代码改动，语义确认 + 测试锁定即可（坑 3）。

### 3.3 编译注入与缓存（零改动 ✅）

- [`src/cache.cpp`](../../src/cache.cpp) `build_compile_args()` `:402-470`：只要 `LanguageInfo.std_flag` 仍是单一具体标志，`:442` 的 `args.push_back(in.lang.std_flag)` 与 MSVC 翻译表（[`src/toolchain.cpp`](../../src/toolchain.cpp) `:29-41`）**零改动**。
- `compile_package()`（`src/pkg.cpp:638`）与 `prepare_build_state()`（`src/build.cpp:602`）调用点签名不变，仅 `LanguageInfo` 多两个字段。

### 3.4 安装期标准兼容校验（核心新逻辑）

**方向**：`包.min_ver > 消费者.min_ver` → 警告（如 `package 'x' requires at least C++17, but this project compiles at C++11 — the package may fail to compile or link`）。源码包与预编译包**统一警告**（信息性不 fail，避免破坏现有包生态；严格化开关预留 1.4.0）。

**实现**（`src/pkg.cpp` 新增两个 helper + 两处调用）：

1. `int std_min_of(const std::string& language)` —— `parse_language(language).min_ver`（无区间 = 精确值）。
2. `std::optional<int> consumer_std_min()` —— `util::locate_project_root()`（`pkg.cpp:1262/1366` 已有调用模式）→ `config::parse_config(proj_root / "ezmk.toml")` → `project.language` 的 min；无 ezmk.toml（全局/用户级安装）→ `nullopt` 跳过校验。
3. 调用点：
   - `compile_package()`（`src/pkg.cpp:638`）开头：编译源码包前校验；
   - `select_precompiled_archive()`（`src/pkg.cpp:605`）开头：预编译包选择前校验（ABI 风险更高，警告措辞加强，复用 1.2.0-dev.10 的 ABI 警告风格）。

**容错**：消费者 `ezmk.toml` 存在但 `language` 非法 → 警告并跳过（不阻断安装）。

### 3.5 CMake 导出修复（坑 1）

[`src/export.cpp`](../../src/export.cpp) `:257-259` 的兜底逻辑：

```cpp
if (std_num == 0) {
    for (char c : lang.normalized_lang)        // "CPP11..CPP17" → 数字 "1117"
        if (c >= '0' && c <= '9') std_num = std_num * 10 + (c - '0');  // → 1117
}
```

- 改为直接读 `lang.min_ver`（`std_num = lang.min_ver`），彻底消除裸数字提取。
- 语义映射：EazyMake min → CMake `CXX_STANDARD <min>`（CMake 语义恰好是"至少 N"，天然对齐）。

### 3.6 导入器（延后，不蔓延）

[`src/import.cpp`](../../src/import.cpp) `:446-447` 目前对 CMake `LANGUAGES CXX` 硬编码 `C++17`，且轻量解析器不读 `CXX_STANDARD`。CMake `CXX_STANDARD`（"至少 N"语义）→ 区间映射**归 1.4.0**（与能力表同批），本版不改，避免范围蔓延。

## 6 跨版本关注点

- **1.4.0 预留（本版不写 1.4.0 文档，仅登记范围）**：
  - **工具链能力表**：`toolchain.cpp` 新增 `max_supported_std(family, version)`（MSVC 已有 `_MSC_VER` 分段先例 `:504-506`），为语义 C（"编译器支持多高用多高"，CMake `CXX_STANDARD` 式）铺路；
  - **编译协商（语义 B）**：包按 `max(包min, 消费者标准)` 编译——需把消费者标准传入 `compile_package`，打破"包独立编译"模型与共享缓存语义，工程量大，独立版本推进；
  - **严格化开关**：标准校验 warn → error 可配；
  - **import.cpp `CXX_STANDARD` 映射**（`src/import.cpp:446-447` 硬编码 C++17 一并处理）。
- **与 2.0.0 解耦**：本版纯增量，不依赖任何 deprecation 到期；2.0.0 保持破坏性变更窗口。
- **回归基线**：全量 863 用例 / 5007 断言（1.3.0-dev.5 后基线），新增功能不得引入回归。
- **i18n**：新增 key 三向一致（`.def` + en/zh JSON + 重新生成 `locale_data.cpp`），`check_i18n.py` 通过。
- **与 1.2.0-dev.10 ABI 体系的关系**：标准兼容校验与 `os-arch-compiler-abi` 平台标识互补——前者管"语言标准维度"，后者管"工具链/ABI 维度"；未来可考虑标准进 abi 标签（1.4.0 评估）。
- **后续窗口**：`+` 后缀别名、双边区间的"验证到 max"（CI 矩阵式多标准编译验证）、header-only 包的标准声明——归 1.4.0 或后续评估。
