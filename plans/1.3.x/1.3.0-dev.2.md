## 1 背景

dev.1 完成 workspace 配置解析、根定位与成员/依赖校验。本版实现**构建命令组**与**成员依赖图的执行**：Kahn 拓扑分层 + 层内并行 + 子进程按成员执行 + 头文件/静态库产物注入，让「共享基础库 + 多个可执行文件」的 monorepo 一次命令全量构建、增量语义正确。

## 3 详细设计

### 3.1 命令组（`Command::WorkspaceList / WorkspaceBuild / WorkspaceTest / WorkspaceClean`）

- `ezmk workspace list`：打印根路径、名称、每成员 `name / type / ws_deps`（校验结果；invalid 成员标 `(invalid: <原因>)`）
- `ezmk workspace build [-j N] [--stop-on-error] [--member <name>...]`：定位 → 校验 → 拓扑执行
- `ezmk workspace test  [-j N] [--stop-on-error] [--member <name>...]`：同 build，逐成员透传 `[test-opts]`；无测试的成员跳过（不报错）
- `ezmk workspace clean`：按拓扑逆序对每成员执行 `ezmk clean`
- **`--member <name>`**：只对指定成员（及**其依赖闭包**，依赖按拓扑先构建）执行；名称 = 成员路径末段或完整相对路径；未知成员 → fatal
- **触发方式**：
  1. workspace 根内任意子目录：`ezmk workspace build`（`locate_workspace_root` 自动定位）
  2. 项目目录内：`ezmk build -w`（在项目正常构建**之外**再触发一次 workspace 全量构建）
  3. workspace 根：`ezmk build -w`（根本身是项目时可二者兼得；根非项目时 `-w` 仅做 workspace 构建）

### 3.2 拓扑分层（`include/ezmk/workspace.hpp` 扩展）

```cpp
// Kahn 算法：返回层列表（每层为并列可并行成员）
std::vector<std::vector<size_t>> topo_layers(const Workspace& ws);
// 失败：环已在 dev.1 validate_ws_deps 拒绝；此处仅作防御断言
```

- 节点 = 校验通过的成员；边 = `ws_deps`（已被 dev.1 解析为成员索引）
- 入度 0 成员入第 0 层；剥除后新入度 0 入下一层……（同层内互相无依赖，可并行）
- 依赖顺序保证：被依赖成员的层号严格小于依赖者层号

### 3.3 子进程执行（`src/workspace_build.cpp`）

- 每成员一个子进程：`<ezmk 可执行路径> build --cwd <member> --no-workspace`
  - `--no-workspace`：防止嵌套触发 `locate_workspace_root`（成员构建保持单项目语义）
  - 复用 `util::run_command`/现有子进程工具；继承环境变量
- 层内并行：`util::ThreadPool`（worker 数 = `-j`/`default_jobs`/`hardware_concurrency`），每任务一个子进程
- `stop_on_error`：失败 → 该层等待在跑成员结束后终止，退出码非 0，摘要打印失败成员与原因

### 3.4 产物注入

**注入机制**：通过环境变量把依赖信息传给成员子进程（**不**改写成员 `ezmk.toml`，保证既有项目文件零变更）：

```
EZK_WS_ROOT=<ws 根>
EZK_WS_DEPS=<m1>;<m2>;...   # 该成员的直接 [depends] workspace 引用（basename）
```

成员构建进程（`build.cpp`）启动时读取这两个环境变量：

1. `EZK_WS_DEPS` 非空时，对每个依赖 `m` 自动追加：
   - `-I <ws>/<m>/include`（若该目录存在）
   - `-L <ws>/<m>/build -l<m>`（若 `build/lib<m>.a` 存在）
2. 注入发生在**编译参数签名之前**（见 3.5 增量语义）：签名含注入参数，依赖库参数变化 → 依赖者自动重编
3. 注入的 `-I` 优先级**低于**成员自身 `include_dirs`、**高于**系统路径

**为什么用环境变量而非改配置**：① 成员 `ezmk.toml` 保持与单项目构建完全一致（工作区是"外面套的一层"）；② 无需解析/合并 TOML，无写入冲突；③ 依赖声明集中在 workspace 层（成员 `[depends] workspace` 只写名字，路径由注入器统一拼装）。

### 3.5 增量语义

| 事件 | 效果 | 机制 |
|------|------|------|
| 依赖库 `.cpp` 变 → 库重编 | 库 `build/lib<m>.a` 时间戳/内容变 | 子进程自身增量（成员构建即单项目构建） |
| 库产物变 → 依赖者 | 依赖者**重新链接** | 链接阶段比较 `lib<m>.a` 时间戳 |
| 库 `.h` 变 | 依赖者**重新编译**该头引用翻译单元 | 依赖者 depfile 含 `<ws>/<m>/include` 头文件（注入 `-I` 进入预处理器，`-MD` 自动收录） |
| 库头文件变 | 依赖者编译参数签名不变 | 签名不哈希头文件内容——依赖者重编由 depfile 头哈希驱动（与单项目一致） |

- 签名：`compile_options_signature` 计算时已含注入的 `-I/-L/-l`（注入参数改变 → 签名变 → 全量重编该成员）
- **正确性保证**：依赖者重编/重链都由依赖库的**产物/头文件**驱动，不依赖用户手动 `clean`

### 3.6 与既有代码的边界

- **build.cpp 微扩**：启动时读 `EZK_WS_*` 环境变量追加注入参数（默认无 → 零影响）；其余构建逻辑**零改动**
- **新增**：`src/workspace_build.cpp`（子进程编排 + 摘要打印）、`workspace.hpp` 的 `topo_layers`
- **既有命令零改动**：`ezmk build`（无 `-w`）行为完全不变；`ezmk clean` 同理
