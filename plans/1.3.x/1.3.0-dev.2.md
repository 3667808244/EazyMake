## 1 背景

dev.1 交付了 `ezmk-workspace.toml` 解析与成员校验（`Workspace` 结构）。dev.2 把它变成**可执行命令**：顶层 `ezmk workspace` 命令组（`list` / `build` / `test` / `clean`），跨成员**并行调度**（子进程模型）并汇总结果。

## 3 详细设计

### 3.1 CLI（`include/ezmk/cli.hpp` + `src/cli.cpp`）

```cpp
enum class Command { ..., Workspace, ... };   // 1.3.0

struct WorkspaceOptions {
    std::string action;                 // "list" | "build" | "test" | "clean"
    std::vector<std::string> members;   // --member <name>（可多次；空 = 全部）
    bool stop_on_error = false;         // --stop-on-error
    int jobs = 0;                       // -j（0 = 用 workspace options.default_jobs）
    // build/test 透传：复用 BuildOptions / test 选项
    BuildOptions build_opts;
    std::string test_framework, test_filter; bool test_verbose; std::string test_profile;
};
```

- 解析仿 `project` 组（`parse_options(argc, argv, 3, spec, "ezmk workspace")`）：
  - `ezmk workspace` / `ezmk workspace list` → list（无子命令 = list，同 `example` 惯例）
  - `ezmk workspace build [build-opts]` / `test [test-opts]` / `clean`
  - 未知子命令 → fatal（列出可用 action）
- **顶层 `ezmk build` 纯容器根提示**：`cli.cpp` 或 `main.cpp` 在 `ProjectBuild` 分发前检查——cwd（或向上 5 层）存在 `ezmk-workspace.toml` 且无 `ezmk.toml` → `util::info("workspace root detected — use 'ezmk workspace build'")` 后按原样走（会因找不到 `ezmk.toml` 报既有错误）？**不**——更好：直接 fatal 提示，避免误导性报错。有 `ezmk.toml` 则行为不变。

### 3.2 执行器（`src/workspace.cpp`）

```cpp
namespace ezmk::workspace {
int run_workspace(const cli::WorkspaceOptions& opts);   // main.cpp 分发
}
```

**子进程模型**（关键决策）：
- 对每个成员，构造命令 `<当前ezmk可执行文件> <action> [透传选项]`，在**成员目录**执行
- 复用 `util::run_command`；工作目录：若 `RunOptions` 支持 `cwd` 则直接指定，否则 `cd <dir> && <ezmk> ...`（与 `test_integration::build_ezmk_cmd` 同思路）
- **为什么子进程而非线程**：cwd 是进程级全局（线程内 `fs::current_path` 切换互踩）、Lua 状态/缓存/日志等内部状态非线程安全；子进程天然隔离且复用全部单项目逻辑（增量缓存、测试缓存、`[hooks]`、`--profile` 等零改动）

**并行调度**：
- 复用 `util::ThreadPool`（`include/ezmk/thread_pool.hpp`）：并发度 = `-j`（显式）或 `default_jobs`（workspace 配置，0 → `hardware_concurrency`）
- 每成员一个 task：`run_command` 捕获 stdout/stderr → 加 `[member] ` 前缀 → 收集结果
- 线程安全：任务间零共享（各自进程）；结果汇总用互斥锁

**汇总与退出码**：

```
[workspace] Building 3 members (-j 2)...
  ✓ apps/tool-a      (2.1s)
  ✗ apps/tool-b      (0.4s) — exit 1（见下方输出）
  ✓ libs/strutil     (1.8s)
[workspace] 2 succeeded, 1 failed
```

- 每成员失败详情（stderr 尾部若干行）在汇总后打印
- 默认继续执行全部；`--stop-on-error` 首批并发完成后，剩余成员标记 `skipped`
- 任一失败 → 返回非零；全成功 → 0
- `clean` 默认串行（无并行收益）+ `-j` 忽略（可并行但没必要）

**`--member <name>`**：名称匹配 = 成员相对路径（`apps/tool-a`）或其末段（`tool-a`）；未知名称 → fatal；空结果（全过滤）→ 提示无成员。

**`list`**：

```
[workspace] my-workspace — 3 members
  ✓ apps/tool-a      (executable)
  ✓ libs/strutil     (static)
  ✗ tests/e2e        (invalid: missing ezmk.toml)
```

## 6 跨版本关注点

- **dev.3 依赖本版**：集成测试覆盖命令行为。
- **子进程模型的可移植性**：`cd <dir> && <exe>` 命令串在 Windows（`cmd /c`）与 POSIX（`sh -c`）均可用——与 `test_integration::build_ezmk_cmd` 的既有做法一致；优先用 `RunOptions.cwd`（若存在）消除转义风险。
- **并行上限**：并发成员数 ≤ `hardware_concurrency`；成员内 `-j` 由透传选项控制（默认各自 auto，总负载由成员数 × 成员内并行约束）。
