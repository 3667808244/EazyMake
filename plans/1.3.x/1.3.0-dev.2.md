# EazyMake 1.3.0-dev.2 — workspace 构建命令与并行

> 1.3.0 第二个开发子版本。总览见 [`1.3.x/README.md`](README.md)，正式版设计见 [`1.3.0.md`](1.3.0.md)。

---

## 1 背景

dev.1 完成 workspace 配置解析、根定位与成员/依赖校验。本版实现**构建命令组**与**成员依赖图的执行**：Kahn 拓扑分层 + 层内并行 + 子进程按成员执行 + **成员自发现注入**（无环境变量）+ 命令行长度兜底（响应文件），让「共享基础库 + 多个可执行文件」的 monorepo 一次命令全量构建、增量语义正确、大型项目不炸。

## 3 详细设计

### 3.1 命令组（`Command::WorkspaceList / WorkspaceBuild / WorkspaceTest / WorkspaceClean`）

- `ezmk workspace list`：打印根路径、名称、每成员 `name / type / ws_deps`（校验结果；invalid 成员标 `(invalid: <原因>)`）
- `ezmk workspace build [-j N] [--stop-on-error] [--member <name>...]`：定位 → 校验 → 拓扑执行
- `ezmk workspace test  [-j N] [--stop-on-error] [--member <name>...]`：同 build，逐成员透传 `[test-opts]`；无测试的成员跳过（不报错）
- `ezmk workspace clean`：按拓扑逆序对每成员执行 `ezmk clean`
- **`--member <name>`**：只对指定成员执行（**含其依赖闭包**：依赖成员按拓扑先构建，保证产物新鲜）；名称 = 成员路径末段或完整相对路径；未知成员 → fatal
  - 只想构建**单个成员、不构建闭包**（接受兄弟产物可能已过期）→ `cd <member> && ezmk build`：成员内本地构建，仅注入**已存在**的兄弟产物，不触发闭包构建
- **`-w` / `--workspace`**（附在 `build/test/clean` 上）：把该命令**重定向**到 workspace 命令组——`ezmk build -w` ≡ `ezmk workspace build`（自动向上定位 workspace 根，从根内任意子目录可用）
  - **不是**「项目 + workspace 都构建」，也**不改变**成员内 `ezmk build` 的单项目语义（无 `-w` 时只构建当前成员 + 注入已存在兄弟产物）
  - 纯容器根（仅 workspace 文件、无 `ezmk.toml`）`ezmk build` → 提示用 `ezmk workspace build`（或 `ezmk build -w`）
- 无别名；未知子命令/未知成员 → fatal

### 3.2 拓扑分层（`include/ezmk/workspace.hpp` 扩展）

```cpp
// Kahn 算法：返回层列表（每层为并列可并行成员）
std::vector<std::vector<size_t>> topo_layers(const Workspace& ws);
// 失败：环已在 dev.1 validate_ws_deps 拒绝；此处仅作防御断言
```

- 节点 = 校验通过的成员；边 = `ws_deps`（已被 dev.1 解析为成员索引）
- 入度 0 成员入第 0 层；剥除后新入度 0 入下一层……（同层内互相无依赖，可并行）
- 依赖顺序保证：被依赖成员的层号严格小于依赖者层号

### 3.3 子进程执行（`src/workspace_build.cpp`）

- 每成员一个子进程：`<ezmk 可执行路径> build`，cwd = 成员目录（复用 `util::run_command`；继承环境变量）
  - **无需 `--no-workspace` 等开关**：成员进程自发现 workspace 只是"注入兄弟产物"的附加行为，不会递归触发 workspace 构建
- 层内并行：`util::ThreadPool`（worker 数 = `-j`/`default_jobs`/`hardware_concurrency`），每任务一个子进程
- **`--stop-on-error` 精确语义**（`build` 与 `test` 一致）：
  - 首个失败发生后，调度器**停止派发新任务**——本层未启动的成员与所有后续层标记 `skipped`
  - 已在运行的成员**自然结束，不 kill 子进程**（避免不确定中间状态）
  - 摘要含 succeeded/failed/skipped；退出码非零
  - 不设该 flag（默认）：全部成员跑完再汇总，任一失败 → 退出码非零
  - `clean` **不支持** `--stop-on-error`（clean 无依赖语义，批量执行、失败即汇总非零退出码）

### 3.4 兄弟产物注入：成员自发现（无环境变量）

成员 `ezmk.toml` 声明了 `[depends] workspace` 时，**该成员自己的构建进程**在启动时完成注入：

1. 读自身 `[depends] workspace`（dev.1 已把该字段解析进 `Config`）；非空才继续
2. `locate_workspace_root()`（≤5 层上溯）→ `load_from(root)` 得到 `Workspace`（复用 dev.1，含成员校验/依赖校验）
3. 对每个依赖名（末段或完整相对路径）在 members 中解析 → 路径
4. 追加注入参数（依赖成员类型已被 dev.1 校验为 `static`，此处防御性复核）：
   - `-I <ws>/<m>/include`（目录存在才加）
   - `-L <ws>/<m>/build -l<m>`（`build/lib<m>.a` 存在才加）
5. 注入参数进入**编译参数签名之前**（见 3.6）：签名含注入参数，依赖库参数变化 → 依赖者自动重编
6. 兄弟产物缺失（独立构建时）→ 提示「先 `ezmk workspace build` 或构建依赖成员」，继续构建本成员（缺失的 `-L/-l` 不注入，链接失败会自然报错并给出上一条提示）

**为什么自发现而非环境变量**：

| 方案 | 长度 | 正确性 | 结论 |
|------|------|--------|------|
| 环境变量传依赖列表（`EZK_WS_DEPS=...`） | 随依赖数线性增长 → Windows 环境块 32KB 上限，**大型项目无声炸** | orchestrator 与成员两份信息需保持一致 | ❌ 否决 |
| 环境变量传已解析路径 | 同上（更长） | 同上 | ❌ 否决 |
| **成员自发现** | 环境零开销，与规模无关 | 单一事实源 = workspace 文件；成员独立构建时也自动校验 | ✅ 采用 |

- 注入的 `-I` 优先级：成员自身 `include_dirs` > 注入 `-I` > 系统路径
- 成员 `ezmk.toml` 保持与单项目构建完全一致（工作区是"外面套的一层"）；注入逻辑全部在成员进程内，不写入任何文件

### 3.5 命令行长度兜底（响应文件）

- 编译/链接命令以整体字符串执行（`util::run_command`），Windows 侧受 CreateProcess 32767 字符限制——**超长直接失败且报错晦涩**（"command line too long"或静默截断）
- 对策：命令字符串长度 > **16K 字符**时，改写为 GCC 响应文件：参数逐行写入 `<tmp>/ezmk-<n>.rsp`，命令变 `g++ @<rsp> ...`（g++ 原生支持 `@file`；行内参数含空格不转义问题）
- 适用：编译命令 + 链接命令（链接命令本就长，注入 `-L/-l` 是最大推手）
- 属**通用加固**（深路径大项目同样受益），1.3.0 注入只是让问题更容易暴露；阈值 16K 保守于 32767，留足余量
- 响应文件写入用临时目录 + 使用后删除；内容 ASCII/UTF-8 无 BOM

### 3.6 增量语义

| 事件 | 效果 | 机制 |
|------|------|------|
| 依赖库 `.cpp` 变 → 库重编 | 库 `build/lib<m>.a` 时间戳/内容变 | 子进程自身增量（成员构建即单项目构建） |
| 库产物变 → 依赖者 | 依赖者**重新链接** | 链接阶段比较 `lib<m>.a` 时间戳 |
| 库 `.h` 变 | 依赖者**重新编译**该头引用翻译单元 | 依赖者 depfile 含 `<ws>/<m>/include` 头文件（注入 `-I` 进入预处理器，`-MD` 自动收录） |
| 库头文件变 | 依赖者编译参数签名不变 | 签名不哈希头文件内容——依赖者重编由 depfile 头哈希驱动（与单项目一致） |

- 签名：`compile_options_signature` 计算时已含注入的 `-I/-L/-l`（注入参数改变 → 签名变 → 全量重编该成员）
- **正确性保证**：依赖者重编/重链都由依赖库的**产物/头文件**驱动，不依赖用户手动 `clean`

### 3.7 与既有代码的边界

- **build.cpp 微扩**：编译/链接参数组装处增加"成员自发现注入"分支（`[depends] workspace` 非空才进入；默认路径零影响）+ 响应文件阈值分支
- **新增**：`src/workspace_build.cpp`（子进程编排 + 摘要打印）、`workspace.hpp` 的 `topo_layers`
- **既有命令零改动**：`ezmk build`（无 `-w`）行为完全不变；`ezmk clean` 同理
