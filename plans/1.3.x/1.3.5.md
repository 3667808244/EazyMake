# EazyMake 1.3.5 — pack 多格式输出（`--format zip|tar.gz`）+ SHA-256 边车

> 1.3.0 正式发布后的**补丁版本**（与 1.3.1 语言区间、1.3.2 测试报告、1.3.3 简写、1.3.4 watch `--run` 相互独立，可并行）。发布总览见 [`1.3.x/README.md`](README.md)。

---

## 1 背景

`pack_project`（[`src/build.cpp`](../../src/build.cpp) `:1576-1696`）只产出 `.tar.gz`（`:1598`，`util::create_targz`，`src/util.cpp:416`），而 **`extract_archive` 早已同时支持 `.tar.gz` / `.tgz` / `.zip`**（`src/util.cpp:841-851`，zip 走 vendored miniz，`miniz_zip.c`）——**消费 zip 早已可用，产出 zip 是缺口**：

- Windows 用户免 tar 直接解压（Windows 10+ 虽有内置 tar，但 zip 是原生双击即开的形态）；
- 发布生态（winget / 仓库 `file` 字段）常见 zip；
- `pkg install` 端到端闭环：`ezmk project pack --format zip` → `ezmk pkg install <dir或zip>` 零障碍。

**明确不做**（本版边界）：`.deb` / `.rpm` 等包管理器分发格式——由 `fpm` + `ezmk project install --prefix <staging>` 配方覆盖（non-goals 方向，见 [`docs/zh/non-goals.md`](../../docs/zh/non-goals.md) 相关讨论）；发布自动化不进 CLI。

| 6 | **明确不做**：`.deb` / `.rpm` / 其他包管理器格式；发布自动化 | P0 |

## 3 详细设计

### 3.1 CLI

- `project pack` spec（`src/cli.cpp:361-377`，现有 `--precompiled` / `--output`）追加 `{'\0', "format", true}`；
- `PackOptions.format`（缺省 `"tar.gz"`）；合法值：`tar.gz` / `zip`（大小写不敏感）；非法 → fatal（新 i18n key `cli_err_invalid_format`，复用风格）。

### 3.2 实现：stage 流程复用 + 归档器分发

- `pack_project` 现有流程（stage 目录构建 → 归档）**零改动**，仅 `:1696` 的 `create_targz(stage_dir, output_archive)` 改为按格式分发：
  - `tar.gz`：现状 `util::create_targz`；
  - `zip`：新增 `util::create_zip(source_dir, output_file)`（miniz `mz_zip_writer_*`，`miniz_zip.c` 已 vendor）。
- 归档名：`name-version.zip`（对应现有 `name-version.tar.gz`，`:1598`）。
- **zip 内部结构与 tar.gz 等价**：顶层 `name-version/` 目录 + 相对路径（与 `create_targz` 的打包结构一致，保证 `pkg install` 的顶层目录探测逻辑 `pkg.cpp:1510-1521` 行为一致）。

### 3.3 SHA-256 边车（P1）

- pack 成功后写 `<archive>.sha256`（`crypto::sha256_file` 已有），两种格式统一；
- 纯新增文件，不影响既有产物与消费路径；发布/仓库索引可直接引用。

### 3.4 已知坑位与对策

| # | 坑 | 优先级 | 对策 | 落点 |
|---|-----|--------|------|------|
| 1 | **zip 条目路径用反斜杠**（Windows）→ 解压坏档 | 高 | `create_zip` 内部统一 `/` 分隔符；测试含 Windows 路径断言 | §3.2 |
| 2 | **zip-slip**（条目名 `../` 逃逸） | 高 | 写侧只遍历 stage 内文件且路径规范化（相对、无 `..`）；复用 extract 侧 `safe_extract_path` 的校验思路 | §3.2 |
| 3 | miniz 写 API 与 targz 流式实现差异 | 中 | `create_zip` 独立实现（内存缓冲 or 顺序写），复用 `create_targz` 的目录遍历/排序 | §3.2 |
| 4 | 默认行为回归（无 `--format`） | 高 | 回归断言：默认仍产 `.tar.gz` | §3.4 测试 |
| 5 | `.sha256` 边车改变 pack 输出目录 | 低 | 新文件，不破坏现有产物；文档注明 | §3.3 |

### 3.5 测试

- **端到端**：`pack --format zip` → `ezmk pkg install <zip>` 成功（闭环消费，复用 1.2.5 pack 源码包端到端测试模式）；
- **等价性**：同一项目分别 `--format tar.gz` / `zip` → 解包后内容集合一致（文件清单 + 关键内容哈希）；
- **回归**：无 `--format` → 仍产 `.tar.gz`；非法格式（`--format deb`）→ fatal；
- **边车**：两种格式均产出 `.sha256` 且与 `crypto::sha256_file` 一致。

## 6 跨版本关注点

- **与 1.3.1 ~ 1.3.4 相互独立**：代码路径不相交（config/pkg / test 报告 / cli 别名 / watch 回调 / pack 归档），可并行推进；发布顺序按各自完成度。
- **`.deb` / `.rpm` 明确不做**：用户项目分发走 `fpm` + `ezmk project install --prefix <staging>` 配方（non-goals 方向）；ezmk 自身分发归 `publish/` 流水线——均不进 CLI 与版本计划。
- **与 1.2.5 的关系**：pack 默认源码包（1.2.5）语义不变；`--format` 与 `--precompiled` 可组合（预编译包也可选 zip）。
- **回归基线**：全量 863 用例 / 5007 断言（1.3.0-dev.5 后基线）。
- **i18n**：新增 `cli_err_invalid_format`；三向一致 + `check_i18n.py` 通过 + 重新生成 `locale_data.cpp`。
- **后续窗口**：`--format` 扩展其他归档（如 `tgz` 别名）、sha256 边车纳入 `pkg install --sha256` 自动校验（与 index.toml 联动）——归 1.4.0 或后续评估。
