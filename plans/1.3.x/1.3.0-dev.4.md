# EazyMake 1.3.0-dev.4 — 语言变体（locale variants）

> 1.3.0 第四个开发子版本。总览见 [`1.3.x/README.md`](README.md)，正式版设计见 [`1.3.0.md`](1.3.0.md)。

---

## 1 背景

当前 i18n 只支持**基础语言**：`locale/en.json` + `locale/zh.json`（336 键，`check_i18n.py` 三向一致）。`EZMK_LANG` / 系统检测只认 `en` / `zh` 两个值——`zh-CN`、`zh-TW`、`en-US` 等**变体标签**无法命中：

- `EZMK_LANG=zh-CN` → 归一化掉 `-CN` 落到 `zh`（简体中文），**用户选不了繁体**
- `EZMK_LANG=zh_CN`（下划线写法）→ **完全不归一化**（`detect_language` 只切 `-` 和 `.`），查不到数据后落到系统检测，行为不可预期
- 系统语言检测（Windows `GetUserDefaultLocaleName` / POSIX `$LANG`）同样只取前缀，`zh-TW` 系统下拿到的是简体中文文案

需要**语言变体（locale variant）**支持：变体标签（BCP 47 风格 `zh-TW` / `en-US` / `en-GB`）可显式选择，命中变体专属文案；无变体专属文件时**按链回退**（`zh-TW` → `zh` → `en`）；变体文件只需声明**与基础语言的差异**（继承式，免维护 336 键 × N 变体）。

## 3 详细设计

### 3.1 变体标签解析（`i18n.cpp` 新增 `normalize_locale_tag()`）

```cpp
// "zh-CN" / "zh_CN" / "zh_CN.UTF-8" / "zh-cn" / "ZH-cn" → "zh-CN"
// 规则：小写基础语言（2~3 字母） + 可选 "-" + 大写地区（2 字母）
std::string normalize_locale_tag(std::string_view raw);
```

- 输入拆分：先去 `.` 后的编码后缀（`zh_CN.UTF-8` → `zh_CN`）
- 分隔符统一：`_` / `-` 都视为分隔；分段后**首段小写**（语言）、**次段大写**（地区）
- 非法输入（空 / 非字母 / 超过两段）→ 返回空串，调用方回退检测逻辑
- 输出规范形：`en` / `zh` / `zh-TW` / `en-US` / `en-GB` —— 内部比较、JSON 键名、文件名全部用规范形

### 3.2 变体文件与继承加载

`locale/zh-TW.json` 结构（继承式，**可缺键**）：

```json
{
  "meta": {
    "language": "zh-TW",
    "language_name": "繁體中文",
    "version": "1",
    "extends": "zh"
  },
  "strings": {
    "build_success": "構建成功: {path}"
    // …… 只写与 zh 不同的键；未列出的键继承 locale/zh.json
  }
}
```

- `meta.extends`：声明继承哪个基础语言；缺省 → 取标签首段（`zh-TW` → `zh`）；显式声明更稳（如未来 `en-GB` extends `en`）
- **加载序列**（`i18n::init` 重写）：
  1. 定位目标语言：`EZMK_LANG` → 系统检测 → `"en"`（现状），输出**规范变体标签**
  2. 加载**基础语言**：`<tag 首段>.json`（runtime 文件 → embedded → 兜底链，现状不变）
  3. **叠加变体**：`locale/<tag>.json` 存在 → 解析其 `strings` 覆盖到 `g_strings`（只更新出现的键，不清空）；不存在 → 跳过（纯回退，无报错）
  4. `g_current_lang` 记录实际生效的标签（如 `zh-TW`；纯回退时记基础语言 `zh`）
- `parse_locale_json` 增加"覆盖模式"参数：`overlay=true` 时不 `g_strings.clear()`，逐键覆盖
- `meta.version` 校验沿用（变体文件同样要求 `version=1`）；`meta.language` 必须等于文件标签

### 3.3 检测路径统一（`detect_language()` 重写）

```
EZMK_LANG=zh_CN.UTF-8
  → normalize("zh_CN.UTF-8") = "zh-CN"
  → 命中条件放宽：规范标签或其首段有数据（embedded 或 runtime 文件）即采用
  → 返回 "zh-CN"
Windows GetUserDefaultLocaleName → "zh-TW" → normalize → "zh-TW"（原生即 BCP 47）
POSIX $LANG=zh_TW.UTF-8 → normalize → "zh-TW"
```

- 现有「只返回有数据的语言」守卫保留，但判断从「精确等于 en/zh」改为「标签或首段可解析」
- 优先级不变：`EZMK_LANG` > 平台检测 > `"en"` 兜底

### 3.4 首个变体文件 `locale/zh-TW.json`（繁体中文）

- **策略**：以 `zh.json` 为底稿做繁体转写——全部 336 键逐一核对，术语对齐（如「构建」→「構建」、「错误」→「錯誤」、「文件」→「檔案」）；代码/路径/占位符/命令名原样保留
- **继承使用**：即使个别键漏转写，回退链保证显示简体（可接受、可后续补）；`check_i18n.py` 保证「不多键」
- 不新增 `en-US`/`en-GB`（英文变体差异极小，收益低）——机制就绪，按需添加即可

### 3.5 `check_i18n.py` 扩展（变体校验）

| 检查 | 基础语言（en/zh） | 变体（其余 *.json） |
|------|-------------------|---------------------|
| 键 ⊆ def | **必须全等**（三向一致，现状） | **只允许子集**（缺键=继承，合法） |
| 键 ⊇ def | — | **不允许多余键**（防漂移，报错） |
| meta.extends | 无要求 | 缺省时取标签首段；显式声明必须存在对应基础文件 |

- 变体文件列表自动发现：`locale/*.json` 中除 `en`/`zh` 外的全部
- 变体文件必须可解析、`strings` 存在、`meta.language` 与文件名一致

### 3.6 与既有代码的边界

- **零改动**：`embed_locale.py`（按目录扫描，`zh-TW.json` 自动嵌入）、`i18n_keys.def`（键集合不变）、`ezmk_lua_main.cpp`
- **改动**：`src/i18n.cpp`（`normalize_locale_tag` + `detect_language` 重写 + `init` 继承加载 + `parse_locale_json` overlay 模式）、`scripts/check_i18n.py`、新增 `locale/zh-TW.json`
- **行为不变**：`EZMK_LANG=en` / `zh`（规范形）→ 结果与现状完全一致；未设 `EZMK_LANG` 且系统为 en/zh → 不变
- **行为增强**：`zh-CN` → 现命中 `zh`（等同现状）；`zh-TW` → 新增繁体文案；`zh_CN` 下划线 → 从「不可预期」变为「规范化命中」

## 6 跨版本关注点

- **与 dev.1 ~ dev.3 解耦**：workspace 的 `workspace_*` i18n 键自动继承（变体文件缺键回退 `zh`），无需联动。
- **回退链设计**：变体 → 基础 → 英文，保证任何新键（如 dev.2 的 `workspace_*`）在变体文件未转写时不出现 `{???}`。
- **键集合单一事实源**：`i18n_keys.def` 不变；变体文件只可能少于 def（继承），`check_i18n.py` 防「多键」漂移。
- **后续窗口**：`en-GB`/`en-US` 变体、完整 BCP 47（脚本/地区扩展如 `zh-Hant-TW`）按需添加，机制已就绪；归 2.0.0 或后续评估。
