## 1 背景

2026-11-08 对 `src/` 全部非 vendor 代码（约 2.1 万行）、`include/ezmk/` 头文件与 `build.sh` 做了逐文件审核，并用 clang-tidy（clang-analyzer / bugprone / performance 子集）、单元测试、离线集成测试与 4 个黑盒复现交叉验证。

结论：核心构建链路（单一命令构造、缓存签名、原子落盘、跨平台路径、workspace 拓扑）质量较高，但存在 **6 个 P1、约 20 个 P2 与若干 P3**。系统性问题集中在三处：

1. **错误路径被静默当成成功**（读失败返回半截哈希、pack 遍历出错继续打包、waitpid 失败当 0、repo 缺 sha256 不校验）；
2. **Windows/POSIX 语义分叉**（stdin、递归监听、CreateProcess 引用、环境变量大小写）；
3. **test 子管线长期落后于主构建管线**（对象命名、Catch2 include、包扫描顺序）。

阶段零已把 P1 与一批低风险 P2/P3 修复落地；本计划记录已落地项，并安排剩余项的修复、测试、文档与回归收口。

## 5 兼容性

| 变更 | 影响 | 缓解 |
|------|------|------|
| `project.name` 必须是安全 basename | 非法名字（`../x`、盘符、分隔符）由静默接受变为报错 | 文档 + 明确错误信息；正常项目名不受影响 |
| Lua 沙箱内存/墙钟上限 | 恶意或失控脚本会更早失败 | 默认阈值按正常构建留足余量；错误信息说明预算 |
| Linux/macOS watch 递归 | 监听 fd 数量随目录深度增加 | 限制深度/数量并告警；可用 `[watch].ignore` 剪枝 |
| `[settings].linker` 生效 | 配置了该键的用户链接器改变 | 空值保持原行为；启动日志提示实际链接器 |
| C 项目缓存标识 | 换 `CC` 后首次构建全量重编 | 一次性成本；之后恢复增量 |
| `build.sh` 默认告警/优化 | 编译变慢、历史告警可能出现 | 首方代码清零；`CXXFLAGS` 可覆盖 |
| i18n key 清理 | 无用户可见变化（仅删除未引用键） | 保留公共键；三向校验 |
| 公共 API | 无破坏性变更 | 仅内部行为与诊断增强 |
