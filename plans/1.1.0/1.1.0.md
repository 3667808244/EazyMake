## 3 发布步骤

### 阶段一：冻结与回归

1. 合并所有 pre.3 收尾提交，`git status` 干净
2. 本地全量回归：`bash build.sh test-all`（556/2666 零回归）
3. 确认 CI 工作流在最后一次 push 上绿色（含 zsh-completions job）

### 阶段二：打 tag 触发 Release

4. `git tag v1.1.0` + `git push origin v1.1.0`
5. 创建 GitHub Release → `release.yml` 运行 4 平台 job，产出 `ezmk-windows-x64.zip`、`ezmk-linux-x64.tar.gz`、`ezmk-macos-x64.tar.gz`、`ezmk-macos-arm64.tar.gz`
6. 人工核对：每个 job 的 `res/ezmk.zsh` 被拷贝为 `_ezmk`；二进制可运行（`./ezmk version`）

### 阶段三：分发渠道

7. **Homebrew**：以 Release 的 `ezmk-linux-x64.tar.gz` URL + `sha256sum` 填 `homebrew-eazymake/ezmk.rb`，`brew install` 冒烟
8. **winget**：以 Release 的 Windows 安装包 URL + sha256 填 manifest，提交 `microsoft/winget-pkgs` PR（后续由 winget 官方审批合并）
9. **install.sh**：真实 Linux 环境验证（含 zsh 补全）；**install.ps1**：Windows 验证

### 阶段四：收尾

10. `CHANGES.md` 补 1.1.0 条目；`plans/README.md` 状态更新
11. 发布门槛最终核对（§2.1 三项）
12. 若任何一项不满足，回退 tag 并修复，禁止带病发布

## 4 兼容性

1.1.0 全周期（dev.1 ~ pre.3）公共 API 无破坏性变更：

| 变更 | 兼容性处理 |
|------|-----------|
| 顶层别名（`ezmk build` 等） | 纯增量，完整形式 `project <action>` 不变 |
| `[test]` / `[install]` 配置节 | 新增可选字段，不影响既有配置 |
| `run_command()` 加 timeout 参数 | 默认参数，调用方不传即无超时 |
| CI / Homebrew / winget | 新渠道，纯增量 |
| `check_built` / Catch2 解析修正 | 修复边缘 bug，行为更正确 |

破坏性变更仅在 `2.0.0` 引入（`CHANGES.md` API 稳定性承诺）。

## 5 风险与关注点

- **release.yml 首次真实运行**：从未被 Release 触发验证，4 平台构建可能在 macOS（`clang++` 别名、静态链接）或打包路径上出错——首次 Release 需现场修复并补跑
- **winget 审批周期**：提交 `winget-pkgs` 后由官方维护者审批，不阻塞 1.1.0 发布，作为 1.1.0 发布后跟进项
- **Homebrew 依赖 Release 产物**：必须在 §阶段二 Release 完成且 sha256 已知后才能填公式
- **zsh 补全真实验证**：只能在 Linux/macOS 完成；CI 的 zsh-completions job 已覆盖 install.sh 的激活逻辑
