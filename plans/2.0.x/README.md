## 定位

`CHANGES.md` §API Stability 的既有承诺：**破坏性变更只在 `2.0.0` 引入，且提前至少一个次版本发出弃用警告**。因此 2.0.0 的性质与 1.x 不同——它有两个必须交付的面：

1. **移除面**（本目录 `REMOVALS.md`）：把 1.x 期间弃用/垫片化的接口清掉，并给出迁移指南；
2. **新增/重构面**（待立项）：在移除窗口内才划算的破坏性改进（例如 `cli.cpp` 单文件命令组拆分到 2.0.0 前评估、配置未知键策略升级为 fail-fast 等）。

## 与 1.4.x 的边界

- **1.4.x（含 1.4.4）不放宽、不提前移除任何弃用面**；本清单只登记、不执行。
- 触发条件很硬：删 `[test].flags` 或 `ezmk utils cc` 会让 `scripts/check_man_sync.py` 与 `scripts/check_i18n.py` **立刻变红**（1.4.3 埋下的设计意图）——2.0.0 计划必须把"同步 man / i18n / 测试夹具 / 文档"写成**显式交付项**。
- 1.4.4 的遗留清理（`install.ps1 -DryRun`、测试告警、`.gitignore`、过期 TODO、`macos-x64` job、docs-sync 接线）见 [`../1.4.x/1.4.4.md`](../1.4.x/1.4.4.md)，与本目录正交。

## 与发布流程的关系

2.0.0 仍需满足 1.1.0-pre.3 定义的发布门槛（① 清单完成 ② API 兼容——**本版例外：允许破坏性变更** ③ 全量零回归），并额外要求：

- `CHANGES.md` 提供**逐条迁移指南**（旧写法 → 新写法），而非仅列变更；
- 三渠道分发同 1.x（Homebrew / winget / pacman），Windows 侧同样不含 man；
- 移除项的**负向用例**（旧写法必须得到明确报错或迁移提示，而不是静默失效）纳入回归。
